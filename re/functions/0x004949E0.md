## Purpose

A drop-in for `MessageBoxA(NULL, text, caption, type)` with three arguments
(text, caption, type) that shows the box inside the game UI when it can.
Order of what it touches:

1. Byte 0x00B06B38 set: answers at once, nothing shown, **no clock bracket**
   (5 for type nibble 2, else 6) (read 0x004949E3-0x00494A0E).
2. Otherwise: `TimeInfo::Freeze` 0x0047D120 on `g_timeInfo` 0x00B33E90
   (0x00494A13/0x00494A18). Everything below runs inside the bracket.
3. Guards (reentrancy byte 0x00B06B16, `g_osGlobals` 0x00B33398 and its
   +0x20, main thread via `GetCurrentThreadId` vs +0x10). Any guard fails:
   step 5.
4. In-game path: clears 0x00B06B16, picks button labels by type, calls
   `ShowMessageBox` 0x00579C10. If that returns 0: result 6, step 6.
   Otherwise saves/overrides some state on the object at [0x00B3A6B0]
   (0x00572DF0, 0x00579930, 0x00572EC0) and enters a **modal loop**:
   Win32 message pump (PeekMessageA/TranslateMessage/DispatchMessageA),
   then, only while the game window is the active window, input poll and
   key tests that may set `choice`; menu calls 0x005791A0, 0x00579970 +
   0x00578D70 (second source of `choice`), close step, 0x00579220; always
   0x00579260(0) and 0x005792B0. Repeats while `choice == 0xFF`. Then the
   jump table at 0x00494E70 turns `choice` into a result, 0x00578DA0,
   0x00579260(0), 0x005792B0, optional restore 0x005732D0, sets 0x00B06B16
   = 1.
5. No-UI path: 0x00B06C74 and 0x00B34FA8 both nonzero: auto-answer
   (5 for type nibble 2, else 6). Otherwise the real
   `MessageBoxA(NULL, text, caption, type)` (IAT 0x00A28258), a blocking
   modal Win32 dialog per Microsoft Learn.
6. A result of 4 becomes 5; `TimeInfo::Unfreeze` 0x0047D0F0
   (0x00494E59/0x00494E5E); return the result.

**Answer to slice question 2 (how long the clock stays frozen):** inside
the bracket the function both pumps messages and waits:

- In-game path: a loop with no iteration count or timeout in this
  function's own instructions; its only exit is `choice != 0xFF` at
  0x00494D73 (read). `choice` is set by a key test (only while the game
  window is active, 0x00494B78/0x00494B7A) or by AL of 0x00578D70 (read).
  PeekMessageA is called with PM_REMOVE and returns zero when no message is
  available (Microsoft Learn), so the pump itself does not block; whether
  any of the loop's callees blocks, sleeps or renders is **unverified**:
  0x005791A0, 0x00579970, 0x00578D70, 0x00579220, 0x00579260 and
  0x005792B0 are not in the export; a map-only export of that group would
  settle it. This function's own Unfreeze (0x00494E5E) does not run before
  `choice != 0xFF` (read: single loop exit 0x00494D78). Whether the clock
  stays frozen that whole time also needs no unmatched
  `TimeInfo::Unfreeze` to run in a message dispatched at 0x00494B50 or in
  an unexported loop callee; that is **unverified** (claim 16, open
  question 8). While the window is not active the
  loop still spins, skipping input (0x00494B7A -> 0x00494D64, read).
- MessageBoxA path: the call at 0x00494E40 lies between Freeze (0x00494A18)
  and Unfreeze (0x00494E5E) (read); MessageBoxA is modal and returns when
  the user selects a button (Microsoft Learn), so the call lies inside this
  function's Freeze/Unfreeze bracket for the whole dialog (read). That the
  clock stays frozen also assumes no unmatched `TimeInfo::Unfreeze` runs in
  the window procedure that MessageBoxA's modal loop dispatches to; that is
  **unverified** (open question 8).
- Auto-answer and ShowMessageBox-failed paths: frozen only for the few
  instructions between the two calls (derived from the straight-line paths
  0x00494E0B-0x00494E2D and 0x00494AD5 -> 0x00494E02).
- Early-out (0x00B06B38 set): never frozen (read: returns at 0x00494A0E
  before 0x00494A13).

What the freeze does to the clock comes from `knowledge/frame-clock.md`,
not from this export: Freeze/Unfreeze are a nesting counter at TimeInfo
+0x00 that shifts clockMs (+0x10) and startTick (+0x14) by the frozen
stretch, so the next update's delta excludes the wait; while the counter is
nonzero an update writes frameSeconds as 0 (knowledge/frame-clock.md,
TimeInfo table row +0x00 and the "bracket pair" paragraph). Whether any
callee in the loop runs `TimeInfo::Update` while frozen is **unverified**.

1. **read** - The function reads no field of `g_timeInfo` 0x00B33E90 itself;
   both references are `MOV ECX,0xb33e90` (0x00494A13, 0x00494E59) followed
   by `CALL 0x0047d120` (0x00494A18) and `CALL 0x0047d0f0` (0x00494E5E).

   holds 0x00494D90, 0x00494D9A, 0x00494DA4, 0x00494DAE, 0x00494DB8,
   0x00494DC2 for indices 0..5, followed by `cc` padding. This settles the
   pilot's dispute and its open question 7.
3. **read** (asm.s 0x00494D90-0x00494DC2) - Those targets write `result` =
   6, 7, 2, 3, 4, 5 in that order. **derived** (claims 2, 3): choice 0->6,
   1->7, 2->2, 3->3, 4->4, 5->5 before the fold.
4. **derived** (from the instruction ranges 0x00494A13..0x00494E59 and every
   jump inside them landing inside them, read) - Every path that runs
   Freeze also runs Unfreeze exactly once; the early-out at 0x004949F4 runs
   neither.
5. **derived** (claims 2, 3; fold 0x00494E4A-0x00494E51 reached from every
   case body via 0x00494DCA -> 0x00494E02 -> `JMP 0x00494e4a` 0x00494E09,
   and from MessageBoxA at 0x00494E46; read) - The function never returns
