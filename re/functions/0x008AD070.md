## Purpose

When called, it (1) resets the caller's point collector, (2) widens the Havok world's shared collision
tolerance by the proxy's two floats at +0x58 and +0x5C, (3) lets the proxy's phantom fill the collector
through phantom vtable +0x34, (4) restores the tolerance to the saved dword, (5) builds a second
collector on its own stack and hands both collectors to the proxy's vtable +0x08, (6) frees the second
collector's hit array if it left the inline buffer. Steps 1-5 are read (addresses below); step 6 is read
as a call to 0x008A75D0 only when bit 31 of C+0x18 is clear - that the call frees memory is unverified
(0x008A75D0 not followed). That step 3 is a closest-points query and step 5 a manifold update is
unverified: it rests on the seed context (support check) and on the code's shape resembling
`hkpCharacterProxy`, not on a followed callee. Neither indirect callee was resolved, and no string or data
reference names them. Other readings are not excluded by the export: vt+0x34 could be any
tolerance-dependent query (penetrations or closest points), and vt+0x08 any consumer of two collectors.
The pattern resembles the published Havok `hkpCharacterProxy` support check (collector reset,
`input.m_tolerance += keepDistance + keepContactTolerance`, `getClosestPoints`, `updateManifold`), but that
source was not consulted in this run: the Havok mapping and the proposed name are unverified. What would
settle it: resolve the proxy's and the phantom's vtables (from the constructor or the caller 0x008AE100),
read the slot targets +0x34 and +0x08, and check them against Havok's `hkpCharacterProxy::updateManifold`
and `getClosestPoints`.

No clock or time global is read or written by its own instructions (derived: data.json has only the
three addresses above; none is a clock).

## Control flow

No loop. Two conditional branches, three flows.

| # | at | condition | effect | mark |
|---|---|---|---|---|
| 1 | 0x008AD0FE `JS 0x008AD138` | C+0x18 (capacity and flags) has bit 31 set after `this` vt+0x08 returns | skip the free, return | read |
| 2 | 0x008AD118 `JNZ 0x008AD120` | TLS block +0x19C non-zero | use the thread allocator; else load [0x00BA7D9C] at 0x008AD11A | read |

Test flows for a rebuild:
- F1: the vcall left the inline buffer (bit 31 still set) -> no free.
- F2: bit 31 clear, TLS allocator set -> `0x008A75D0(ECX = TLS allocator, ptr = [C+0x10], bytes = (cap & 0x3FFFFFFF) * 0x30, 0x14)`.
- F3: bit 31 clear, TLS allocator null -> the same call with ECX = [0x00BA7D9C].

That bit 31 clears only when the array grows past its 8 inline entries is unverified (the growth happens
inside `this` vt+0x08, not followed). Before every flow the tolerance write and restore run
unconditionally (read: no branch between 0x008AD080 and 0x008AD0F1).

## The tolerance write and restore (slice question 1)

1. 0x008AD0A1 `MOV EDX,[EDI+0x8]` - the original tolerance dword is read (EDI = [world+0x74], loaded at 0x008AD09E). Read.
2. 0x008AD0A8 `MOV [ESP+0x10],EDX` - saved to L. Read (slot derived, stack tracking above).
3. 0x008AD094/0x008AD09A/0x008AD0A4 - x87: `[this+0x5C] + [this+0x58]`, then `+ [EDI+8]`, in that order. Read.
4. 0x008AD0AC `FSTP float [EDI+0x8]` - the widened tolerance is stored into the shared collision input. Read.
5. 0x008AD0B4 `CALL [phantom vtable+0x34]` with ECX = phantom, one argument = the start collector. This is the only instruction that runs between the write and the restore (read). That the callee reads [world+0x74]+8: unverified (not followed). Supporting: the cast 0x008ECC60, phantom vt+0x30, reads the same field at 0x008ECC8C (knowledge/actor-frame-map.md; 0x008ECC60.md in progress).
6. 0x008AD0B7 `MOV ECX,[ESP+0xC]` / 0x008AD0BB `MOV [EDI+0x8],ECX` - the saved dword is written back, bit-exact (integer move, not an FPU store). Read; slot derived.

Pseudocode disagreement: pseudo.c writes `*(iVar1 + 8) = unaff_EBX` for step 6, i.e. it believes the
restore stores the caller's EBX. The instructions reload the slot written at 0x008AD0A8; with the vcall
popping its argument (derived, see stack tracking) that slot holds the original tolerance. The
instructions win; pseudo.c's `unaff_EBX` is a stack-depth error of the decompiler (derived).

For threads (a conditional hazard, derived from steps 4-6 and the absent lock): the write has no lock
prefix and no lock call around it in this function (read: no LOCK byte in asm.s, no call besides the
phantom vcall before the restore). Whether the caller 0x008AE100 or the world (controller vt+0x58 lock
pairs in knowledge/actor-frame-map.md) serialises the support check is unverified (open question 3).
Only if two calls overlap without an outer lock, or other readers run concurrently with this call: a
reader of [world+0x74]+8 in the same world - for example the cast 0x008ECC60 (R 0x008ECC8C) - running
between 0x008AD0AC and 0x008AD0BB sees the widened value, and two overlapping calls on the same world can
leave a widened value behind permanently (proxy A saves t, B saves t+dA, A restores t, B restores t+dA).
What would settle it: follow 0x008AE100 and the hkpWorld lock above it.
