## Purpose

Uploads an indexed array of matrices (the skinning bone palette of one skin
partition) as vertex shader float constants. It accepts the entry only when
the entry's type, through the identity table 0x00B428D8, is 8 or 9 (matrix
types per re/functions/0x007830C0.md C8, unverified). For each bone `i` of
`count` it issues one `SetVertexShaderConstantF(device, reg0 + i*stride,
base + indices[i]*stride*16, stride)`, where `reg0` is the entry's start
register (entry+0x1C). It returns AL = 1 after the loop (whatever the
device calls returned) and AL = 0 when the type check fails.

The destination registers are contiguous: bone `i` occupies registers
`[reg0 + i*stride, reg0 + (i+1)*stride)`. The source blocks are gathered
through the 16-bit index list. They are adjacent and in order if and only if
`indices[i] == indices[0] + i` for every `i` (any consecutive ascending run;
identity is the special case `indices[0] == 0`); then they form one block
starting at `base + indices[0]*stride*16` (derived from C4).

## Calling convention and parameters

`__thiscall`, callee cleans 20 bytes (`RET 0x14` at 0x007831D2 and
0x0078322D). `this` arrives in ECX and is spilled to the stack slot created
by `PUSH ECX` 0x00783180 (`MOV [ESP+8],ECX` 0x00783191, after two more
pushes), reloaded per bone at 0x007831F8 (`MOV EAX,[ESP+0x10]` after five
pushes). Saved registers: ESI, EDI (0x00783188, 0x0078318D), EBX, EBP on
the accept path (0x007831D5, 0x007831D9).

Stack offsets at the loop (pushes ECX, ESI, EDI, EBX, EBP = 0x14 bytes,
return address at +0x14): arg1 at +0x18, arg2 +0x1C, arg3 +0x20, arg4
+0x24, arg5 +0x28.

Caller mapping: 0x009A56D0 pushes EBX (partition+0x04), EAX (skin+0x24),
the word partition+0x20, EDX (skin+0x20), entry ([EBP+0xC]) in that order
(0x009A5B24..0x009A5B32), with ECX = program ([EBP+8], 0x009A5B1F), then
`CALL [vtbl+0x2C]` at 0x009A5B33 (export/pass-drivers/0x009A56D0/asm.s
lines 317-334, read).

Return: `bool` in AL only. The fail path sets AL with `XOR AL,AL`
(0x007831CE), the accept path with `MOV AL,1` (0x00783229); the upper 24
bits of EAX are not cleared (they hold the last device call's HRESULT bits,
or whatever 0x00783C70 / the caller left there). The caller tests AL at
0x009A60E4 (re/functions/0x009A56D0.md C11, in progress).

Per-bone instruction order (B7): load `indices` (0x007831F0), read
`indices[i]` (0x007831F4), reload `this` (0x007831F8), `indices[i] *= stride`
(0x007831FC), read `this+0x24` (0x007831FF), read the device (0x00783202),
read the device vtable (0x00783208), `<<4` (0x0078320A), add `base`
(0x0078320D), push stride, data, reg, device (0x00783211..0x00783214), read
slot +0x178 (0x00783215), call (0x0078321B). The device pointer and its
vtable entry are re-read for every bone (read, 0x007831FF..0x00783215).

Pseudocode disagreement: pseudo.c returns `undefined4` 0 / 1 as full
32-bit values. The instructions set AL only (`XOR AL,AL` 0x007831CE,
`MOV AL,1` 0x00783229). The instructions win; callers must test AL only.
pseudo.c otherwise agrees with the instructions (argument order of the
device call, start register increment by `stride`, the double table check).

## Open questions

- The run-time value of `stride` (skin+0x24): 3 (4x3 rows) or 4. Settles the
  rows per bone and the register footprint `count*stride`.
- The bone count per partition on the fixed Walkers scene (partition word
  +0x20), and with it the device calls per invocation; 0.33 us a call is
  only interpretable with that number.
- Whether the per-bone source blocks are contiguous in practice
  (`indices[i] == indices[0] + i`) - if they are, the single call from
  `base + indices[0]*stride*16` needs no gather.
- Whether any per-bone call fails in practice (start register range beyond
  the device's vertex constant limit). With one large call, D3D9 would fail
  the whole range rather than only the bones past the limit (D3D9 behaviour
  unverified).
- What OBVR's method-94 detour does per call (cache, compare, forward):
  a rebuild that merges the calls changes what that hook sees.
- The type ids 8 and 9 as MATRIX3 / MATRIX4 (re/functions/0x007830C0.md C8,
  unverified): whether the type decides 3 or 4 rows anywhere, given that this
  body uses only `stride`.
- Whether HLSL vertex programs (slot 11 = 0x007839C0) carry the bones in the
  measured scene instead of this function.

## Callees and smaller slices worth their own work

- 0x00783C70 - fills the type identity tables (re/functions/0x007830C0.md C6). Trivial; no slice.
- Device method 94 (+0x178) - D3D9 runtime (and OBVR's detour), not engine code.
- No other callee. The lever is in the caller: 0x009A56D0's ids 33-36 path
  (0x009A5B08..0x009A5B35) and the writer of skin +0x20 / +0x24 (where the
  bone palette is built each frame), which is worth its own slice for the
  "one call per partition" rebuild.

## Layout requests

A shared header (e.g. `src/engine/render/ShaderConstants.h`) would need:

- `NiD3DShaderConstantMapEntry` (name unverified): `uint32 type` at +0x14
  (low byte used), `uint32 shaderRegister` at +0x1C (same as 0x007830C0).
- `NiD3DShaderProgram`: `uint32 renderState` (handle) at +0x24; vtable slot 11
  (+0x2C) = SetVertexShaderConstantArray(entry, base, count, stride, indices)
  -> bool in AL, `RET 0x14`.
- Render-state-like object: `uint32 device` (IDirect3DDevice9 handle) at +0xFF8.
- Skin data (name unverified): `uint32 boneMatrices` (handle) at +0x20,
  `uint32 registersPerBone` at +0x24.
- Skin partition (name unverified): `uint32 bones` (handle to uint16[]) at
  +0x04, `uint16 boneCount` at +0x20.
- Device slot constant: 94 (SetVertexShaderConstantF, OBVR-verified).
- Globals: `kTypeTable = 0x00B428D8`, `kTypeTableReady = 0x00B4295B`;
  accepted table values 8 and 9.
