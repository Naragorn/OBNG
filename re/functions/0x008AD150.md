## Purpose

It rebuilds the proxy's contact manifold (array of 0x30-byte contact points at this+0x74) from a fresh
set of hits and re-registers the proxy as a listener on every body and phantom the manifold touches.
In order (all read, addresses in Control flow):

1. Unregisters the proxy's entity-listener subobject (this+0x08) from every body in this+0x8C[0..n) via
   0x008A6300 and clears the count +0x90; the same for the phantom-listener subobject (this+0x0C) from
   every phantom in this+0x98 via 0x008DE670, count +0x9C := 0.
2. Takes a scratch block of `(n*0x30 + 0x10) & ~0xF` bytes through the Havok thread memory (TLS
   +0x19C, else [0x00BA7D9C]), n = arg1+0x14: bumped from that allocator's stack only when
   top+size <= [mem+0x2C] (0x008AD208/0x008AD20B), otherwise from mem vt+0x0C(size) (0x008AD217; where
   that block comes from is unverified, settled by following vt+0x0C's target), and copies arg1's n hits into it, keeping the smallest
   float at hit +0x1C (initial 0x7F7FFFFF = FLT_MAX).
3. For each manifold point from the last to the first: finds the copied hit with the smallest
   0x008ABF70 score below 1.1 (0x3F8CCCCD, immediate at 0x008AD2BA). Match found: when the hit's +0x28
   differs from the point's +0x28, every proxy listener gets vt+0x0C(old point) then vt+0x08(new hit);
   the point is overwritten by the hit and the hit is swap-removed from the scratch array. No match:
   every listener gets vt+0x0C(point) and the point is swap-removed from the manifold.
4. Each remaining scratch hit whose +0x1C equals the minimum exactly and for which 0x008AC640 returns a
   negative index: listeners vt+0x08(hit), then appended to the manifold.
5. When arg2 holds at least one hit: its first hit, when 0x008AC640 returns -1, is announced
   (vt+0x08) and appended.
6. Removes near-duplicates: for i from size-1 down to 1, the first j < i (from i-1 down) with
   0x008ABF70(m[i], m[j]) < 0.1 removes m[i] (listeners vt+0x0C, swap-remove).
7. For each manifold point: its collidable [pt+0x28]; type byte +0x18 == 1 -> owner registered as body
   (0x008A6550 with this+0x08, pushed to this+0x8C); type == 2 -> owner registered as phantom
   (0x008DE710 with this+0x0C, pushed to this+0x98); only when the owner is not already in that list.
8. Returns the scratch block to the allocator (+0x20 := block; vt+0x10 when block == [mem+0x28]).

Hkp-style naming ("start points", "cast collector", "contact added/removed") follows the published
`hkpCharacterProxy::updateManifold` shape and is unverified: no string or RTTI in this function names it.

## Thread safety (slice question)

Could two threads run this at once for two different proxies? **Not safely as built** (derived):
1. Steps 1 and 7 write the listener arrays of other objects (body +0xAC/+0xB0, phantom +0x5C/+0x60)
   through 0x008A6300/0x008A6550/0x008DE670/0x008DE710, whose add and remove of data and count have
   no LOCK prefix and no lock call (read: this function and the four callees' bytes). Whether
   0x008A6EE0's allocator takes a lock is unverified (settled by reading 0x008A6EE0/0x008A7560); the
   unsafety conclusion rests on the unlocked add and remove of data and count alone. Two proxies touching the same body (shared
   ground, a static, the same other character's phantom) race on the same array: lost appends, a
   double grow through 0x008A6EE0 (heap free of a buffer the other thread still writes), and
   0x008DE670's shift-down interleaved with an append. This happens on every call, not only when the
   contact set changes (C4).
2. The proxy listeners' vt+0x08/+0x0C run per contact change; what they touch is unverified.
3. When a worker's TLS +0x19C is 0 the scratch block comes from the shared [0x00BA7D9C] with an
   unlocked bump of +0x20 (read); with a set per-thread memory this is per thread.
4. 0x008A6EE0's allocator (0x008A7560/0x008A75D0) and its locking: unverified.
5. Reads of other collidables (+0x10, +0x18) race with any main-thread change to them (unverified
   whether the main thread changes them during the controllers).
What would make it safe (proposal, not built): defer steps 1 and 7 (the listener add/remove on other
objects) into a per-proxy list applied on one thread afterwards, and give every worker its own thread
memory at TLS +0x19C.

  +0x74/+0x78/+0x7C manifold (data, count, capacity|flags); +0x80/+0x84 listener array (data, count;

  +0x20, +0x24, +0x28 collidable handle, +0x2C.
