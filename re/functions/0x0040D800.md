## Purpose

The per-frame body of the main loop's frame. In order it:

1. sets Havok's pause from the menu state and, on the first frame in a menu,
   gives every high-process actor and the player one call of 0x00651DD0
   (0x0040D809-0x0040D88C);
2. counts the frame (`++[0x00B02C54]`, 0x0040D898) and reads the clock once:
   `GetTickCount` (IAT 0x00A280D0, 0x0040D89F) into `TimeInfo::Update`
   0x0047D170 on `g_timeInfo` 0x00B33E90 (0x0040D8A5-0x0040D8AB);
3. hands `frameSeconds` to the Havok step planner `PlanHavokSteps`
   0x00889810 (0x0040D8B0-0x0040D8C2), then polls input (0x0040D8CD) and the
   IO manager (0x0040D8D8);
4. advances the game subsystems, each behind its own fresh `IsMenuMode`
   call: menu snapshot, world/game time, sound, actor AI, the player, the
   camera, the player's position in the world, actor-process time, TES
   (sky/weather per the RTM label) time, a scene-node update;
5. ends with menu bookkeeping and calls the render routine 0x0040D4D0
   (0x0040DF54), then one optional one-shot (0x0040DF61).

`frameSeconds` (`g_timeInfo`+0x0C = 0x00B33E9C) is read six times, all after
the update at 0x0040D8AB, and never written in this body (**read**: the
five `FLD [0x00B33E9C]` at 0x0040D8B0, 0x0040DB8B, 0x0040DC8E, 0x0040DE62,
0x0040DEAF and the `FMUL [0x00B33E9C]` at 0x0040DE89; no store to
0x00B33E9C in asm.s).

### Clock sources

- `GetTickCount` is read exactly once in the body, at 0x0040D89F, through
  0x00A280D0 (**read**: the only reference to 0x00A280D0 in asm.s and
  meta.json `data_refs`; data.json types 0x00A280D0 as a pointer).
- Its result feeds only `TimeInfo::Update` (`PUSH EAX` 0x0040D8A5 is its
  only use before the call at 0x0040D8AB; **read**).
- All six `frameSeconds` reads come after that call (**derived**: all six
  addresses > 0x0040D8AB, and the only backward jump is the actor loop at
  0x0040D875).
- `fixedStepMs` (+0x04), which `TimeInfo::Update` reads to choose fixed-step
  mode (`knowledge/frame-clock.md`), is written by 0x0040D4D0 at
  0x0040D7A3/0x0040D7AD/0x0040D7B7 (**read** in that export), and
  0x0040D4D0 runs at the end of this body (0x0040DF54, after the update at
  0x0040D8AB; **read**). So the next `TimeInfo::Update` call of 0x0040D800
  that can see a value stored there in frame N is frame N+1's (**derived**
  from the call order). This holds provided neither 0x00406360 (store at
  0x0040692B) nor 0x0040D4D0 run from its four other callers (0x0044E720,
  0x00440C40, 0x005BDCD0, 0x004455E0) rewrites it in between (**unverified**).
  Whether any other reader (for example 0x00497E70 at 0x0040DF61) uses it
  first is **unverified**. What value is written is 0x0040D4D0's question
  (in progress).
- Two other time-like inputs, neither a clock: the float [0x00B06530] (image
  value 1.0, data.json) scales frameSeconds for 0x004424D0, and the float
  [0x00B33A48] (image value 0.0) goes to 0x005732D0 in the one-shot block
  (**read**; meaning unverified).
- Whether a callee reads a clock of its own is **unverified** (callees not
  exported).

## Calling convention and parameters

- `this` arrives in ECX and is kept in EBP for the whole body (`MOV EBP,ECX`
  0x0040D807; EBP is never written again before `POP EBP` 0x0040DF6E)
  (**read**).
- `this` is used as `[EBP+0x20]` (ECX for `OSInputGlobals::PollAndUpdateInputState`
  0x004046A0, 0x0040D8C7) and `[EBP+0x24]` (ECX for 0x006AE860, 0x0040DBB0),
  and itself as ECX for 0x0040D160 (0x0040DA60, 0x0040DEF3), 0x00407AE0
  (0x0040DEFA) and 0x0040D4D0 (0x0040DF52) (**read**).
- `this` is an `OSGlobals` (`*g_osGlobals` 0x00B33398) (**derived**: xOBSE
  `GameOSDepend.h` lays out `OSGlobals` with `input` at +0x20 and `sound` at
  +0x24; OBVR `GameSound.cpp:15-16` reads the sound system from
  `*(0x00B33398)+0x24`). 0x0040D4D0 uses the same receiver the same way
  (`MOV EBP,ECX` 0x0040D4E9, `MOV ECX,[EBP+0x20]` 0x0040D6FC in its export;
  **read**), consistent with being passed this `this`.
- No stack arguments (**derived**, pilot analysis unchanged: with base = ESP
  after the four pushes, every ESP-relative access lands in the 0x10 bytes
  of locals or in an outgoing argument slot just made by `PUSH`/`SUB ESP`;
  none reaches base+0x24, under either `ret N` reading of 0x004C9CF0 and
  0x0067ACA0).
- Stack cleanup: plain `RET` at 0x0040DF73, no `ret N` (**read**). So:
  `thiscall` with zero stack arguments (**derived**).
- Callee-saved EBX, EBP, ESI, EDI pushed at 0x0040D803-0x0040D806, popped at
  0x0040DF6C-0x0040DF6F; `SUB ESP,0x10` / `ADD ESP,0x10` at 0x0040D800 /
  0x0040DF70; EBX = 0 from 0x0040D81C and used as the zero for every compare
  and store (**read**).
- Return value: no `MOV EAX` before 0x0040DF73 on any path (**read**). EAX
  is left by 0x0040D4D0 (0x0040DF54) or 0x00497E70 (0x0040DF61), and on the
  0x0040DF5F path by the `CMP` sequence (**read**). That it returns `void`
  is **unverified**: no caller is known (meta.json `callers` is `[]`), so
  whether a caller uses EAX cannot be checked. Finding the caller and
  reading the instructions after its call would settle it.
