## Purpose

An in-place recursive quicksort over an array of 0x30-byte records, ascending by the
float at record offset +0x14, using the middle record's key as the pivot (Hoare-style
partition with two inward scans). It is called by 0x008B22F0 on the array at
`[collector+0x10]` with count `[collector+0x14]`, after the cast in 0x0088B850; the caller
then reads record 0 (0x0088B9FE..0x0088BA04), i.e. the record with the smallest key.

It touches nothing but its own array and its own stack: no global, no TLS slot, no world,
no lock, no counter, no queue, no heap call. Answer to the slice question: it does **not**
lock, count or queue on the world (read: no call other than itself, no absolute address
operand anywhere in asm.s).

## Control flow

Notation: i = ESI, j = EDX, pivot = record[(lo+hi)>>1].fraction (SAR, arithmetic shift:
0x008B2208).

| # | Address | Condition | Taken / not taken | Test flow |
|---|---|---|---|---|
| B1 | 0x008B223B JP | after `FLD rec[i].f; FCOMP pivot; TEST AH,5` - jumps when C0 and C2 are both clear (rec[i].f >= pivot) or both set (unordered, NaN) | taken: stop left scan; not taken (rec[i].f < pivot): i++ and loop 0x008B2241 | left scan stops on equal, greater, NaN |
| B2 | 0x008B225B JP | after `FLD pivot; FCOMP rec[j].f; TEST AH,5` - jumps when pivot >= rec[j].f or unordered | taken: stop right scan; not taken (pivot < rec[j].f): j-- and loop 0x008B2261 | right scan stops on equal, smaller, NaN |
| B3 | 0x008B2265 JL | j < i | taken: leave partition to 0x008B22C6 without swap and without i++/j-- | scans crossed |
| B4 | 0x008B2267 JZ | j == i | taken: skip swap, still j--, i++ (0x008B22BC) | scans met on one record |
| B5 | 0x008B22C0 JLE | i <= j after i++, j-- | taken: next scan round at 0x008B2220 (pivot not reloaded) | partition continues |
| B6 | 0x008B22C8 JGE | lo >= j | not taken (lo < j): recurse on (records, lo, j, compare) at 0x008B22D1 | left part sorted by recursion |

## Claims

1. 0x008B21F0 calls nothing but itself and references no absolute address, TLS slot or
   global - **read** (meta.json callees/data_refs; asm.s, every operand is register-relative).
2. It does not lock, count or queue on the Havok world - **derived** from claim 1.
3. It sorts records of stride 0x30 ascending by the float at +0x14, pivot = middle record
   `(lo+hi)>>1` - **read** (0x008B2205..0x008B2210, B1, B2, swap 0x008B2269..0x008B22B9).
4. The swap moves only +0x00..+0x0F, +0x10, +0x14 and +0x20; +0x18, +0x1C and +0x24..+0x2F
   stay in place, so they are either padding or not owned per record - **read** for the
   movement, the interpretation is **unverified**.
5. MOVAPS is used only on the swap path (0x008B2277, 0x008B228B, 0x008B2291, 0x008B22B6,
   all inside 0x008B2269..0x008B22B9, reached only when j > i: B3 0x008B2265, B4 0x008B2267)
   - **read**. So the array base must be 16-byte aligned whenever a swap runs; a misaligned
   array that is never swapped (for example already in ascending order with distinct keys)
   does not fault - **derived** from the branch structure and MOVAPS's alignment rule. A
   rebuild may require 16-byte alignment, but as a precondition it chooses, not as an
   invariant the original enforces on every call - **derived**.
6. The key moved from j to i goes through x87 (FLD 0x008B2273 / FSTP 0x008B22A6), the key
   from i to j as an integer (0x008B229A/0x008B229D). A signalling-NaN key would be quieted
   on the j->i path only - **derived** from the instruction forms; never observed.
   Pseudo.c shows both as plain `undefined4` copies; the instructions win.
7. The scans have no bound check (0x008B2230..0x008B2241, 0x008B2250..0x008B2261) - **read**.
   The left scan stops on the first key >= pivot or unordered (B1 0x008B223B), the right
   scan on the first key <= pivot or unordered (B2 0x008B225B); a key equal to the pivot and
   any unordered compare (NaN key or NaN pivot) stop a scan - **read**. The pivot value is
   cached at [ESP+0x24] (0x008B2216) and never reloaded inside the partition loop - **read**.
   What keeps the scans inside [lo,hi] is: in the first round the pivot record itself; after
   a swap, the records just exchanged (rec[i-1] <= pivot bounds the right scan at the old i
   position, rec[j+1] >= pivot bounds the left scan at the old j position, or NaN). The pivot
   record itself may have moved by then - **derived** from B1..B5 and the swap.
8. Only the left part recurses; the right part loops (0x008B22DE..0x008B22E3), so the
   worst-case recursion depth is linear in the count - **derived** from B6/B7. Each level
   costs at least 0x88 bytes of thread stack (0x64 locals + 4 return address + 4 saved EBP
   + 12 for EBX/ESI/EDI + 16 for the 4 arguments) plus 0..12 bytes of alignment from
   `AND ESP,0xFFFFFFF0` at 0x008B21F3 - **derived** from the prologue 0x008B21F0..0x008B21FE
   and the call site 0x008B22CA..0x008B22D1.
9. Argument 3 is never read as a value, only forwarded (0x008B22CA) - **read**. That it is an
   empty comparator object passed by value (a template sort) is **unverified**.
10. Re-entrant: two threads may run it at once on two different arrays - **derived** from
    claim 1. Two threads on the same collector array would race - **derived**.
11. The records are Havok ray-cast hit records (normal at +0x00, shape key at +0x10, hit
    fraction at +0x14, root collidable at +0x20) and 0x008B22F0 is the all-hits collector's
    sort - **unverified**. No RTTI, string or SDK layout is in the export. The consumer in
    0x0088B850 (0x0088B9FE..0x0088BA0E copies record 0's +0x00, +0x10 and +0x14 into
    [ESI+0x30..]) fits the claim but does not prove it. Would settle it: an
    hkpAllRayHitCollector / hkpWorldRayCastOutput layout from Havok SDK headers, or the RTTI
    of the collector's vtable in 0x0088B850.
12. Where the collector array lives (heap, Havok stack area 0x00B47900, or a caller's frame) -
    **unverified**: the function receives only the pointer. Would settle it: the
    0x0088B850 / 0x008B22F0 export, tracing how EBX (the collector) and its +0x10 field are
    set up before 0x0088B9F9.
