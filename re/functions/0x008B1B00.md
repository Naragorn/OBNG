## Purpose

Builds a rotation quaternion from an axis and an angle:
`out.xyz = axis.xyz * sin(angle * 0.5)`, `out.w = cos(angle * 0.5)`, for
|angle*0.5| < 2^63. The result is a unit quaternion only when the caller
passes a unit axis: the function does not normalise (derived: no length
computation in 0x008B1B00..0x008B1B3D). For |angle*0.5| >= 2^63 and for
+-Inf, FSIN/FCOS leave ST0 unchanged with C2 set and the body has no check
of C2, so out = (axis.xyz*h, h) with h = angle*0.5; a NaN angle propagates
(derived from the instruction list, no FNSTSW/branch between 0x008B1B1A and
0x008B1B35; the FSIN/FCOS out-of-range behaviour is the Intel SDM's, not
retrieved in this run - unverified until checked against the SDM or a test).
A pure leaf: no callees, no globals written, no heap. Mark: derived from the
instructions 0x008B1B09..0x008B1B35 and the constant at 0x00A3D65C = 0.5f
(data.json, bytes `00 00 00 3f`).

## Claims

1. `__thiscall`, `RET 0x8`, two stack arguments - read, 0x008B1B3B and the
   [EBP+8]/[EBP+0xC] loads.
2. Out quaternion = (axis.xyz * sin(a/2), cos(a/2)) for |a/2| < 2^63 -
   derived from 0x008B1B09..0x008B1B35 and 0.5f at 0x00A3D65C (data.json).
   For |a/2| >= 2^63 and Inf, out = (axis.xyz*h, h) with h = a/2, NaN
   propagates - derived (no C2 check in the body; FSIN/FCOS out-of-range
   behaviour per the Intel SDM, unverified in this run).
3. sin and cos are both taken by the x87 (`FSIN` 0x008B1B1A, `FCOS`
   0x008B1B26) of the same product `angle*0.5`: `FLD ST0` at 0x008B1B18
   duplicates it - read. The product (`FMUL` 0x008B1B0F) is formed under the
   calling thread's x87 control word; the game runs at 24-bit precision
   control (knowledge/frame-clock.md:197, measured at the first
   TimeInfo::Update under Proton), so it is normally the same product rounded
   at 24-bit PC; per call site unverified. Multiplying a float by 0.5f is
   exact at any precision control except on underflow into denormals -
   derived (0.5 is a power of two). Each FSIN/FCOS result is rounded to float
   on store (0x008B1B1C, 0x008B1B35) - read. Whether the precision control
   also rounds the FSIN/FCOS results in ST0 before those stores (making a
   double rounding at PC 53/64) is unverified: the Intel SDM lists PC as
   affecting only FADD/FSUB/FMUL/FDIV/FSQRT (not retrieved in this run); a
   test that runs FSIN/FCOS under PC 24 and PC 64 and stores ST0 as 80-bit
   settles it. A rebuild with SSE/libm sin/cos would be class C (differs in
   the last bits); x87 FSIN/FCOS gives bit identity per CPU - derived.
   Whether FSIN/FCOS give the same results across CPU vendors is unverified
   (settled by running the value-class tests on an Intel and an AMD machine).
4. Both the output and the axis must be 16-byte aligned, otherwise MOVAPS
   faults - read (0x008B1B15, 0x008B1B32: `MOVAPS` with memory operands).
5. The written lane 3 of the MOVAPS is dead; out.w comes only from FCOS -
   read (store order 0x008B1B32 then 0x008B1B35).
6. Pseudo.c agrees with the instructions on the result; it shows the axis as
   four scalar loads and stores where the binary uses one MOVAPS each and an
   SSE broadcast (`SHUFPS ...,0x0` 0x008B1B2B) - read; the instructions are
   the reference.
7. No shared state written; reentrant and thread-safe for disjoint outputs -
   derived from groups (c)-(e) being empty.
8. Nine callers (0x008F4100, 0x00896000, 0x008B4790, 0x00916400, 0x0094DB40,
   0x0088D900, 0x008B51C0, 0x00958750, 0x008B1EB0) - read, meta.json. Which
   of these is on the controller path the sampler hit is unverified here.

## Concurrency

Could two threads run this at once for two different phantoms? Yes, when
they pass different output objects: the function reads only its arguments
and a read-only constant (0x00A3D65C), writes only the 16 bytes at ECX and
its own stack, calls nothing and allocates nothing (derived from the
read-and-write list). What stands against it: nothing in this function. A
conflict can come only from callers handing the same output object or an
axis that another thread writes at the same time (unverified, caller side).
Each thread's x87 control word is the one the product is formed under
(exact for 0.5f except on denormal underflow, see claim 3); on Windows that
state is per thread (unverified for this process).
