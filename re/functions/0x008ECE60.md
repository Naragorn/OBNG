## Purpose

For every collidable in the phantom's overlap list (+0x120 array, +0x124 count, walked from the last entry to the
first) it asks both shapes for their type (shape vtable +0x08), looks up an agent index in the collision dispatcher's
byte table (+0x190 + ownType*32 + otherType), and calls the dispatcher's function at `+0x994 + index*0x14` with
(own collidable, other collidable, the world's collision input, the caller's collector). After every call it reads
the collector's byte +0x04 and stops the walk when that byte is non-zero. It writes nothing outside its own stack
frame.

It is the third member of a family of three: 0x008ECC60 (+0x30) uses dispatcher slot `+0x99C + index*0x14`
(the linear cast), 0x008ECDD0 (+0x34) uses `+0x998 + index*0x14`, and this function `+0x994 + index*0x14` (read:
0x008ECECB here, 0x008ECE41 in 0x008ECDD0, 0x008ECC60.md C7). All three use the same entry layout: stride 0x14,
consecutive dwords +0x994 / +0x998 / +0x99C, indexed by the +0x190 byte table (read). That they index the same
dispatcher object, and so the same entry, holds for 0x008ECE60 and 0x008ECDD0, both through `[[world+0x74]+0]`
(derived from C4 and 0x008ECDD0's asm); for 0x008ECC60, whose dispatcher comes from `[world+0x7C]`, it holds only if
C8 holds, which is **unverified**. Which agent query slot +0x994 is (Havok's `getPenetrationsFunc` by the order
createFunc / getPenetrations / getClosestPoints / linearCast) is **unverified**: nothing in the export (no strings, no
data refs, no callers, no RTTI) separates +0x994 from getClosestPoints, the slot +0x998 that 0x008ECDD0 uses; the
early-out byte (0x008ECED2) is the only discriminator, and tying it to a bool-early-out pair collector rather than a
point collector comes from Havok memory. Settled by a Havok SDK header, RTTI for the collector vtable 0x00A56370, or
reading one concrete agent function in slot +0x994.

Differences from 0x008ECDD0 (read, both asm.s): this one has the early-out test on collector +0x04
(0x008ECED2-0x008ECEDA), 0x008ECDD0 has none; the collision-input pointer is pushed as the 3rd argument by both.
Differences from 0x008ECC60 (read): no position write, no AABB, no broad-phase call (0x008DE950), no type 0x18
override, and the dispatcher is taken from `[[world+0x74]+0x00]` instead of `[world+0x7C]`.

**Clock:** no clock or time global is read or written by its own instructions (derived: data.json has no data entry
and asm.s has no absolute address). The two vcalls and the dispatcher functions are not covered (unverified).

**Who calls it on the controller's path:** not found. A grep of the rea-all pseudocode of the controller functions
0x00896000, 0x00891780, 0x008902B0, 0x008AE890, 0x008AE100, 0x008AD070 and 0x008AD7D0 for a vcall at +0x38 found
none (derived from that grep; pseudocode only). The one candidate found in rea-all is **0x00895F00** (pseudocode
only, unverified): it takes `[[ECX+8]+0x30]` through the getter 0x008AC0C0 (the proxy's phantom per
re/functions/0x00891780.md and knowledge/actor-frame-map.md), builds a collector on its stack (vtable 0x00A56370,
early-out byte +0x04 = 0, an inline array of 0x10 entries of 16 bytes, count +0x0C, capacity word 0x80000010) and
calls `vt+0x38` with it, then scans the hits' `[entry]+0x1C & 0x3F`. 0x00895F00 is called from 0x005EB150
(pseudocode), not from the controller's update. Two more vcall sites at +0x38 in 0x0088D560 / 0x0088D900 (right
after a +0x30 vcall on the same object) were not identified as phantom calls (unverified). 0x008BA27E and 0x008D9667
call a `+0x38` slot with three arguments (read, havok-thread-conditions exports), so they are not this function
(derived: this one pops 4 bytes).

## Read-and-write map (the manifest's five groups)

- **(a) Own arguments and stack**: reads arg 1 (collector) at 0x008ECEB8; writes its locals at 0x008ECE6C,
  0x008ECE77, 0x008ECE7B, 0x008ECEDC and the saved registers (read).
- **(b) The phantom it works for**: reads +0x08, +0x14, +0x120 (each iteration), +0x124 (once). Writes nothing (read).
- **(c) Other phantoms, bodies, shapes, world, broad phase, pairs, pending queue**: reads world+0x74, the collision
  input +0x00, the dispatcher's table +0x190 and function slots +0x994, every overlapping collidable's +0x00 and its
  shape's type. No write in its own instructions (read). Writes inside the agent functions (to the other
  collidable's owner, to pair caches, to the collector): not followed (unverified). No broad-phase call, no
  world+0x88 counter, no pending-operation queue in its own instructions (read).
- **(d) Globals, singletons, TLS**: none in its own instructions (read: no absolute address, no `FS:` access).
- **(e) Heap and Havok stack area**: none in its own instructions (read: no call besides the three indirect ones).
  Whether the agent functions take scratch from the thread memory at TLS +0x19C or the fallback 0x00BA7D9C: unverified.

## Two threads at once, for two different phantoms

Its own instructions are reentrant: they write only their stack frame and read shared structures (read, C6). What
stands against running two at once:

1. **The overlap lists.** It reads the phantom's +0x120/+0x124 without a lock and keeps the count for the whole walk.
   If another thread moves another phantom through 0x008ECC60 -> 0x008DE950 and the broad phase adds or removes a
   pair involving this phantom (0x008D8370 / 0x008D83E0, proposals in the manifest), this phantom's list can change
   or be reallocated mid-walk: the stale count or the reloaded data pointer can then index past the end or read a
   freed array (derived from C2; that the pair functions write the other phantom's list is unverified).
2. **The agent functions** (not followed): any write to shared state or any non-thread-local scratch in them is
   unknown (unverified).
3. **The collector** is the caller's; two calls with two different collectors share nothing through it (derived from
   C4/C5).

So: safe in its own code only if no thread changes any overlap list while it runs and the agent functions behind
slot +0x994 are reentrant; neither condition has been shown.
