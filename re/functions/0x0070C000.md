## Purpose

Given a camera and a visible array (list of geometries), it draws that array through the
renderer's current accumulator:

1. returns when the renderer global [0x00B3F928] is null or the camera argument is null
   (0x0070C02A, 0x0070C032);
2. takes a counted reference on the renderer's accumulator [renderer+0x08]
   (`InterlockedIncrement(acc+4)` at 0x0070C043) and registers it as an EH-protected
   local (try level 0 at 0x0070C04B);
3. when the accumulator is non-null, calls its vtable +0x4C with the camera
   (0x0070C057-0x0070C05D; proposed StartAccumulating, unverified);
4. calls 0x0070BF30(visibleArray) (0x0070C064), which re-reads the renderer and its
   accumulator and either hands the whole array to the accumulator's vtable +0x54, or -
   with no accumulator - calls every geometry's vtable slot 33 (+0x84) with the renderer
   (objdump 0x0070BF30-0x0070BFF3; see "The callee 0x0070BF30");
5. when the accumulator is non-null, calls its vtable +0x50 with no arguments
   (0x0070C072-0x0070C077; proposed FinishAccumulating, unverified);
6. drops the reference (`InterlockedDecrement` at 0x0070C089) and, when the count
   reaches 0, calls the accumulator's vtable slot 0 with 1 (deleting destructor,
   0x0070C093-0x0070C09B).

It reads no clock and writes no global: the only absolute memory operands are the cookie
0x00B30AAC, the renderer global 0x00B3F928 and the two IAT slots (read: asm.s; meta.json
`data_refs`). It writes no field of any object; every write is to its own stack frame or
to FS:[0] (read: the only memory stores are 0x0070C01D, 0x0070C039, 0x0070C04B,
0x0070C07B, 0x0070C0A1).

  matching the caller's `ADD ESP,4` at 0x0070C069).

- 0x0070BF82 `JE`: accumulator non-null -> `acc->vt+0x54(array)` thiscall
  (0x0070BF84-0x0070BF90), then release.
- accumulator null -> `count = [array+0x04]` (0x0070BF98); 0x0070BF9F `JBE`: count 0 ->
  skip; loop: `geom = [[array+0x00] + i*4]` (0x0070BFA1-0x0070BFA3),
  `geom->vt+0x84(renderer)` thiscall with the renderer pushed (0x0070BFA6-0x0070BFAF),
  `i++`, 0x0070BFB6 `JB` while `i < count` (unsigned). No null check on the elements.
- Release of the accumulator as in 0x0070C000 (0x0070BFC6-0x0070BFDE).
- Only caller: 0x0070C064 (exe scan: one `E8` call, dword not present in the image).

## Calling convention and parameters

cdecl, two stack arguments, plain `RET` (0x0070C0AE); the caller cleans with `ADD ESP,8`
(0x0070C101). ECX on entry is not read: `PUSH ECX` at 0x0070C00E only reserves the local
slot [ESP+0x0C] that 0x0070C039 later fills; no instruction reads ECX before
0x0070C05B overwrites it (read).

Frame after the prologue (7 dwords pushed, read 0x0070C000-0x0070C018):
[ESP+0x00] cookie ^ ESP, +0x04 EDI, +0x08 ESI, +0x0C accumulator local, +0x10 previous
FS:[0] (registration record, installed at 0x0070C019-0x0070C01D), +0x14 handler
0x009BD558, +0x18 try level, +0x1C return address, +0x20 arg1, +0x24 arg2.

Return value: none. EAX on exit holds whatever the last call left (InterlockedDecrement's

Note on the seed: the seed says "(process, camera) pushed". The pushes are `PUSH ESI;
PUSH EBX` (0x0070C0FA-0x0070C0FB), so the first argument is EBX (camera) and the second
ESI, and ESI is the visible array taken from the process's +0x08, not the process itself
(read; derived for the role names from 0x0070BF30's reads).

register ESI, which nothing between them writes (read: ESI is callee-saved across the
three calls by the MSVC convention; the function itself does not write ESI after
0x0070C034), so they form one decision, not sixteen combinations.

## Open questions

1. Is 0x0070C000 reached at all at run time, and from which of the seven hop call sites?
   C11 says not from RenderScene's main pass if OBVR's measurement holds. Cheapest
   settle: a call counter on 0x0070C0FC (the existing probe pattern in OBNG.dll) in the
   prison scenario, or reading where the stack-local culling processes at the C12 sites
   set their +0x08.
2. Which class is the accumulator, and what do its vt+0x50 (FinishAccumulating) and
   vt+0x54 (RegisterObjectArray) do? With an accumulator, the per-geometry draw (slot 33
   or a shader-sorted equivalent) happens inside vt+0x50, not here. Reading the vtable
   of the object [renderer+0x08] points to (RTTI COL in front of it) would name the class
   and give the two bodies.
3. Does any vt+0x4C implementation write renderer+0x08 (C5)? Only matters for a rebuild
   that reads the field once instead of twice.
4. Why the culling process's visible array at +0x08 is null in the main pass (C11) while
   the hop still has this path - a feature used by other passes (water reflections,
   local maps, menus?) is the guess, unverified.
