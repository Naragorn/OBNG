## Purpose

0x004E1580 does **not read any `TimeInfo` field itself**. Its two
references to `g_timeInfo` (0x00B33E90) are `mov ecx,0xB33E90` used as the
`this` of two calls (read):

- 0x004E15CF / 0x004E15D6: `call 0x0047D120` on `g_timeInfo`, near the
  start, before any branch.
- 0x004E18C1 / 0x004E18C6: `call 0x0047D0F0` on `g_timeInfo`, at the single
  common exit, which every path reaches.

So the function brackets its whole body with a `TimeInfo` call pair. Which
fields 0x0047D120 and 0x0047D0F0 touch is not in this export; their bodies
were not exported (unverified). The same pair brackets the body of
0x004949E0 (0x00494A13/0x00494A18 and 0x00494E59/0x00494E5E, read in
`re/export/frame-clock/0x004949E0/asm.s`), a function whose callees are
`MessageBoxA`, `PeekMessageA`, `DispatchMessageA` (that export's meta.json).
Both bracketed bodies block the frame (a modal message loop; a synchronous
model load via `g_modelLoader`), which suggests the pair pauses and resumes
the frame clock so the blocked time is not charged to the next frame's
seconds at +0x0C. That is a hypothesis (unverified) until 0x0047D120 and
0x0047D0F0 are read.

Between the bracket the function (re)builds the 3D of a reference
(`this` is a reference whose base form is at +0x1C and scene node at
+0x3C, derived below) by dispatching on the base form's type byte:

- type 0x23: if `this->vfn[0x168]()` returned nonzero, calls
  `0x00526DB0(baseForm, this)` (thiscall on the base form).
- type 0x24: only if the node at `this+0x3C` exists. Builds the base model
  through `0x0051E240` or `0x0051D460`, then walks a list obtained from
  `baseForm+0xEC` (via 0x006899C0). For each entry it takes the base form's
  model path (`baseForm+0xAC`, vfn 0x14), replaces the file name after the
  last `\` with the entry's string, loads that file through
  `g_modelLoader` (0x00B33A1C) at 0x00439EB0, clones or creates a node from
  it, and attaches it to the reference's node - either through a
  "SkinAttachment" extra/object found by name (0x004E17E4) or the plain
  attach at 0x00479140.
- any other type: returns `baseForm->vfn[0xFC]()`.

Answer to the slice question ("Which field does it read, and what does it
drive?"): it reads no `TimeInfo` field directly; it drives the
`TimeInfo` calls 0x0047D120/0x0047D0F0 around a model (re)load. Which field
those two read or write needs their export.

## Open questions

1. What do 0x0047D120 and 0x0047D0F0 read and write in `TimeInfo` (the
   frozen flag at +0x00, the previous milliseconds at +0x10, the start tick
   at +0x14)? This is the slice's actual question and it cannot be answered
   from this export. Cheapest step: export both functions. Their entries
   lie 0x30 and 0x50 bytes before the TimeInfo update 0x0047D170, so each
   is at most that long if nothing else sits between them (derived from
   the addresses; the gaps are unverified).
2. Are 0x0047D120/0x0047D0F0 a nesting counter or a plain flag? If 0x004E1580
   runs inside 0x004949E0's bracket (or vice versa) a plain flag would
   resume the clock early.
3. Is type 0x23 NPC and 0x24 Creature? Check xOBSE GameForms.h's
   `kFormType_*` enum.
4. What is the caller 0x004E3490 (load of a reference's 3D, a reset, a
   race/body change)? It decides how often this bracket runs per frame.
5. What does `this->vfn[0x168]` return (it gates type 0x23 and is read
   before the clock bracket begins)?
6. What string is at 0x00A30968?
7. What does `this->vfn[0xEC]` return (the float copied three times into
   the local at `[esp+0x24]`, 0x004E175C-0x004E1764)?
