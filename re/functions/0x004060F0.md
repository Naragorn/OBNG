The slice manifest's "known" line is wrong on two points (read):

## Purpose

The game window's WNDPROC (derived: four stack arguments, `RET 0x10`, and
the default path forwards exactly (hwnd, msg, wParam, lParam) to
`DefWindowProcA` through the IAT slot 0x00A28260 at 0x004062E4..0x004062E8).
It handles eight messages and passes everything else to DefWindowProcA.
The clock part: on `WM_ACTIVATE` it flushes and polls input, then calls
`TimeInfo::Unfreeze` 0x0047D0F0 on g_timeInfo 0x00B33E90 when the window
becomes active, and `TimeInfo::Freeze` 0x0047D120 when it becomes
inactive, and records the state in byte +0x02 of the OSGlobals object.
Message identities come from the Windows SDK header
`~/tools/xwin/Windows Kits/10/Include/10.0.26100/um/WinUser.h` (lines
1986..2262, 1994..1996, 2578).

| msg | SDK name | Handling (summary) |
|---|---|---|
| 0x0002 | WM_DESTROY | osGlobals->quitGame = 1, then DefWindowProc |
| 0x0006 | WM_ACTIVATE | input flush + poll, clock Unfreeze/Freeze, active byte; returns 0, never DefWindowProc |
| 0x0014 | WM_ERASEBKGND | returns 1 for the window held in 0x00B34FA8, else DefWindowProc |
| 0x0047 | WM_WINDOWPOSCHANGED | when 0x00B350D8 != 0, 0x00497BF0(pos->x, pos->y), then DefWindowProc |
| 0x0084 | WM_NCHITTEST | DefWindowProc first; only when OSGlobals and its `input` exist, hides (HTCLIENT, byte 0x00B02F99 != 0) or shows (not HTCLIENT, byte == 0) the cursor; returns the hit-test result |
| 0x0086 | WM_NCACTIVATE | when wParam == 0, byte 0x00B333F5 = 1; then DefWindowProc |
| 0x0105 | WM_SYSKEYUP | returns 0 (swallowed) |
| 0x0200 | WM_MOUSEMOVE | osGlobals->0x00405370(LOWORD, HIWORD); returns 0 when its AL != 0 (upper EAX bytes ignored), else DefWindowProc |

## Claims

1. **This is the game window's WNDPROC** (derived: stdcall with four
   arguments, `RET 0x10`; the default path forwards the four arguments
   unchanged to DefWindowProcA, 0x004062E4..0x004062E8; message handling
   by switch on arg1). Which window class registers it is unverified (no
   reference in the export).
2. **The clock bracket is the window's focus bracket** (read, bytes.bin):
   activation (WA_ACTIVE/WA_CLICKACTIVE, not minimized) calls
   `TimeInfo::Unfreeze` on g_timeInfo at 0x0040616E; deactivation
   (WA_INACTIVE) calls `TimeInfo::Freeze` at 0x004061AF. Each is preceded,
   when the input object exists, by `FlushKeyboardBuffer` and
   `PollAndUpdateInputState` on OSGlobals->input.
3. **Order within the bracket** (read, bytes.bin): input flush ->
   input poll -> clock (Unfreeze/Freeze) -> OSGlobals+0x02 written.
4. **[EDI+2] at 0x00406173 is byte +0x02 of the OSGlobals object**
   (read: EDI = `[0x00B33398]` from `MOV EDI,EAX` at 0x00406159), set to
   1 after Unfreeze and to 0 after Freeze at 0x004061B4 - a
   window-is-active flag (derived from the two writes; xOBSE leaves it
   `unk02`). Its readers are not in this export (unverified).
5. **The two halves are not gated alike - this is where an unbalanced
   Unfreeze comes from** (derived from A3/A4 and A7/A8): Unfreeze has no
   pairing state and lacks only the 0x00B333F0 gate; it still needs a
   non-null `[0x00B33398]` (A4, `JE` 0x0040614F) and a non-minimized
   activation (A3). The null-osGlobals case is not an independent cause:
   Freeze bails out on it (A7, `JE` 0x00406187) and so does Unfreeze
   (A4), so it skips both halves alike. Unfreeze runs on a counter this
   function never raised only when the window is activated without a
   Freeze having run on this path before - the window's first activation,
   or a deactivation while `[0x00B333F0]` != 0 (A8) that skipped Freeze. When the counter is 0 then,
   Unfreeze takes its counter-zero flow F1 and writes nothing
   (re/functions/0x0047D0F0.md claim 2). When the counter is nonzero
   because another bracket (GameMessageBoxA 0x004949E0, LoadBaseFormModels
   0x004E1580) is open, the surplus Unfreeze closes that bracket's level
   instead (derived; whether that ever happens is unverified).
6. **The converse imbalance also exists** (derived from A3): a Freeze on
   WA_INACTIVE followed by activation while minimized (HIWORD(wParam) != 0)
   runs no Unfreeze, so the clock stays frozen until a later non-minimized
   activation.
7. **Which of the 32 Unfreeze calls in the 2026-10-27 shadow run was the
   surplus is unverified.** The shadow counted calls over all call sites
   (knowledge/frame-clock.md, "The TimeInfo class verified in the game");
   that the surplus came from 0x0040616E, and from the first activation in
   particular, is a candidate, not a finding. Whether `[0x00B33398]` is
   already set at the window's first WM_ACTIVATE is also unverified (on
   disk it is 0, data.json). What would settle both: a per-call-site count
   of Unfreeze/Freeze in the shadow run (the return address 0x00406173 /
   0x004061B4 identifies this function), or a log of `[0x00B33398]` at the
   window's first WM_ACTIVATE.
8. **WM_ACTIVATE never reaches DefWindowProcA** (read): every path returns
   0 directly, so default activation handling (keyboard focus via
   DefWindowProc) is not done for this window here.
9. **WM_DESTROY sets OSGlobals+0x00** (read, 0x00406200; xOBSE names it
   `quitGame`).
10. **WM_NCHITTEST hides or shows the cursor only under three gates**
    (read, H1..H6): both actions need `[0x00B33398]` != 0 (`JZ` 0x00406249)
    and OSGlobals->input (+0x20) != 0 (`JZ` 0x0040624F). Over HTCLIENT the
    hide loop runs only when byte 0x00B02F99 != 0 (`JZ` 0x0040627E); it is
    a do-while - at least one ShowCursor(FALSE), repeated while the return
    is > 0 (signed `JG` at 0x0040628C) - then the byte is set to 0. Not over
    HTCLIENT, ShowCursor(TRUE) runs once only when the byte == 0 (`JNZ`
    0x0040625D), then the byte is set to 1. Otherwise nothing is called and
    the hit-test result is returned unchanged. 0x00B02F99 tracks the game's
    own show (on-disk 1, data.json).
11. **WM_SYSKEYUP is swallowed** (read, M3: return 0 without
    DefWindowProc).
12. **WM_MOUSEMOVE goes to 0x00405370 as a thiscall on OSGlobals with
    (x, y)** (read, 0x004062B7..0x004062C7); only AL is tested (`TEST AL,AL` at
    0x004062CC): the window procedure returns 0 when AL != 0, else
    DefWindowProcA. The upper bytes of EAX are ignored (read).
13. **0x00405370 is called without a null check on `[0x00B33398]`**
    (read: 0x004062C1 loads ECX directly, no TEST before the call).
14. **pseudo.c and the instructions disagree in three places** (read):
    pseudo.c shows `FUN_00405370(param_4 & 0xffff, param_4 >> 0x10)` with
    no `this`, while the instructions load ECX = `[0x00B33398]` at
    0x004062C1; and it shows FlushKeyboardBuffer/PollAndUpdateInputState
    as argument-less calls, while ECX = OSGlobals->input at 0x00406151 /
    0x00406162 (bytes.bin); and it writes `TimeInfo::Freeze()` /
    `TimeInfo::Unfreeze()` with no `this`, while the instructions pass
    ECX = g_timeInfo 0x00B33E90 (`MOV ECX,0xB33E90` at 0x00406169 and
    0x004061AA, bytes.bin). The instructions win. Otherwise pseudo.c's
    control flow matches the instructions, including the gap cases.
