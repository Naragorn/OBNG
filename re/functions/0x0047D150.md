## Purpose

Initialises a 0x18-byte `TimeInfo` in place: clears the frozen byte, the
three floats and the previous-milliseconds dword, and stores the caller's
start tick at +0x14. It reads no global and calls nothing (read, asm.s
0x0047D150-0x0047D16C).

Answer to the slice question: it writes a zero byte to +0x00, 0.0f to +0x04,
+0x08 and +0x0C, integer 0 to +0x10 and the argument to +0x14. It does not
write +0x01..+0x03. +0x04 (the fixed step, `clampMs` in
`src/engine/time/TimeInfo.h`) is written as 0.0f here, so when an instance
ever runs in fixed-step mode, the nonzero step is written somewhere else; that
writer is not in this slice (unverified where).

## Calling convention and parameters

- `__thiscall`: `this` in ECX, used as the base of every store
  (`[ECX]`, `[ECX+0x4]` ... `[ECX+0x14]`) without being loaded inside the body
  (read, 0x0047D156-0x0047D169). The only caller sets `MOV ECX,EDI` at
  0x005AD30C, EDI being the `FormHeap_Allocate(0x18)` result from 0x005AD2EE
  (read, `re/export/frame-clock/0x005AD0D0/asm.s`).
- One 4-byte stack argument at `[ESP+4]` on entry: `MOV EAX,[ESP+0x4]` at
  0x0047D152 (read). The caller pushes the return value of the import through
  0x00A280D0 (`PTR_GetTickCount_00a280d0`, `CALL EBX` at 0x005AD309 with
  `MOV EBX,[0x00a280d0]` at 0x005AD2F9) at 0x005AD30B, so the argument is a
  `GetTickCount` value (derived from those caller instructions).
- Callee cleans the stack: `RET 0x4` at 0x0047D16C (read); the caller has no
  `ADD ESP` after 0x005AD30E (read, 0x005AD313 is `JMP 0x005ad317`).
- Return: EAX holds the argument (the tick) on return, not `this`, because the
  last write to EAX is 0x0047D152 (read). The caller does not use EAX after
  the call; it keeps the pointer in EDI and stores EDI at `[ESI+0x54]` at
  0x005AD31F (read, caller export). So the function returns nothing a caller
  relies on (derived).
- x87 stack: one push (`FLDZ` 0x0047D150), one pop (`FSTP` 0x0047D166);
  balanced on return (derived from the three FPU instructions).

Proposed signature: `void __thiscall TimeInfo::TimeInfo(TimeInfo* this, std::uint32_t startTick)`.

## Control flow

No branch. One straight-line block 0x0047D150-0x0047D16C ending in `RET 0x4`
(read, asm.s; meta.json `body` is a single range; data.json has no jump
table).

| # | Flow | Condition | Address |
|---|---|---|---|
| F1 | Initialise and return | always (no conditional instruction in the body) | 0x0047D150-0x0047D16C |

Test flows the rebuild needs for F1 (derived from the stores above):

- F1a: tick = 0 -> +0x14 == 0x00000000, the other written fields zero.
- F1b: tick = 0xFFFFFFFF -> +0x14 == 0xFFFFFFFF (stored unchanged, no sign or
  range handling, read: plain `MOV` at 0x0047D169).
- F1c: a block pre-filled with a sentinel (for example 0xCD): after the call
  +0x00 == 0x00, the 32-bit patterns of +0x04, +0x08, +0x0C == 0x00000000,
  +0x10 == 0x00000000, +0x14 == tick, and +0x01..+0x03 still hold the
  sentinel (the original does not write them).
- F1d: compare the floats as 32-bit patterns, not as float values, so that a
  rebuild writing -0.0f (0x80000000) fails.

## Open questions

1. Constructor or init method? Claim 13 points to a constructor in a
   new-expression; claim 11 (EAX is not `this` on return) does not match the
   usual MSVC rule that a constructor returns `this` (unverified compiler
   behaviour; link-time code generation dropping the unused return value
   would explain it, also unverified). The behaviour to rebuild is the same
   either way; only the name depends on it. Cheapest step: look at another
   class's known constructor in this binary (e.g. one named in xOBSE) and see
   whether it returns `this` in EAX.
2. Who writes the fixed step +0x04 (and the frozen byte +0x00) on g_timeInfo
   0x00B33E90 and on the LoadingMenu's instance at `LoadingMenu+0x54`? Neither
   constructor path (here, 0x009DC2A0) does. Needs the xrefs to 0x00B33E94
   and to `[reg+0x4]` stores on a TimeInfo pointer - the freeze bracket
   0x0047D120 / 0x0047D0F0 is the candidate for +0x00 (in progress in this
   slice).
3. Whether `1000 / iFPSClamp` is ever stored to +0x04 stays unverified; this
   function only shows it is 0.0f right after construction.

## Layout requests

For `src/engine/time/TimeInfo.h` (all offsets already present there; this
function confirms them by a second path, claim 10):

- `std::uint8_t frozen` at +0x00, initialised to 0.
- `std::uint8_t pad[3]` at +0x01, never written by the constructor - the
  rebuild must not zero it if it is to match byte for byte (claim 7).
- `float clampMs` at +0x04, `float clampCarryMs` at +0x08, `float frameSeconds`
  at +0x0C, all initialised to +0.0f (pattern 0x00000000).
- `std::uint32_t lastMs` at +0x10, initialised to 0 (integer store).
- `std::uint32_t startTick` at +0x14, initialised to the constructor argument.
- `static_assert`s worth adding: `offsetof(TimeInfo, clampMs) == 0x04`,
  `offsetof(TimeInfo, clampCarryMs) == 0x08`, `offsetof(TimeInfo, lastMs) == 0x10`.
- The header's comment "FormHeap_Allocate at 0x005AD2E7" names the `PUSH 0x18`;
  the call itself is at 0x005AD2E9 (read, caller export) - a precision fix,
  not a correction of the claim.
