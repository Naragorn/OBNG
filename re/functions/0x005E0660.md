## Purpose

Returns a height of the object it is called on: the float at +0x08 of the pointer returned by virtual slot +0x15C,
minus the float at +0x08 of the pointer returned by virtual slot +0x158, times the float returned by virtual slot
+0xEC, rounded to float (read, 0x005E0666-0x005E06AE). Each of the two slots is handed a pointer into this function's
frame; that the returned pointer is that buffer and that the callee writes it is unverified. Its callers use the result as a height above the reference's
position: 0x00632090 and 0x00619B10 take 0.75 of it, 0x005FA0A0 takes 0.25 of it capped at 32, 0x005E06C0 scales it
by a parameter and adds the reference's z (read, re/export/rea-all/functions/0x632090.c line 54, 0x619b10.c line 42,
0x5fa0a0.c lines 70-76, 0x5e06c0.c lines 22-25 - pseudocode). Reading slot +0x15C / +0x158 as bound max / bound min
and slot +0xEC as the reference's scale is unverified (knowledge/fly-camera.md also sees vtable +0xEC used as a
multiplier of a height on the player, 0x006669F0).

**It is not the direct caller of the character controller's update 0x00896000** (derived, see Claims C6-C8): none of
its three slot targets can be 0x00896000 itself. Whether a slot target reaches 0x00896000 through further calls is
unverified (the slot targets are not followed), so the seed name's sampler word 0x005E06A6 is either a stale stack word
or a live ancestor return through the slot +0xEC target - open.

## Control flow

No conditional or computed branch (read: asm.s contains no Jcc/JMP; data.json `jump_tables` is empty). One flow:

1. 0x005E0675: `pA = this->vt[0x15C](&bufA)`; 0x005E0677/0x005E067C: `t = (double)pA->z` stored as double.
2. 0x005E068D: `pB = this->vt[0x158](&bufB)`; 0x005E068F/0x005E0692: `ST0 = t - pB->z` (`FSUBR` = memory minus ST0),
   stored as double at 0x005E06A0.
3. 0x005E06A4: `s = this->vt[0xEC]()`; 0x005E06A6: `ST0 = s * diff`.
4. 0x005E06AB/0x005E06AE: round to float through memory, return in ST0.

Test flows a rebuild would need (derived): the single path with representative values; rounding: two double stores
and one float store, so the result equals `(float)(((double)A.z - B.z) * s)` only when the x87 precision control is
53 or 64 bits - under 24-bit precision every intermediate already rounds to float (derived, x87 semantics; the
precision control at this call is unverified); negative heights (A.z < B.z) and s = 0 pass through unchanged
(no clamp, read: no compare instruction).
