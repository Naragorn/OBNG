OBVR calls this function "the master frame function" (OBVR `HANDOFF.md`
1867-1868: "the wrapper `0x00579260`, which the master frame function calls
at `0x0040D6F7`"). The name proposed here keeps the receiver OBNG already
uses for its caller and says what most of the body does: it runs the
ten-frame state sequence, renders the world live or, on the snapshot path,
runs one of two paths gated by [0x00B333E8] (only one of which passes
[0x00B333E8] to a draw call, claim 12), then the interface pass, then
handles the camera-path capture toggle, then presents.

## Purpose

0x0040D800 calls it with its own `this` at 0x0040DF54 (0x0040DF52-0x0040DF54,
**read**), which 0x0040D800 reaches on every path to its `RET` (**read**, for
the call from 0x0040D800). Four other callers (0x0044E720, 0x00440C40,
0x005BDCD0, 0x004455E0; meta.json, **read**) call it outside the update
step, so it is the frame's render-and-present routine with several callers,
not only the second half of 0x0040D800 (**derived** from the caller list).
Besides rendering, the body handles input (the capture toggle and
0x00411750, item 6) and the ten-frame state sequence (item 3). In this order
(all **read** for the calls; the subsystem names are the sources named in
each line, otherwise **unverified**):

1. 0x00977C50(3) at 0x0040D4EB and 0x007A99A0() at 0x0040D4F3 - unknown
   (unverified); 0x00977C50 is called again with 2 at 0x0040D7E0, so it
   brackets the function (read), what it records is unverified.
2. Optional 0x00497C30() when byte 0x00B34FA4 != 0 (0x0040D500-0x0040D508).
3. A ten-frame counter on [0x00B33418] driven by 0x00572E30(2) on the object
   at [0x00B3A6B0]: on its first frame g_TES->0x00440AF0(0,0,0) and
   0x00674500 on the actor process manager 0x00B3BD00; on its tenth frame
   0x00572EC0(2,0), flag clean-up on [0x00B33B00]+0x18, release of the
   refcounted object at [0x00B333E8] and clearing of `kMenuSnapshotValid`
   0x00B33397 (0x0040D50D-0x0040D5F8).
4. The world: either live through `kRenderScene` 0x0040C830 (OBVR
   `GameAddresses.h:1018`) at 0x0040D658, or, when the menu snapshot is valid
   or one of three gates refuses the live render, and [0x00B333E8] != 0
   (B18, 0x0040D668), one of two paths (0x0040D662-0x0040D6EC, read). Only
   path B (byte 0x00B42F3E != 0) passes [0x00B333E8] to 0x007B4900
   (0x0040D699-0x0040D6A6, read). Path A (0x0040D6B0-0x0040D6EC) never
   references [0x00B333E8]: it calls 0x007D71C0(7,0), renderer
   vtable+0x144(0) under the +0x200/+0x204/+0x20C gates, and
   0x00709C60(renderer) on [0x00B333EC] (read). That either path draws the
   snapshot is **unverified**.
   OBVR `GameAddresses.h:1154-1165` names this exact guard ("0040D5FE cmp
   byte ptr ds:[00B33397h],bl / 0040D604 jne 0040D662 / 0040D658 call
   0040C830").
5. 0x007B8400() at 0x0040D6F1, then the interface pass wrapper 0x00579260(0)
   at 0x0040D6F7 (OBVR `GameAddresses.h:1289`: "The wrapper that owns the
   interface pass, 00579260").
6. The camera-path capture toggle on input (0x0040D6FC-0x0040D7B7): the only
   place in this function that writes `g_timeInfo.fixedStepMs`.
7. 0x007D7210() unless 0x0040FDA0 answers true or renderer+0x200 is 0
   (0x0040D7BD-0x0040D7CE). OBVR `GameAddresses.h:1289-1305` reads
   0x0040FDA0 as "the loading thread is still running".
8. 0x00411100 on the world scene graph [0x00B333CC] (OBVR
   `kWorldSceneGraphPointer`, `GameAddresses.h:1056`) at 0x0040D7D9.
9. 0x00977C50(2), the security cookie check, `RET`.

The clock: this function does not read g_timeInfo at all (no reference to
0x00B33E90..0x00B33EA7 other than 0x00B33E94 among data.json's 30 data addresses,
**read**); it writes only `fixedStepMs` (+0x04), and only inside the
capture toggle.

- When the counter of B2-B4 reaches 10 with B6 not taken, the path clears
  0x00B33397 and jumps to 0x0040D606 directly, which is where B11 would
  go with the byte zero; the effect is the same as taking B11's fall-through
  (derived: 0x0040D5D6 `MOV [0x00B33397],BL` then `JMP 0x0040D606`).
- While 0x00572E30(2) keeps answering true, the counter keeps growing past
  10 and no action is taken for values other than 1 and 10 (derived: B3
  and B4 are the only tests of the counter).
- In a frame where QueryControlState(0x1F, 1) returns 0 (B25), nothing in
  this function writes fixedStepMs (derived: the three stores are all
  after 0x0040D70D and before 0x0040D7BD).

Pseudo.c and the instructions agree on the branch structure. One difference
in presentation: pseudo.c writes `_DAT_00b33e94 = (float)DAT_00b02d48;
... _DAT_00b33e94 = (float)_kMillisecondsPerSecond / _DAT_00b33e94`, which
reads like an intermediate float store and a float division. The

and store once (`FSTP float` 0x0040D7A3); there is no intermediate store
and no float-typed 1000. The instructions win.

## Claims

1. **The three fixedStepMs writes** (read): 0x0040D7A3 stores
   1000.0 / N with N = the dword at 0x00B02D48 read as unsigned; 0x0040D7AD
   stores 0.0f when N == 0; 0x0040D7B7 stores 0.0f when the capture flag
   0x00B333B9 was just toggled off.
2. **All three happen only on a toggle of the capture flag** (read): when
   QueryControlState(0x1F, 1) on this+0x20 is nonzero, and either
   QueryKeyboardKeyState(0x9D, 0) is nonzero or the flag is already set.
   The flag becomes `old == 0` (`SETZ` at 0x0040D73E). Turning it on (B28
   not taken) writes 1000/N or 0; turning it off writes 0.
3. **Turning the capture on also** (read, 0x0040D74A-0x0040D77C): increments
   [0x00B02D58], zeroes [0x00B333C8], formats `"%s%03d"` (0x00A30060) with
   the string at [0x00B02D50] and the new counter into a 260-byte local
   buffer, and calls `CreateDirectoryA(buffer, NULL)`. With the image's
   initial values, the first directory is "TestCameraPath001" (derived from
   data.json: [0x00B02D50] = 0x00A3150C -> "TestCameraPath", [0x00B02D58] = 0
   before the increment; the runtime values are unverified).
4. **With the image's initial value N = 60, site 1 stores 1000/60 ms**
   (derived: data.json 0x00B02D48 bytes `3c 00 00 00`). As a float this is
   16.666666f, bits 0x41855555 (derived; the rounding under the game's
   measured 24-bit x87 precision control, knowledge/frame-clock.md, rounds
   the quotient to 24 bits before the float store, which gives the same
   bits - derived, not run). Whether N is still 60 at runtime (an INI value
   could replace it) is unverified.
5. **N is not the global the other writer reads** (read): 0x00406360 reads
   [0x00B02D10] at 0x004068FA before its own store at 0x0040692B
   (re/export/clock-callers/0x00406360/asm.s lines 413-427), this function
   reads [0x00B02D48]. Whether either one is iFPSClamp: unverified here.
6. **N looks like a setting of the camera-path group** (derived from
   data.json bytes, layout unverified): the bytes from 0x00B02D48 read as
   (value, name pointer) pairs: (60, 0x00A314FC), (0x00A3150C
   "TestCameraPath", 0x00A3151C), (0, 0x00A31538), (0, 0x00A3154C), and the
   bytes at 0x00A3151C begin "sDirectoryName:C" (data.json, entry
   0x00A3150C, bytes 16-31). This matches the SettingInfo layout OBNG
   already uses for fGlobalTimeMultiplier (value at +0x00, name pointer at
   +0x04; `src/engine/time/TimeInfo.h:39`). Under that reading 0x00B02D50 is
   the setting "sDirectoryName:C..." with the value "TestCameraPath" and
   0x00B02D58 is the next setting, an int incremented here. The name of N

9. **0x0040D6F7 is not a call of 0x0040D800** (read): 0x0040D6F7 is
