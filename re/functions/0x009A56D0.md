## Calling convention and parameters

`__thiscall`, eleven stack arguments, callee cleans: `RET 0x2C` at 0x009A6051
and 0x009A60FA (read). ECX = `this` (the `NiD3DSCM_Vertex` map), copied to EDX
at 0x009A56EB and used from EDX for `[this+0x2C]` in cases 0-7 (read).
Frame: `PUSH EBP; MOV EBP,ESP; AND ESP,0xFFFFFFF0; SUB ESP,0x174`, then EBX,
ESI, EDI saved (0x009A56D0..0x009A56EA, read). EBX holds the id `[a2+0x10]`
for the whole body (0x009A56E0; every id test is `CMP EBX,imm`, read). The
status word lives at [ESP+0x1C], zeroed at 0x009A56ED.

**Ghidra disagrees**: pseudo.c shows eight stack parameters after `this`.
The instructions win: `RET 0x2C` pops 44 bytes = 11 arguments, and the caller
pushes 11 (0x009A8FE3..0x009A9005, read). Arguments 9..11 ([EBP+0x28],
[EBP+0x2C], [EBP+0x30]) are never read in this body (read: no operand uses
them), which is why Ghidra dropped them.

The caller's mapping (read, 0x009A8FDF..0x009A9008, with the caller's
ESP = ESP0-0x18 in its loop): EDI = caller arg10 (loaded 0x009A8E6C), EBX =
caller arg9 (0x009A8E67), then caller args 8, 7, ..., 2 from the stack, EAX =
the entry, EBP = caller arg1 (0x009A8E34): 11 pushes. So callee a1 = caller
arg1, a2 = the entry, a3..a11 = caller args 2..10; caller arg11 is not passed
(0x009A8E30 itself ends in `RET 0x2C` at 0x009A903A, read).

Returns (EAX): 0 on success and for every "nothing to do" path;
0x80000050 when the upload slot returned AL = 0 (0x009A60E8); 0x80000010
when the `NDL_UpdateTime` lookup failed (0x009A5F63, but see C9) or the time
sub-switch is out of range (0x009A6046, unreachable - C10). The caller clears
its result byte on any non-zero return (0x009A900A..0x009A900E, read) and
continues with the next entry; the meaning of the two codes beyond that is
unverified.

  pointer (+0x0C) = 0x00B329A0, whose name at 0x00B329A8 is

  0x00AB297C) has its own 0x009A3310 there. The class rests on this one RTTI

  0x009A8E30 (slot +0x40 of all three map vtables). Before the loop it stores

  geometry's `__NDL_SCMData` extra data (string pointer 0x00B29F84 loaded at
  0x009A8E42, call at 0x009A8E4D). It returns at once when the count word
  [map+0x16] is 0 (0x009A8E58/0x009A8E60). It then walks the entry array
  [map+0x10] from index 0 (0x009A8E70/0x009A8E73), per entry:
  null entry -> next entry (0x009A8E76/0x009A8E78 -> 0x009A9013);
  byte [entry+0x08] == 0 -> **the loop ends** (0x009A8E7E/0x009A8E82 ->
  0x009A902A, the `POP EDI; POP EBX` epilogue after the back edge

  [entry+0x24] == 0 -> next entry (0x009A8E8B..0x009A8E98 -> 0x009A9013);

  slot +0x54 = this function (0x009A8EA1..0x009A8EB4, call 0x009A9008). A
  non-zero return clears the caller's result byte (0x009A900A..0x009A900E)
  and the loop continues. Whether other code calls slot +0x54 of a constant
  map virtually is not excluded by the byte search (Q9).

- Q5: Are ids 41-44 meant to read map slot +0x04 (C12)?

- Q7: The meaning of the status codes 0x80000010 and 0x80000050 and of the
