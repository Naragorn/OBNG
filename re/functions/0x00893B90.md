## Purpose

Called once per character-proxy solve, before the simplex solver, with the
contact manifold (0x30-byte points) and the solver input (0x40-byte planes).
In this order (read, addresses in Control flow):

1. **Reset per-solve controller state** (0x00893BD0-0x00893C2B): `L+0x50` and
   `L+0x54` = FLT_MIN (0x00A96588 = 0x00800000), flag bit 2 of `L+0x04`
   cleared, `L+0x1C4` = 0, `L+0x1C8` = 0 when flag bit 16 is set,
   `L+0x40` = `L+0xC0` (16 bytes).
2. **Capsule end points** (0x00893C3D-0x00893E23), when `L+0x17C` != 1, flag
   bit 1 is clear and the controller has a proxy, a phantom and a shape at
   `[[L+0x184]+8]` of type 0x0C with vt+0x1C == 3 whose children 1 and 2 are
   type 8: two points `phantom transform (phantom+0x70) * (child.vertex(+0x10)
   + (0,0,child.radius(+0x0C)))` via 0x0088FCC0, a threshold `radius * 0.333`
   (0x00A74D10 double 0.333000004), and two debug crosses (0x008A7930 on
   `[0x00BA7DA0]`, size 4.0, colours 0xFF0000FF and 0xFF008000).
3. **Per plane i in [0, n)**, n = `[arg2+0x4C]` read once (0x00893E2C); the
   manifold point is `[arg1] + i*0x30`, the plane `[arg2+0x48] + i*0x40`:
   - classify the contact by the root collidable B (`point+0x28`): its owner
     entity when its broad-phase type byte +0x18 == 1, and its collision layer
     `[coll+0x1C] & 0x3F`;
   - **picked body** (0x00893EB9-0x008942F1): when the contact has an entity,
     normal z > 0.985, entity `[+0x50]` vt+0x08 == 6, `[0x00BA7A5C]` == 0 and
     the contact lies at or below the controller's position z + `L+0x58`: copy
     the controller phantom's overlap list (`[[L+0x174]+8]+0x120`, count
     +0x124) into a thread-memory scratch array, set `[0x00BA7A58]` =
     -1.0E13, ray-cast every overlapping collidable whose owner's
     `[+0x50]` vt+0x08 == 6 along a vertical segment from contact + 36 to
     contact - 18 (z), filter the hit by its material/layer, and keep the
     highest hit: `[0x00BA7A58]` = hit z, `[0x00BA7A5C]` = the hit
     collidable's owner (0x0047DE00); then free the scratch array;
   - **per-layer handling of the plane** by two jump tables (entities: layers
     2-10; no entity: layers 12-20): zero the plane's velocity (+0x10), set
     +0x28 to 0.577, zero +0x2C, or flatten the plane (z = 0) and renormalise;
   - **slope test** against `L+0x20`: a steep plane either gets a flattened
     copy appended to the solver input (0x008945C1-0x00894653, at most 4 per
     call), or sets flags 0x404, pushes the plane up (z = 1) and adds 1.0 to
     +0x18; a walkable plane sets flag 0x400, may call 0x0088FF20 and sets
     +0x28 to 5.77;
   - **support bookkeeping** (0x008947C3-0x0089481B): flag 0x200,
     `L+0x1C4`++, 0x00891850 with the manifold point, the plane summed into
     `L+0x40`, `L+0x1C8` = entity +0x0C when flag bit 16 is set.
4. **Finish** (0x00894834-0x008948D4): byte `L+0x60` = (`L+0x1C4` == number
   of steep planes that were appended and kept supporting); `L+0x40`
   normalised when `L+0x1C4` != 0 and its squared length is > 0.

It reads and writes no clock: no RDTSC, no time global in the body (read, the
whole asm.s). The step time reaches it only through the caller's solver input
(+0x40, not read here).

## Read and write list by group

**(a) Own arguments and stack.** Locals only on its stack frame (0x1A8 bytes,
16-aligned). The scratch array header and the dead local object at ESP+0x164
(read). The plane array of arg2 is written in place (velocity, +0x08, +0x18,
+0x28, +0x2C, the plane itself) and appended to: new plane at
`[arg2+0x48] + [arg2+0x4C]*0x40` filled by 0x008909D0 (copy of 13 dwords,
pseudocode) then +0x10 (0x008945E9), +0x08 (0x008945ED), +0x00 (0x00894642),
count `[arg2+0x4C]`++ at 0x00894645 (read). No capacity check precedes the
append (read: no access to a capacity field of arg2 in asm.s). Per
0x008AD7D0.md (in progress) the plane array lies on the calling thread's Havok
stack with capacity user planes + manifold size + 10.

**(b) The controller it works for.** Writes: L+0x04 (0x00893BE1, 0x0089445E,
0x008944AC, 0x0089466A, 0x008947A9, 0x008947C3), L+0x28 (0x00894167), L+0x40
(0x00893BEF, 0x00893C2B, 0x00894804, 0x008948D4), L+0x50 (0x00893BE5), L+0x54

## Could two threads run this at once for two different phantoms?

It cannot safely run concurrently as it stands (derived from the points
below); concurrent runs are racy, not impossible. The one blocker read from
this body is point 1, and it applies when both calls reach the pick block
(0x00893F4A-0x008942F1, entered only when `[0x00BA7A5C]` == 0 and the pick
gates 14-18 pass). Point 2 applies only on threads whose TLS +0x19C is null;
point 3 is a read-under-concurrent-write hazard, not a write in this body.

1. **0x00BA7A5C / 0x00BA7A58 are one global result channel for all
   controllers** (read, the byte scan above). The read-test-write sequence -
   test (0x00893EDF), reset (0x0089407C), compare (0x0089420A) and store
   (0x00894219, 0x00894270) - has no lock (read). With two controllers in
   the pick block at once, one thread's non-zero pick
   makes the other skip its own pick (0x00893EE6), a reset at 0x0089407C can
   overwrite the other's best height, and 0x00896000's read at
   0x00896C0C-0x00896CA6 can apply another controller's body and height to its
   phantom (derived from the instructions listed). Fix at the root: make the
   pick a per-controller field (or a per-thread slot passed to 0x00896000).
2. **The fallback allocator [0x00BA7D9C]** is shared only on threads whose
   TLS +0x19C is null (read: 0x00893FBC, 0x008942C0 select it only then);
   0x008A7560/0x008A75D0 mutate the allocator's free lists (pseudocode,
   unverified). A thread whose TLS +0x19C holds its own thread memory does not
   touch it (see slice havok-thread-conditions).
3. **Reads of shared world state**: the controller phantom's overlap list is
   only read here (0x00893F90, 0x00893FD2, 0x00893FE2; read), as are other
   collidables' transforms and shapes and their ray casts. A race on the
   overlap list needs a concurrent writer elsewhere, such as the broad
   phase's pair add/remove (0x008D8370 / 0x008D83E0, in progress); that such
   a writer can run during this phase is not shown in this export -
   **unverified** until 0x008D8370 / 0x008D83E0 are mapped. The ray cast
   vt+0x14 is not followed, so whether it writes caches is **unverified**.
4. **Debug display [0x00BA7DA0]**: 0x008A7930 -> 0x008A78E0 under its own
   critical section (re/functions/0x00896000.md, pseudocode, in progress).
5. **Unfollowed callees** 0x00891CC0, 0x0088FF20, 0x00891850, the vt+0x14 ray
   cast, bhk vt+0x9C and 0x008AFBE0 -> 0x00560920 (global map 0x00BA7F9C):
   their writes are unverified.

Everything else in the body writes only the calling controller (L), the
caller's solver input on the calling thread's stack, its own stack and its
scratch buffer (read).
