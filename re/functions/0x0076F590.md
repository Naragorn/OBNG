## Purpose

Packs one entry of a vertex declaration for one geometry (or one skin
partition of it) into a locked vertex buffer. It takes the entry's
destination type (entry+0x0C), finds that type's routine row in the global
routine table at [0x00B42700], picks the source array and the source format
from the entry's selector (entry+0x08) - position, normals, colours, one of
eight texture-coordinate sets, the two arrays behind the normals, the
partition's blend weights or blend indices, or an extra-data stream - builds
a 0x28-byte descriptor on its stack at L and calls the chosen routine with
it once. It returns the routine's EAX (for 0x0076E610 the byte total) or 0
when anything is missing (**derived** from the Control flow below).

Subsystems touched, in order (**read** unless marked):
1. The size table 0x00B42708 indexed by the destination type (0x0076F5BE).
2. The routine table: `[[0x00B42700]+4]` indexed by the destination type
   gives a row (0x0076F5C5-0x0076F5D3).
3. The geometry data (arg2): +0x1C / +0x20 / +0x24 / +0x34, +0x08 (word),
   and through 0x007282F0 its texture sets.
4. The partition (arg4): +0x08, +0x0C, +0x10, +0x24 (word).
5. One extra-data lookup 0x00726320 for negative selectors.
6. One indirect call of the routine (0x0076F881).

It reads no clock and no other global: the only data references are the
five in meta.json (**read**). Neither the frame clock nor game time is read
or written here (**derived** from meta.json data_refs; the indirect routine
is not covered by this statement - for 0x0076E610 it holds, see its file).

## Claims

1. stdcall, seven arguments, `RET 0x1C` at all four exits; ECX is not an
   input (**read**, 0x0076F5E1, 0x0076F610, 0x0076F88D, 0x0076F896;
   0x0076F598).
2. The descriptor is built at L and passed by address as the routine's only
   argument; the caller cleans it (`ADD ESP,4` at 0x0076F883), so the routine
   is cdecl with one argument (**read**, 0x0076F87C-0x0076F883). This matches
   0x0076E610's own reading (its file, Claim 1) (**derived**).
3. The offsets and store widths of all ten descriptor fields (type code
   +0x00, +0x04, count +0x08, indices +0x0C, source +0x10, elementBytes
   +0x14, sourceStride +0x18, countedBytes +0x1C, destStride +0x20, dest
   +0x24) are confirmed at instruction level (**read**, Struct accesses,
   descriptor table). OBVR's model of +0x00..+0x07 is not: the writer stores
   +0x00 and +0x04 as dwords (`MOV [ESP+0x10],EAX` 0x0076F86E, `MOV
   [ESP+0x14],EDX` 0x0076F872), while OBVR's `StreamCopyLogic.h:33-36`
   models each as a UInt16 plus a separate UInt16 (word1 at +0x02, pad6 at
   +0x06) (**read**, both files). OBVR's meaning for +0x04 (sourceWords)
   does not hold: the field is the routine-table column (Claim 6); the
   reader 0x0076E610 reads only its low word (its file, Claim 8) (**read**).
   **Finding for OBVR:** +0x02 and +0x06 are the high halves of dwords
   written here, and on the unset paths (Claim 16) +0x06 carries the high
   half of destStride (**derived** from 0x0076F872 and Claim 16).
4. **The null-source gate.** The routine is called only when desc.source is
   non-zero: B18 at 0x0076F876 tests `[ESP+0x20]` = L+0x10 after every write
   to it (**read**). So from this caller 0x0076E610's zero-fill path (taken
   only on a null source, its file Claim 4) never runs (**derived** from B18
   and that claim). This was the open question of the stream-copy mapping;
   it is now instruction-checked for this caller. Other callers of the
   routine table were not checked (Open question 1).
5. Two further gates come first: no row for destType (B2) and no routine for
   (destType, column) (B14). destType 0x11 exits before any table read (B1)
   (**read**). Every gate returns 0 and calls nothing (**read**, the exits
   0x0076F5DA, 0x0076F607, 0x0076F890).
6. The routine row is `[[0x00B42700]+4][destType]` and the routine is
   `[row+8][column]` (**read**, 0x0076F5C5-0x0076F5D3, 0x0076F834-0x0076F83B).
   So the descriptor's +0x04 value is the routine-table **column**, written
   from the same local that indexes the row (EDX at 0x0076F837, stored at
   0x0076F872) (**read**).

    nothing to 0x00B4274C (type 0x11) (**unverified**: Ghidra pseudocode,
    `re/export/rea-all/functions/0x76f9b0.c`, instructions not checked).
    With those values countedBytes = elementBytes exactly when the source
    width equals the destination width, e.g. position (12) to FLOAT3 (12);
    it differs on conversions, e.g. colours (elementBytes 16) to D3DCOLOR
    (countedBytes 4), blend weights with 4 bones (elementBytes 12) to FLOAT4
    (countedBytes 16), blend indices (1..4) to UBYTE4 (4) (**derived** from
    the selector table and those unverified values).
11. For 0x0076E610 every hard-coded case gives countedBytes ==
    elementBytes (**unverified**). The selector-side inputs are **read**:
    float sources with column n have elementBytes 4n (12/12/16/8/12 for
    columns 3/3/4/2/3 in the selector table, weights with 1..3 bones), and
    weights with 4 bones have elementBytes 12 with column 3 (0x0076F6BF,
    0x0076F6CF). The conclusion also needs two premises that come only from
    pseudocode: that 0x00771300 maps (destType n, column n+1) to 0x0076E610
    (so the 4-bone case reaches it only with destType 2), and that
    0x00B42708 holds 4n for the FLOAT types (Claim 10). Given those premises
    the logic is sound; an instruction check of the stores in 0x0076F9B0 and
    of the selection in 0x00771300 would settle it. Extra-data streams
    (selector < -1) take elementBytes from a record, so equality there is
    **unverified** as well.
12. **sourceWords is not always elementBytes/4.** The descriptor +0x04 is the
    source format column (Claim 6). For float columns 1..4 it equals
    elementBytes/4 in every hard-coded case (selector table: 3/12, 4/16,
    2/8, weights 1/4, 2/8, 3/12, 3/12) (**read**), and trivially on the
    extra-data failure path (column 0, elementBytes 0, see below). For blend indices it is
    0x18 + elementBytes (0x19..0x1C with 1..4 bytes) (**read**,
    0x0076F709-0x0076F76F). On the extra-data failure path it is 0 with
    elementBytes 0 (**read**, 0x0076F822-0x0076F830). On the unset paths
    (Claim 16) it is arg6. So "sourceWords" is a misnomer; the field is the
    source format code, and 0x0076E610 uses it as the per-index word step on
    its indexed path (its file, Claim 7) - which is right for float columns
    only (**derived**).
13. Column meaning (**derived** from Claim 6 and the selector tables, plus
    the decompiled 0x00771300, which is **unverified**): columns 1..4 are
    float sources with 1..4 components (0x00771300 picks 0x0076E610 when
    column - 1 == destType for destTypes 0..3, 0x0076E430 when smaller,
    0x0076E4B0 when larger); columns 0x19..0x1C are 1..4 unsigned-byte
    components (this function: elementBytes 1..4); the groups 5..8, 9..0xC,
    0xD..0x10, 0x11..0x14, 0x15..0x18, 0x1D..0x20 exist in the table but no
    hard-coded case here selects them - only the extra-data path can.
14. Indices are set only when a partition is present and the selector is
    neither 1 nor 2 (**read**, B15-B17, 0x0076F85F). So for a skin
    partition the descriptor of every geometry stream carries the vertex map
    (partition+0x0C), while the partition's own weights and indices get a
    null indices field (**derived** from B15-B17). 0x0076E610 takes its
    indexed path when indices != 0 (its file); whether the other column
    routines honour the field is **unverified** (not read). The selector is re-read from
    entry+0x08 at 0x0076F852, not taken from EDX (**read**).
15. The count field is written as a word (0x0076F5A5); bytes L+0x0A..0x0B
    keep whatever was on the stack (**read**). 0x0076E610 reads only the word
    (its file, Claim 8), so this is harmless there (**derived**); other
    routines are **unverified**.
16. **Unset paths.** When the selector is >= 15 (B12), or 1/2 with
    bonesPerVertex 0 or >= 5 (B6, B10), elementBytes (L+0x14) and
    sourceStride (L+0x18) are never written in this call, and the column is
    the arg6 slot's original value, destStride; with selector >= 15 the
    source (L+0x10) is not written either (**read**: the only writes to
    those locals are listed in Struct accesses, none on these paths). The
    routine is then picked by `column = destStride` and, if non-null, called
    with stack garbage in those fields when the gate passes (**derived**).
    Whether these selectors or bone counts reach here in the game is
    **unverified**; the caller 0x0076FE20 lets unlisted selectors reach the
    call through its switch default (pseudocode, **unverified**).
17. Selectors 5..12: source = 0x007282F0(this = data, set = selector - 5),
    called as thiscall (ECX = arg2 at 0x0076F79D) with one pushed word
    zero-extended (0x0076F795-0x0076F79C) (**read**). pseudo.c omits the
    `this` argument (pseudo/instructions disagree; the instructions win).
    The decompiled 0x007282F0 returns 0 when the set is not present, which
    then exits through B18 (**unverified** for the callee; **derived** for
    the gate).
18. Selectors < -1: 0x00726320 is called with ECX = data+0x34 (loaded at
    0x0076F5EB, live to 0x0076F80F) and seven pushed arguments: (selector &
    0x7FFFFFFF, &arg7slot, &column, &arg1slot, &arg5slot, &elementBytes,
    &sourceStride) (**read**, 0x0076F7EA-0x0076F80E). It cleans its own
    seven arguments: the code after the call addresses the same locals at
    the same ESP-relative offsets as the paths that never call it
    (0x0076F818 `[ESP+0x54]` = L+0x44, 0x0076F834 onwards) (**derived**).
    pseudo.c omits `this` here too (pseudo/instructions disagree).
19. On success (AL != 0) only the source is read back (from the arg7 slot,
    0x0076F818); column, elementBytes and sourceStride were written in
    place; the outputs into the arg1 and arg5 slots are never read again,
    because count was copied before (0x0076F5A5) and arg5 lives in EBX
    (**read** by absence of later loads from L+0x2C and L+0x3C; **derived**).
    On failure all four are zeroed (0x0076F822-0x0076F830) and the call is
    then skipped by B18 (**derived**).
20. **Cost shape per call:** at most one helper call (0x007282F0 or
    0x00726320, never both) and at most one routine call; no loop in this
    function (**read**: the only backward branches go to the exit 0x0076F607
    (0x0076F647, 0x0076F6E1, 0x0076F6EC, 0x0076F840, 0x0076F876) or to the
    shared tail 0x0076F7C4 (0x0076F7E4), and neither leads back to a
    branch source). The per-vertex work is
    entirely in the routine, which receives count = arg1 (**derived**).
21. **Cost shape per geometry:** the caller 0x0076FE20 calls this function
    once per declaration entry that its flag filter (its argument 4 bits
    1/2/4/8 against selector groups) lets through, in a loop over the
    declaration's entries (0x1C bytes each) (**unverified**, pseudocode of
    0x76fe20.c). So the routine calls per geometry (or per partition) are at
    most the number of declaration entries, and each copies `count`
    vertices; for a skin partition every geometry-stream descriptor carries
    the vertex map, and where the routine is 0x0076E610 it takes its indexed
    path (one memcpy per vertex, its file) (Claim 14, **derived**). The
    per-entry loop and filter are **unverified**: they rest only on the
    pseudocode of 0x76fe20. The call at 0x0077006D cited in
    `re/functions/0x00763130.md` C15 is consistent with a single call site
    but does not show the loop; reading the caller's loop at instruction
    level would settle it.
22. The function reads no clock and writes no global; its only stores are
    to its own frame and its argument slots (**read**: every store operand
    in asm.s is ESP-based).
23. pseudo.c otherwise agrees with the instructions: the case structure,
    the fall-through of bonesPerVertex 4 into the default source load
    (0x0076F6BF -> 0x0076F6D3), the gate order (routine null before source
    null) and arg3 unused (**read**, compared case by case).

## Open questions

1. Does any other user of the routine table (besides this function) pass a
   null source? Only that could reach 0x0076E610's zero-fill path. Settled by
   listing the readers of `[[0x00B42700]+4]` (0x00770150 reads 0x00B42708;
   0x0076F900 frees the table) and checking each call site.
2. The values of 0x00B42708 rest on pseudocode of 0x0076F9B0; instruction
   check of its stores (and of the D3DDECLTYPE size claim) settles Claims
   10-11.
3. Can the unset paths (Claim 16) occur: selectors >= 15, or partitions
   with bonesPerVertex 0 or > 4? A run-time probe on the selector and
   partition+0x24 at 0x0076F5E4 would settle it.
4. The extra-data record (0x00726320, 0x1C-byte records at [this+0x14],
   column from record+4, elementBytes +8, sourceStride +0x10, source from a
   block table at [this+0x20]) is pseudocode only; whether column ever lands
   in the unsupported table groups is open.
5. The meaning of the two arrays after the normals (selectors 13 and 14 at
   data+0x20 + count*24 / + count*12) - tangents and binormals by Gamebryo
   naming - is unverified.
6. arg3 is unused here; what the caller passes there (its param_2, possibly
   the skin instance) is open.

Callees worth their own slice: the table fill 0x0076F9B0 with 0x00771300
(fixes the routine per (destType, column) and the size table), the
extra-data lookup 0x00726320, the texture-set getter 0x007282F0 (small), the
sibling routines 0x0076E430 / 0x0076E4B0 (float expand/truncate) and the
byte-index routines in column group 0x19..0x1C (e.g. 0x0076F3B0 for
D3DCOLOR, 0x00770860, 0x00770FA0). The caller 0x0076FE20 (the per-entry
loop and the flag filter) is the place to measure per-geometry counts.
