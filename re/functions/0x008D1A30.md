## Identity

## Purpose

A pure leaf math routine. Given segment A = (start `A`, direction `dA`) and
segment B = (start `B`, direction `dB`), it finds the parameters `t` (on A) and
`u` (on B), each clamped to [0, 1], of the closest pair of points, writes the
point on A, the difference vector (point on A minus point on B) and its squared
length into a result record, and returns a bit mask that says which parameter
was clamped to which end. It has no callees, touches no global state other than
three read-only float constants, and allocates nothing. (read, whole body
0x008D1A30-0x008D1CC1; meta.json `callees: []`.)

Callers (meta.json): 0x008FA750, 0x0093C690, 0x0093C350, 0x0093BA20,
0x008D0CA0, 0x008D0A10, 0x0093B7D0, 0x0093B220. 0x0093C690 is the convex
feature walk named in knowledge/render-thread-outside-the-pass.md line 126
(that name is itself inferred).

Stack locals (relative to ESP after the two pushes): +0x14 d12 = dot3(dA,dB),
+0x2c r1 = dot3(dA, B-A) (later reused for t), +0x28 r2 = dot3(dB, B-A),
+0x1c a = dot3(dA,dA), +0x18 e = dot3(dB,dB), +0x24 e*a, +0x20 d12*d12,
+0x0c denom = |e*a - d12^2| (later reused for u), +0x10 tNum = e*r1 - r2*d12
(later reused for the recomputed t). (read, stores at 0x008D1A76, 0x008D1AEA,
0x008D1AB6, 0x008D1B0A, 0x008D1AFE, 0x008D1B12, 0x008D1B1E, 0x008D1B2C, 0x008D1B42)

Note on dot3: each dot product is formed as (x + y) + z in SSE single
precision (SHUFPS 0x55, ADDSS, SHUFPS 0xAA, ADDSS; e.g. 0x008D1A5C-0x008D1A6E).
pseudo.c prints it as z + y + x, which is a different summation order; the
instructions win. Products e*a, d12^2, tNum and the comparisons run on x87
(0x008D1B02-0x008D1C45) with each intermediate rounded to float by FSTP/FST to
memory except the chains held on the x87 stack (e.g. 0x008D1B30-0x008D1B52 keeps
e*r1, r2*d12 and tNum*denom at x87 precision). A rebuild that must be
bit-identical has to keep these precisions. (read; consequence derived)

## Control flow

x87 condition flags: C0 = 0x01, C2 = 0x04, C3 = 0x40 in AH. Each test below is
read from the instruction; the condition is derived from the FCOM flag table.

| # | Address | Condition (taken) | Effect |
|---|---------|-------------------|--------|
| B1 | 0x008D1B59 JNP 0x008D1B9E | denom^2 <= tNum*denom (C0 xor C3 set); not taken when greater or unordered | t := 1.0, mask := 1 (A's end) |
| B2 | 0x008D1B6A JP 0x008D1B79 | tNum > 0 or unordered; fall-through when tNum <= 0 | fall-through: t := 0.0, mask := 2 (A's start), to 0x008D1BA9 |
| B3 | 0x008D1B90 JP 0x008D1B9E | 2^-20 * (d12^2 + e*a) >= denom, or unordered; reached only when B1 is not taken and B2 is taken (near-parallel fallback when tNum > 0) | t := 1.0, mask := 1; fall-through: t := tNum/denom, mask := 0 |
| B4 | 0x008D1BC0 JNZ 0x008D1BD1 | uNum = d12*t - r2 < e, or unordered; fall-through when uNum >= e | fall-through: u := 1.0, mask := 4 (overwrites, not OR), go to t recompute |
| B5 | 0x008D1BE0 JP 0x008D1C3D | uNum > 0 or unordered | taken: u := uNum/e, t kept, go to output; fall-through: u := 0.0, mask := 8 (overwrites), go to t recompute |
| B6 | 0x008D1C0C JP 0x008D1C19 | t' = d12*u + r1 > 0 or unordered | fall-through: t := 0.0, mask \|= 2 |
| B7 | 0x008D1C26 JNZ 0x008D1C33 | t' < a, or unordered | taken: t := t'/a; fall-through: t := 1.0, mask \|= 1 |
| - | 0x008D1C49 | join | write out+0x00, +0x10, +0x20; return mask |

Test flows the rebuild needs (derived from the table): crossing segments with
interior closest points (mask 0); t clamped at 0 (2) and at 1 (1) with u
interior; near-parallel segments with tNum > 0 (B3 taken, mask 1);
near-parallel segments with denom > 0 and tNum <= 0 (B2 falls through, t = 0,
mask 2, no tolerance test); exactly parallel segments, denom == 0 (B1 taken,
t = 1, mask 1, whatever the sign of tNum); u clamped at 1 then t
recomputed into interior (4), to 0 (6), to 1 (5); u clamped at 0 then t
interior (8), 0 (10), 1 (9); degenerate zero-length segments (a = 0 or e = 0);
NaN inputs on every compare.

pseudo.c disagrees with the instructions on unordered (NaN) operands at three
places, and the instructions win:
- B3: pseudo `if (fVar1 <= ...) goto` falls through to the division on NaN; the instructions jump to t := 1.0, mask 1 (TEST AH,5 / JP at 0x008D1B8D-0x008D1B90).
- B4: pseudo `if (local_34 < fVar10)` takes u := 1.0, mask 4 on NaN; the instructions jump to 0x008D1BD1 and then (B5, JP on unordered) divide.
- B7: pseudo `if (fVar2 < fVar7)` sets t := 1.0, mask |= 1 on NaN; the instructions jump to the division at 0x008D1C33.

(read: no FLDCW/LDMXCSR in the body; their influence is derived)

**Could two threads run this at once for two different phantoms?** Yes, as far
as this function goes (derived from groups b-e being empty): it is reentrant,
touches no shared state and only writes the caller's `out`. What stands against
it is outside the function, under four conditions:
- each thread passes its own `out` record; whether `out` (this+0x130 at the
  caller 0x0093C690, 0x0093C7C7) is distinct per thread is up to the caller
  (unverified);
- no other thread writes the four input vectors during the call;
- `out` does not alias `segBStart` or `segBDir`: out+0x00 is stored at
  0x008D1C71 before [ESI] (segBDir) and [EDX] (segBStart) are read again at
  0x008D1C74 and 0x008D1C7E, so aliasing changes the result (read). A rebuild
  that keeps bit identity has to keep that read-after-write order (derived);
- each thread's x87 control word and MXCSR match the main thread's for the
  results to be the same (per-thread FPU state; OBNG's earlier finding on x87
  RC in MXCSR applies).
Nothing in 0x008D1A30 itself blocks parallel use.

## Claims

1. The function is cdecl with five pointer arguments and returns a clamp mask in EAX. - read (0x008D1A3B-0x008D1A50, 0x008D1C49, 0x008D1CBB, RET 0x008D1CC1)
2. It computes closest points of two segments parameterised as start + s*dir, s in [0,1]. - derived (from the formulas t = (e*r1 - r2*d12)/|e*a - d12^2|, u = (d12*t - r2)/e, t' = (d12*u + r1)/a read at 0x008D1B02-0x008D1C45, which are the normal equations of min |A + t dA - B - u dB|^2)
3. Mask bits: 1 = t was set to 1.0 (clamped to 1, exactly parallel through B1, or the near-parallel fallback when tNum > 0 through B3), 2 = t set to 0.0 (clamped to 0, including near-parallel segments with tNum <= 0), 4 = u clamped to 1, 8 = u clamped to 0. - read (MOV/OR ECX at 0x008D1B72, 0x008D1BA4, 0x008D1BCA, 0x008D1BEA, 0x008D1C14, 0x008D1C2E); the meaning derived from the stored values 0.0/1.0
4. When u is clamped, the earlier t mask bits are discarded (MOV, not OR) and t is recomputed from u. - read (0x008D1BCA, 0x008D1BEA, 0x008D1BF1-0x008D1BFD)
5. When tNum > 0 (or NaN) and denom^2 > tNum*denom, the segments are treated as parallel if denom <= 2^-20 * (d12^2 + e*a), giving t = 1.0, mask 1. The test is not a general parallel rule: near-parallel segments with denom > 0 and tNum <= 0 get t = 0.0, mask 2 without it (0x008D1B6C/0x008D1B72), and exactly parallel segments (denom == 0) get t = 1.0, mask 1 from B1 (0 <= 0 equal, JNP at 0x008D1B59) whatever the sign of tNum. In every case u is then still computed from t and clamped, so mask 1 may later be replaced by 4 or 8. - read (B1 0x008D1B52-0x008D1B59, B2 0x008D1B5B-0x008D1B6A, B3 0x008D1B79-0x008D1B90, constant from data.json); the conditions derived from the FCOM flag table
6. out+0x00 = closest point on A (all four lanes including w), out+0x10 = point on A minus point on B (four lanes), out+0x20 = squared length of the xyz part of out+0x10. - read (0x008D1C5A-0x008D1CB8)
7. No callees, no global writes, no TLS, no heap, no clock. - read (meta.json callees empty; no CALL, no FS:, only three data refs, all loads)
8. Reentrant and safe for concurrent calls with distinct `out` records, provided no other thread writes the four input vectors during the call and `out` does not alias `segBStart` or `segBDir` (out+0x00 stored at 0x008D1C71 before [ESI] and [EDX] are re-read at 0x008D1C74/0x008D1C7E; a bit-identical rebuild keeps that order). - derived (claim 7 and the read order at 0x008D1C71-0x008D1C7E)
9. pseudo.c misrepresents NaN behaviour at B3, B4 and B7 and the dot3 summation order. - read (instructions cited in Control flow and Struct accesses)
10. Havok SDK name hkLineSegmentUtil::closestLineSegLineSeg and result struct name ClosestLineSegLineSegResult. - unverified (memory only; the seed row re/symbols/slice-frame-update.csv line 53 says hkLineSegmentUtil_closestPoints, inferred; a Havok 3.x/4.x SDK symbol or header, or an xOBSE/OBVR address list naming 0x008D1A30, would settle it; not a refutation)
