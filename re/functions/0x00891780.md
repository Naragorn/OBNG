## Purpose

When bit 0 of the flags byte at `this+0x1F4` is set, the function builds two points in a local frame from two
floats of `this` - `r = [this+0x3A0]` and `h = [this+0x3A4]` - namely `(0, +(0.5*h - r), r, 0)` and
`(0, -(0.5*h - r), r, 0)`, transforms each by a 4x4 matrix found at `[[this+0x8]+0x30]+0x70` (rotation columns
plus the translation column, applied as a point), stores the two results as 16-byte vectors at `this+0x380` and
`this+0x390`, and then adds `[this+0x248]` to the third component (z) of each. Nothing else is written. It makes no
world query, no allocation and touches no global but the stack cookie. The seed name "support probes" fits a pair
of points ahead of and behind the character at height `r`; that interpretation (capsule radius / height,
probe points) is unverified.

## Calling convention and parameters

- `__thiscall`: ECX holds `this` (copied to ESI at 0x00891796); read.
- No stack parameters: the body never reads `[EBP+8]` or above; read (asm.s, whole body).
- `RET` with no immediate at 0x00891844: nothing to clean; read.
- Returns nothing the caller uses. EAX at the return is `this+0x398` (the LEA at 0x0089181C) only on the bit-set
  path, and only if `__security_check_cookie` 0x009811E2 preserves EAX (not followed: **unverified**); on the
  bit-clear path EAX = `[0x00B30AAC]^ESP` (0x00891789-0x0089178E, nothing writes EAX on the way 0x008917A0 ->
  0x00891833). The `void` conclusion does not depend on either value: the caller's next instruction at 0x008968AA
  overwrites EDI and never reads EAX before 0x008968C9; derived (asm.s here and 0x00896000/asm.s
  0x008968AA-0x008968C9). Treat as `void`.
- Frame: `PUSH EBP; MOV EBP,ESP; AND ESP,0xFFFFFFF0; SUB ESP,0x24` (0x00891780-0x00891786), then EBX, ESI, EDI
  pushed and restored (0x00891794-0x0089179F, 0x00891837-0x00891839). After the three pushes ESP is 16-byte
  aligned, so the local vector at `[ESP+0x10]` is 16-byte aligned; derived (0x00891783 and 0x00891786 plus three
  4-byte pushes = 0x30). The callee's `MOVAPS` from it (0x0088FCC6) requires that.
- x87 stack balanced in each iteration (FLDZ/FST/FLD/FSTP/FLD/FSTP/FSTP, then FLD/FADD/FSTP) and empty at each call;
  derived (0x008917C3-0x008917E9, 0x00891815-0x0089182F).

## Control flow

Every branch, in address order. Each is a test flow for a later rebuild.

| # | At | Instruction | Condition | Effect |
|---|---|---|---|---|
| F1 | 0x008917A0 | `JZ 0x00891833` | `([this+0x1F4] & 1) == 0` | skip everything: no read past +0x1F4, no write; only the cookie check runs. read |
| F2 | 0x008917AB | `JZ 0x008917B4` | `[this+0x8] == 0` | EAX = 0 (0x008917B4), so the matrix pointer is 0x00000070; the callee then reads address 0x70 with MOVAPS, which faults. derived (0x008917B4, 0x008917B8, 0x0088FCC9-0x0088FCF6). Whether the engine ever reaches this with bit 0 set is unverified. |
| F2' | 0x008917AD/0x008917B2 | `CALL 0x008AC0C0; JMP 0x008917B6` | `[this+0x8] != 0` | EAX = `[[this+0x8]+0x30]`. read |
| - | 0x008917BB | `JMP 0x008917C0` | unconditional | enters the loop with EDI = 0, EBX = matrix pointer. read |
| F3 | 0x008917ED | `JNZ 0x008917FD` (flags from `CMP EDI,1` at 0x008917C0; the x87 instructions between do not change EFLAGS) | `EDI != 1` | iteration 0 keeps `y = 0.5*h - r`; iteration 1 multiplies y by `[0x00A3D360]` = -1.0 (0x008917EF-0x008917F9). read |
| F4 | 0x00891831 | `JC 0x008917C0` (flags from `CMP EDI,2` at 0x0089182C) | `EDI < 2` unsigned | exactly two iterations, EDI = 0 then 1. read |
| - | 0x0089183C | `CALL 0x009811E2` | always | stack cookie check; its failure path is outside this function. read |

Per iteration i (0, 1), in order (read, 0x008917C0-0x0089182F):

1. local `v = (0.0, y, r, 0.0)` with `y = (h * 0.5) - r` computed on x87 (`FMUL double [0x00A2FAA0]` = 0.5,
   `FSUB float [this+0x3A0]`) and rounded to single by `FSTP float` (0x008917DB); `r` stored as loaded (0x008917E5).
2. when i == 1: `y = y * -1.0` (x87, rounded to single at 0x008917F9).
3. `CALL 0x0088FCC0` (ECX = `this+0x380+16*i`, push 1 = matrix pointer EBX, push 2 = `&v`); the callee cleans
   8 bytes (`ret 0x8` at 0x0088FD0B) - consistent with the caller's ESP-relative locals staying valid in iteration 2.
4. `[this+0x388+16*i] = [this+0x388+16*i] + [this+0x248]` (x87 FLD/FADD/FSTP float).

The callee 0x0088FCC0 (read through disasm.py): `dest = (col0*v.x + col1*v.y) + (col2*v.z + col3)` lane-wise in
SSE single precision (0x0088FCD7-0x0088FCFF), where col_k is the 16 bytes at `matrix+16*k`. The w lane of `v` is
not used: col3 is added unconditionally, so the vector is transformed as a point.

## Claims

1. When bit 0 of `[this+0x1F4]` is clear, the function writes nothing and calls only `__security_check_cookie`.
   **read** (0x00891798, 0x008917A0 -> 0x00891833).
2. When the bit is set, it writes exactly 32 bytes of `this`: `+0x380..+0x39F`, and nothing else in memory except
   its own stack frame. **read** (the only stores outside the frame are 0x0088FD05 through ECX and 0x0089182F
   through EAX = `this+0x388+16*i`; the stores at 0x008917C5-0x008917E9 and 0x008917F9 are `[ESP+0x10..0x1C]`).
3. Group (a), own object (`this`, the controller): reads +0x1F4 (byte), +0x8, +0x3A0 (twice per iteration),
   +0x3A4, +0x248; writes +0x380..+0x38F and +0x390..+0x39F, each z twice (callee, then the add). **read**.
4. Group (b), other actors or references: none touched directly. **read** for this function's own instructions and
   its two callees; whether `[[this+8]+0x30]` can belong to another actor is **unverified** (it is reached through
   this controller's own pointer at +0x8).
5. Group (c), Havok world: reads the 64-byte transform at `[[this+0x8]+0x30]+0x70`, and the pointer at
   `[this+0x8]+0x30`. No write, no world lock, no query, no broad-phase call. **read** (0x008AC0C0, 0x0088FCC0
   fully disassembled: neither writes anywhere but `[ECX]` of 0x0088FCC0). That this transform is the character
   phantom's transform in the Havok world is **unverified**.
6. Group (d), globals: reads `[0x00B30AAC]` (stack cookie, 0x00891789; data.json u32 0xBB40E64E); reads the
   constants `[0x00A2FAA0]` (double 0.5, data.json f64 "0.5") and `[0x00A3D360]` (double -1.0, data.json f64
   "-1.0"). Writes no global. **read**. That the two constants live in a read-only section is **unverified**
   (data.json gives no section).
7. Group (e), heap: no allocation, no free. **read** (callees 0x008AC0C0 and 0x0088FCC0 make no calls; read).
8. The clock: the function reads no frame time and no timer global and writes none. **read** (no data reference
   but the three above; meta.json `data_refs`).
9. Two calls on distinct controllers do not conflict with each other: they share no write, and their only shared
   reads are of constants (`[0x00A2FAA0]`, `[0x00A3D360]`, the cookie `[0x00B30AAC]`). **derived** from claims 2-7.
   Running alongside other threads is safe only if, during the call, no other thread writes `this+0x8`,
   `[this+0x8]+0x30`, `this+0x1F4` (bit 0), `+0x248`, `+0x3A0`, `+0x3A4` or the 64 bytes at
   `[[this+0x8]+0x30]+0x70` (whoever owns that object - that it belongs to the same actor is **unverified**), and
   no other thread reads `this+0x380..+0x39F`: each point is written twice (`MOVAPS` at 0x0088FD05, then the
   separate z `FSTP` at 0x0089182F), so a concurrent reader can see a torn point with a half-updated z.
   **derived** from claims 2-5 and those two stores. The transform condition is the open point for the parallel
   map: whoever moves the phantom (the integrate 0x008AD7D0 path, in progress in this slice) must not write it
   concurrently with this read.
10. Iteration 1 does not read anything iteration 0 wrote: the writes (+0x380..+0x39F) and the reads (+0x248,
    +0x3A0, +0x3A4, the transform) do not overlap within `this`. **derived** (claims 2-3). Overlap of the transform
    with `this` is **unverified** but would need `[[this+8]+0x30]+0x70` to point into the controller.
11. Bit identity: `y = 0.5*h - r` computed on x87 at any precision control and rounded to single equals the IEEE
    single result of the same operations (scaling by 0.5 is exact unless the result is subnormal; one add or
    subtract of two singles rounded through 53 or 64 bits and then to 24 is innocuous double rounding); the same
    holds for the z add. **derived** (instruction sequence 0x008917C9-0x008917DB, 0x00891815-0x0089182F; the
    double-rounding argument is standard numerics, not read from the binary). Subnormal handling differs between
    x87 and an SSE path with FTZ/DAZ set in MXCSR - the callee is SSE and runs under whatever MXCSR the thread has.
    **unverified** in game.
12. The pseudocode is wrong in two places: (1) it shows `FUN_0088fcc0(iVar1 + 0x70, &local_30)` without the ECX
    destination `this+0x380+16*i` set at 0x00891801-0x00891809; (2) rea-all's pseudocode of 0x0088FCC0 sums
    `x*col0 + y*col1 + z*col2 + col3` left to right, while the instructions compute `(col0*x + col1*y) +
    (col2*z + col3)` (0x0088FCDB-0x0088FCFF). The instructions win; a bit-identical rebuild must follow their order.
    **read**.
13. The callees' instructions were read with `tools/re/disasm.py` from the copy at
    `/run/media/nadi/Games/Modding/Oblivion - A Painted World/Stock Game/Oblivion.exe`, whose md5 is
    66a6c2ef97ddea75f43d916aca8d164d, not the reference md5. Its 197 bytes at 0x00891780 equal this export's
    bytes.bin (compared byte for byte), and its readings of 0x008AC0C0 and 0x0088FCC0 agree with rea-all's
    decompile of the reference build in loads, the ECX store and the call shape. **read** for the equality of
    0x00891780. That the callees' bytes in the reference build equal those in the local copy is **unverified**: the
    export holds bytes only for 0x00891780, no slice export has 0x0088FCC0 or 0x008AC0C0, and pseudocode cannot
    settle bytes. Settle it by byte-comparing 0x0088FCC0-0x0088FD0D and 0x008AC0C0-0x008AC0C3 in the reference exe
    (md5 cdd2f0c5eff198d4f26b7b5b54ce4930) against the local copy, or by an export of the two callees with bytes.bin.
    Re-checked in a second pass of this slice (same copy, same md5): bytes.bin equal again, 0x0088FCC0 ends in
    `ret 0x8` at 0x0088FD0B and 0x008AC0C0 is `mov eax,[ecx+0x30]; ret`. **read**.
14. The caller clears bits 9-10 and sets bit 16 of `[this+0x1F4]` right before the call and clears bit 16 after the
    support check (0x0089688F, 0x00896899, 0x008968D5). This function does not test bit 16. **read**.
