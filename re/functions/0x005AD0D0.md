## Purpose

Answer to the slice question ("which situation calls the clock from here?"):

**The loading menu is being constructed, and the clock it updates is not the
game's clock.** 0x005AD0D0 allocates a private 0x18-byte `TimeInfo` for the
menu (0x005AD2E7: `FormHeap_Allocate(0x18)`), constructs it with the current
tick (0x005AD309-0x005AD30E, 0x0047D150), stores it at `this+0x54`
(0x005AD31F) and then calls the TimeInfo update 0x0047D170 **on that private
instance** (0x005AD325 `MOV ECX,EDI`, 0x005AD327 `CALL 0x0047D170`), not on
`g_timeInfo` 0x00B33E90. The update primes the private clock; its `+0x10`
(milliseconds since start) is copied into `this+0x68` and `this+0x6C` as the
menu's time baselines (0x005AD32C-0x005AD335). The loading menu's update
0x005AD980 later ticks the same private clock through `this+0x54`
(0x005AD9B6, 0x005AD9C2) and measures against `+0x68` / `+0x6C`
(0x005AD9CF, 0x005AD9D4).

Everything else in the function is constructor work:

1. Base constructor 0x00584640 with ECX = this (0x005AD116), then the vtable
   0x00A6C40C is written (0x005AD11F) and fields are initialised
   (0x005AD125-0x005AD141).
2. If `g_osGlobals` (0x00B33398) `+0x24` is nonzero, a thiscall to 0x006A9B40
   on that object (0x005AD145-0x005AD158).
3. Reads the four `[LoadingBar] fPercentageOfBar0..3` INI settings through the
   pointer table 0x00B14120 (4 entries, loop bound 0x005AD1AA and
   0x005AD27B), copies each value into the float array 0x00B3B3DC
   (0x005AD18D), sums them, and zeroes `this+0x2C..+0x38`.
4. If the sum is not 1.0 within a tolerance, formats a multi-line warning
   ("Total value of [LoadingBar] percentages is not equal to 1.0000f in ini
   file." + one line per setting + "INI Total = %.04f") and hands it to
   0x004A7A60 (0x005AD2DF).
5. Creates and primes the private clock (above), then sets `this+0x40` from
   the float at 0x00B14158 (0x005AD338-0x005AD33E) and returns `this`.

## Calling convention and parameters

- **thiscall**, `this` in ECX (read: 0x005AD110 `MOV ESI,ECX`; ECX is not
  touched between entry and that instruction, and ECX = this is passed on to
  the base constructor at 0x005AD116).
- **No stack parameters** (read: no access to `[EBP+8]` or above anywhere in
  asm.s; the frame is addressed only through ESP after `AND ESP,0xFFFFFFC0`).
- **`RET` with no immediate** at 0x005AD366 (read) - nothing to clean, ret 0.
- **Returns `this` in EAX** (read: 0x005AD341 `MOV EAX,ESI`).
- Frame (read): EBP frame with the stack aligned down to 64 bytes
  (0x005AD0D3), an SEH registration with handler 0x009C05A9
  (0x005AD0D6-0x005AD10A), a /GS cookie from 0x00B30AAC checked by
  0x009811E2 (0x005AD355-0x005AD35E). EH state lives at `[ESP+0x580]`:
  0 after the base constructor (0x005AD14F), 1 around the TimeInfo
  construction (0x005AD2FF), 0 again (0x005AD317).
- Locals (read, offsets relative to ESP after the prologue): a 0x400-byte
  message buffer at ESP+0x13C (0x005AD1E2 with one push outstanding), a
  0x104-byte line buffer at ESP+0x34 (0x005AD217 with four dwords
  outstanding), a float sum at ESP+0x2C reused for the allocated pointer
  (0x005AD162, 0x005AD2F3), `this` saved at ESP+0x30 (0x005AD112).

### Where pseudo.c and asm.s disagree (the instructions win)

- pseudo.c passes the GS cookie copy as an argument to `FUN_00584640`; the
  instructions pass only ECX = this (0x005AD116). The `PUSH EAX` at 0x005AD102
  is the cookie stored in the SEH frame, not an argument.
- pseudo.c declares `void`; the function returns `this` in EAX (0x005AD341).
- pseudo.c drops ECX on `FUN_006a9b40` (ECX = `[g_osGlobals]+0x24`,
  0x005AD14A), the argument 0x18 of `FormHeap_Allocate`, the tick arguments and
  ECX of 0x0047D150 / 0x0047D170, the index argument of the "Missing" warning
  (0x005AD17B) and the name argument of the "NOT FOUND" line (0x005AD22E) -
  hiding the null dereference of C9.
- pseudo.c writes `local_598 = (float)iVar8`; the instruction is a plain dword
  store of the pointer into the reused slot (0x005AD2F3 `MOV [ESP+0x2C],EDI`).

## Open questions

1. What is 0x0047D150 exactly (does it zero +0x00..+0x10 and set +0x14 = tick)?
   It decides what the first update at 0x005AD327 computes (the delta between
   the two GetTickCount calls minus the initial +0x10). Needs its export.
2. Does the main loop's update step (0x0040D800, update at 0x0040D8AB) run
   while the loading menu is active, i.e. do 0x005AD980 and the main loop

   (0x00578E00, 0x005ADB40, 0x00462B20, 0x0057E150, 0x005ADEC0, 0x00465860).

   destructor (vtable slot 0 of 0x00A6C40C) - unverified.
4. Values of 0x00B14158 (initial +0x40), 0x00A2F928 and 0x00A3B150 (sum check
   constants), 0x00A2FC70 (divisor in 0x005AD980). Not in the export.
5. What does `[g_osGlobals]+0x24` hold, and what does 0x006A9B40 do with it
   during loading-menu construction?
6. Does vtable 0x00A6C40C point back (via its complete object locator at

## Layout requests

For `src/engine/time/TimeInfo.h` (shared header of this slice):

- `TimeInfo` is instantiated more than once: the global at 0x00B33E90 and a
  heap instance per LoadingMenu (C1). The header must not assume a singleton;
  the update must be a member on any instance.
- `TimeInfo` size 0x18 (confirmed independently by the allocation at
  0x005AD2E7), `+0x10` uint32 ms since start (read at 0x005AD32F).
- `TimeInfo::TimeInfo(uint32 tick)` at 0x0047D150, thiscall, ret 4 (derived,
  C2).
- The globals 0x00B39DB0 / 0x00B39DB4 are shared by all instances (C6); model
  them outside the struct.

For a later menu header (outside this slice):

- `LoadingMenu` (proposed, vtable 0x00A6C40C): +0x3C int, +0x40 float,
  +0x54 `TimeInfo*`, +0x60 int, +0x64 int, +0x68 uint32, +0x6C uint32,
  +0x70 bool, +0x71 bool (table above).
- `Setting { float value; const char* name; }` as used through 0x00B14120
  (+0x00, +0x04 read).
