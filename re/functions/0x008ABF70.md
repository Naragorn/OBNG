## Purpose

It returns, on the x87 stack, a scalar "distance" between two 0x30-byte contact points A ([EBP+8]) and
B ([EBP+0xC]) of the character proxy in ECX. The value is (read, instructions 0x008ABF7C-0x008AC06A):

```
angle  = (1.0 - dot3(A.normal, B.normal)) * proxy[+0x60] * proxy[+0x60]     -> stored as float
dist2  = (A[+0x1C] - B[+0x1C])^2                                             -> stored as float
vA     = point velocity of A's body at A.position, or 0 when A has no qualifying body
vB     = point velocity of B's body at B.position, or 0 when B has no qualifying body
dv2    = dot3(vA - vB, vA - vB)                                              -> stored as float
return dv2 * 0.1 + angle * 10.0 + dist2        (x87, ST0)
```

The callers use it two ways. (1) Matching a candidate point A against each manifold entry B: 0x008AC640
(call site 0x008AC66C) keeps the index of the manifold entry with the smallest value below 0.1 (immediate
0x3DCCCCCD at 0x008AC656) and returns it or -1 (read, 0x008AC640 asm); 0x008AD150 at 0x008AD2DB compares the
value against 1.1 (immediate 0x3F8CCCCD stored at 0x008AD2BA, used by FCOM 0x008AD2E0) (read). (2) Pruning
duplicates inside the manifold: at 0x008AD5D8 both arguments are manifold entries - A = entry i
(`[proxy+0x74] + EDI`, 0x008AD5C0-0x008AD5D0) and B = an earlier entry j < i (EBX = A - 0x30 at 0x008AD5CA,
stepped down by 0x30 at 0x008AD5EB) - and a value below 0.1 ([0x00A2FAAC], FCOMP 0x008AD5DD) removes entry i
(0x008AD5F4-0x008AD62B: a vtable +0x0C call on each object of the array [proxy+0x80], then the last entry copied over it and +0x78
decremented) (read). So it is a contact-point similarity score used both to match candidates against the
manifold and to find near-duplicate manifold entries (derived from those three call sites; the manifold
semantics of +0x74/+0x78 come from re/functions/0x008AD7D0.md, mapped).

No loop, no jump table (data.json `jump_tables` is empty). Test flows for a rebuild (derived from 1-4): vA
computed or not (branch 1 taken, branch 2 taken, both fall through) crossed with vB computed or not (branch 3
taken, branch 4 taken, both fall through) - nine combinations, four distinct outcomes (vA in {0, v(A)}, vB in
{0, v(B)}). Plus the numeric flows: identical normals (angle 0), opposite normals (angle = 2 * k^2 * 10), equal
distances (dist2 0), NaN in any input (propagates into ST0; the callers' FCOM/`TEST AH,5`/JP then treat it as
unordered).

Precision path (read, for a class A rebuild): dot3 and dv2 are single-precision SSE (`MULPS`, `ADDSS`); the
angle term is x87 from the float 1.0 and the float dot, multiplied twice by the float k, then rounded to float
by `FSTP` at 0x008ABFD2; dist2 is x87 and rounded to float at 0x008ABFE0; the final `dv2*0.1 + angle*10.0 +
dist2` is x87 under the thread's x87 control word (precision and rounding control) and returned unrounded in
ST0. The SSE parts (dot3 0x008ABF8E-0x008ABFA7, dv2 0x008AC029-0x008AC047, the callee's v + w x r
0x008ABCF3-0x008ABD2C) run under the thread's MXCSR (rounding mode, FTZ/DAZ). The addition order is
(dv2*0.1 + angle*10.0) + dist2 (FADDP 0x008AC064, FADD 0x008AC066). pseudo.c shows the same terms in a
different textual order; the instructions are the reference.

## Could two threads run this at once for two different phantoms

**Yes, as far as this function's own accesses go (derived):** it writes nothing outside its own stack frame and
the out vector on that frame, takes no lock, touches no TLS, no heap, no global except three read-only float
constants. Two calls for two different proxies share no written memory.

What stands against it:
1. **Reads of other bodies' motion state** (M+0x60, +0xD0, +0xE0 of every touched body, via 0x008ABCE0).
   These are written by the world's simulation step and by whatever sets velocities (e.g. 0x008AC6A0's point
   impulses, per 0x008AD7D0.md). If a worker runs this while the main thread steps the world or another
   controller pushes the same body, the vec4 reads can tear or see a half-updated velocity - a data race, not
   a crash (derived; the writers' timing relative to the controllers is unverified here).
2. **Reads of the proxy's manifold entry B**: the caller 0x008AD7D0 rewrites `[proxy+0x74]` entries and may
   reallocate the array (0x008A6EE0, per 0x008AD7D0.md). For two *different* proxies this is not shared; for
   the same proxy it must not run beside its own manifold update (derived).
3. **The contact's collidable pointer [P+0x28]** must still be alive: if the main thread removes a body from
   the world while a worker holds a contact referring to it, the reads at 0x008ABFC7/0x008ABFE8 and in
   0x008ABCE0 read freed memory (derived; removal timing unverified).
4. **The whole floating-point state is per thread**: the angle, dist2 and final sum depend on the x87 control
   word's precision and rounding control (x87 ops 0x008ABF7C-0x008ABFE4, 0x008AC04F-0x008AC066, read); the
   SSE dot3, dv2 and the callee's point velocities depend on MXCSR - rounding mode, FTZ/DAZ (SSE ops
   0x008ABF8E-0x008ABFA7, 0x008AC029-0x008AC047, 0x008ABCF3-0x008ABD2C, read). A worker with a different
   MXCSR or x87 control word than the main thread's gives different low bits, which can flip the callers'
   `< 0.1` / `< 1.1` comparisons at the boundary (derived from those instructions; the main thread's and a
   worker's control words and MXCSR were not measured here).
5. **Alignment**: `MOVAPS` on A+0x10, B+0x10 (0x008ABF82, 0x008ABF8A) and on M (0x008ABCE6 ff.) requires
   16-byte alignment; a worker that builds contact points in its own buffers must keep them aligned (read).
