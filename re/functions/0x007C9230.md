## Purpose

Called once per drawn geometry by the shadow-light shader family before the draw
(C1, C2). It fills the vertex-shader constant globals that depend on the drawn
object's transform and on the current pass, in this order:

1. **Skin gate** (0x007C923C-0x007C929C): when the geometry's shader property
   `[propertyState+0x18]` has bit 1 of its +0x1C flags, a missing partition ends the
   call; otherwise the bone palette is built (0x007655F0 on the global object
   `[0x00B43104]`, args `(skin, world, 0, 3, 1)`) unless `this+0x34` is non-zero, and
   `[[this+0x18]]+0x30(partition.+0x24 word)` is called.
2. **Model transform** (0x007C92A1-0x007C92A7): `0x00765480(world, 0)` on `this+0x14`
   for every draw that is not cut at step 1.
3. **Three early-out pass kinds** that write only the vec4 at 0x00B44FD8 (or its w)
   and return: render mode `[0x00B42EAC] == 5` with `g = [0x00B44EE4] == 0`; pass id
   `[0x00B42E90]` in 6..9 with g > 0; pass id in 6..9 with g <= 0 or NaN.
4. **Inverse world** into a local D3DX matrix `Minv` (D3DXMatrixInverse of the skin's
   +0x28 matrix with the offset vector 0x00B3F92C added, or the NiTransform inverse
   0x00718A80 of `world` rebuilt as a 4x4).
5. **Two light directions** into 0x00B454D8 (gated by descriptor 0x00B45030).
6. **0x007C9140** `(&Minv, world.scale, passId, skin)` - every draw that reaches here.
7. **Eye / point constant** into 0x00B44F08 (and 0x00B44F18 for pass ids 0x180..0x187).
8. **Shadow projection matrix** into 0x00B45498 (gated by descriptor 0x00B4501C).
9. **Packed world transform** into 0x00B45560 (gated by descriptor 0x00B45024 and the
   property's ShadowSceneNode).
10. **Transposed skin matrix** into 0x00B44F98 (gated by descriptor 0x00B45068 and skin).
11. **User clip planes** for pass ids 0x177..0x17A: six `SetClipPlane` calls on the
    D3D device, computed once per shadow light and cached at light+0x1B4 / +0x214.

Return value: always 0 (every exit, read).

## Calling convention and parameters

`__thiscall`. ECX = `this`, copied to EBX at 0x007C9246 and saved at `[ESP+0x1C]` at
0x007C9249 (read). Frame: `PUSH EBP; MOV EBP,ESP; AND ESP,-16; SUB ESP,0x234`, then
PUSH EBX, ESI, EDI (0x007C9230-0x007C9248, read). Arguments are addressed from EBP.
The callee pops 32 bytes: **eight** stack arguments (`RET 0x20` at all five exits, read).

pseudo.c disagrees: it lists seven stack parameters (`param_2`..`param_8`, with
`param_1` = this). The instructions win: `RET 0x20` pops eight, and the HairShader
caller pushes eight dwords before the call (0x0080BF6C-0x0080BF9D, objdump). The
eighth, like the first, fourth and sixth, is never read by this body (derived: the
only EBP-relative operands are +0x0C, +0x10, +0x18, +0x20; grep of asm.s).

## Call sites (the slice's first question)

**0x007655F0 BuildBonePalette** (read, 0x007C926E-0x007C9288):
`ECX = [0x00B43104]`; pushes `1, 3, 0, ESI = arg7, ECX = arg2`, so the call is
`[0x00B43104]->BuildBonePalette(skin = arg2, world = arg7, rowTranslation = 0, mode = 3,
separateSkinToWorld = 1)`. It runs when `[arg5+0x18] != 0`, bit 1 of that property's
+0x1C is set, `arg3 != 0`, and `this+0x34 == 0`. pseudo.c drops the ECX load; the
instructions set it at 0x007C9282.

**0x007C9140 UpdateLightPositionConstants** (read, 0x007C97CB-0x007C97E1):
pushes `arg2` (arg4 `skipAdjust`), `EDI` (arg3), a float slot filled by
`FLD [ESI+0x30]; FSTP [ESP]` (arg2), then `LEA ECX,[ESP+0x10C]` = local +0x100 (arg1).
So `UpdateLightPositionConstants(&Minv, world.scale, passId, skin)`. EDI holds
`[0x00B42E90]` from 0x007C92BC and is not written before 0x007C97D2; ESI holds arg7 on
every path into 0x007C97CB (set at 0x007C9272/0x007C929E/0x007C97C8, not written in
between). `MOV ECX,EBX` at 0x007C97DF sets ECX = this, which the stdcall callee does
not read (0x007C9140.md). It runs on every call that is not cut by B3, B7/B11, B12
(pass 6..9) - that is, for every pass id outside 6..9 and outside the mode-5/g == 0 case.

The seed's "arg2 the scale +0x0C of a transform record" is corrected: arg2 is
`world+0x30`, the NiTransform's scale (read 0x007C97CE).

## Claims

- **C1 read (exe scan)**: the dword 0x007C9230 appears in `.rdata` at 0x00A90668,
  0x00A94090, 0x00A941E0 and 0x00A945D0. Each is slot 13 (+0x34) of a vtable starting
  at 0x00A90634, 0x00A9405C, 0x00A941AC, 0x00A9459C whose Complete Object Locators
  (0x00ACFE38, 0x00AD101C, 0x00AD1080, 0x00AD11A8) name `.?AVShadowLightShader@@`,
  `.?AVParallaxShader@@`, `.?AVSkinShader@@`, `.?AVSpeedTreeBranchShader@@`. xOBSE's
  RTTI list (re/symbols/xobse.csv:1370, 1401) names ShadowLightShader and SkinShader too.
- **C2 read (objdump)**: one direct call, `CALL 0x007C9230` at 0x0080BF9E, at the end of
  0x0080B7A0, which is slot 13 of the HairShader vtable (0x00A942A4, COL names
  `.?AVHairShader@@`); it pushes eight dwords and ends with `RET 0x20` at 0x0080BFAC.
  0x0080B7A0 is not a function in the Ghidra export (no file in rea-all; derived: why
  meta.json lists no caller). Derived: HairShader overrides the slot and calls this
  base implementation last.
- **C3 derived** (C1): `this` is a ShadowLightShader or one of its subclasses; who calls
  slot 13 per geometry (the render loop) is not in this export (open question).
- **C4 read**: return value 0 on all five exits (0x007C9342, 0x007C944B, 0x007C9493,
  0x007C9EF2, 0x007C9F1F).
- **C5 read**: the call at 0x007C92A7 `0x00765480(arg7, 0)` on `this+0x14` runs on every
  path except B3. Unverified (pseudocode of 0x00765480): it packs the NiTransform into
  `renderer+0x940` through 0x00761AE0, would call device slot +0xB0 with 0x100 only if
  its second argument were non-zero (it is 0 here), calls `[[renderer+0x8AC]]+0x34(world)`,
  and transforms two vectors at +0x628/+0x634 into +0x640..+0x654.
- **C6 read**: on the general path Minv is built two ways (0x007C9587-0x007C973C).
  When `skinned && skin != 0`: MC0 = `skin.+0x28` with its translation row (+0x30..+0x38)
  plus 0x00B3F92C/30/34, `D3DXMatrixInverse(&Minv, NULL, &MC0)` (pushes at
  0x007C9653-0x007C965D). Otherwise: `0x00718A80(&local80)` with ECX = arg7 (0x007C9670),
  then Minv rows (R00 s, R10 s, R20 s, 0), (R01 s, R11 s, R21 s, 0), (R02 s, R12 s, R22 s, 0),
  (t'x, t'y, t'z, 1), where R, t', s are the inverted transform's rotation, translation
  and scale at local +0x80..+0xB0 (0x007C9677-0x007C973C). No offset vector on this path.
- **C7 derived** (C6, and 0x00718A80's pseudocode, unverified, which writes the
  transposed rotation, 1/scale and the rotated negated translation): Minv is the D3DX
  (row-vector) form of the inverse world; on the skinned path the inverse of the
  skin-to-world with the offset vector added back to its translation.
- **C8 read**: the light-direction loop (0x007C974E-0x007C97C6) runs twice; for i = 0, 1:
  `v = -(0x00B465A8 + 16 i).xyz`, `D3DXVec3TransformNormal(&tmp, &v, &Minv)`,
  `D3DXVec3Normalize(&out, &tmp)`, `0x00B454D8 + 16 i = (out, 0)`. pseudo.c shows the
  Normalize call with different stack variables; the push arithmetic
  (0x007C978B-0x007C9795) gives pOut = local +0x30, pV = local +0x20.
- **C9 read vs 0x007C9140.md**: both functions read the same float +0x00 of an entry
  of 0x00B465A8 as a w (0x007C9140 its "lightW"; here on the B13 path, entry 0,
  0x007C946E-0x007C948D). This function additionally reads +0x04/+0x08 of entries 0
  and 1, together with +0x00, as direction components (0x007C9750, 0x007C9768,
  0x007C977A). That is not a read contradiction. Derived: the table is a vec4 array
  whose +0..+8 are used as a direction here and whose +0 is used as w there; only the
  inferred symbol name `g_lightWTable` is too narrow.
- **C10 read**: vec4 0x00B44FD8 is written by this function only on the early-out
  paths (B11: w only; B13: (0,0,0,[0x00B465A8]); B21: (0, 0, prop.+0xA0, g')), and by
  0x007C9140 on the general path (0x007C9140.md). Derived: in passes 6..9 and in the
  mode-5/g == 0 case 0x007C9140 is not called from here.
- **C11 read**: only the pass 6..9 sub-path with g = `[0x00B44EE4]` > 0 reaches the
  read: `FCOM`/`JP` at 0x007C935F-0x007C9368 sends g <= 0 or NaN to 0x007C9456 (B13).
  On the g > 0 sub-path ECX = prop only when `1 <= type <= 10` and `5 <= type <= 10`,
  else 0 (0x007C93A3-0x007C93E2); ECX is also 0 when the shader property is null
  (0x007C9374). Then `[ECX+0xA0]` is read at 0x007C93E8 without a null test. Derived:
  with a null property or a type outside 5..10 the read faults there, so callers in
  passes 6..9 must supply a type 5..10 property only when g > 0 (unverified that they
  do).
- **C12 read**: mode-5 path: the radius `[NiLight+0xF8]` is read at 0x007C9300 before
  the null test at 0x007C9306 (B8), so the null branch only skips the release.
- **C13 read**: the shadow matrix (B35) is `transpose(M80 x L.+0x10)` with
  M80 = skin.+0x28 (or 0x007640A0(world)) plus the offset in its translation row
  (0x007C9A54-0x007C9A8E); D3DXMatrixMultiply(pOut = local +0x160, pM1 = M80,
  pM2 = L+0x10) (0x007C9A9D-0x007C9AAE), copy to M40, D3DXMatrixTranspose(M40, M40),
  copy to 0x00B45498. On B29/B30/B32/B33/B34 instead `D3DXMatrixTranspose(0x00B45498,
  copy of renderer.+0x940)` (0x007C9AE4-0x007C9B0C).
- **C14 read**: clip planes (0x007C9CDE-0x007C9EF0): M40 = renderer.+0x980 with its
  translation row replaced by `-(o.x M[0] + o.y M[1] + o.z M[2])` per column
  (o = 0x00B3F92C/30/34, M[k] = row k; FPU sequence 0x007C9CDE-0x007C9D91);
  M80 = M40 x renderer.+0x9C0; M200 = inverse(M80); M80 = transpose(M200). For each
  of the six planes at L+0x150: (n.x, n.y, n.z, -constant) -> D3DXPlaneNormalize ->
  D3DXPlaneTransform by M80 -> local array and `device->[0xDC](i, &plane)`.
  Derived: with +0x980 = view and +0x9C0 = projection (unverified) these are the
  light's planes moved to clip space (inverse-transpose rule), with the eye shifted to
  the offset vector.
- **C15 derived** (C14, B45): the clip planes depend on no stack argument of this
  function. On a cache miss they depend on `this` (the renderer `[this+0x14]` and its
  +0x980/+0x9C0, read through the saved this `[ESP+0x1C]`, 0x007C9249 and
  0x007C9CEA-0x007C9CF0), on the global device `[0x00B43104]+0x280`, on L (+0x150) and
  on the offset vector; on a cache hit they depend only on L+0x1B4. The cached planes
  stay valid only as long as nobody clears L+0x214; the six device calls run on every
  draw in passes 0x177..0x17A (0x007C9EFD loop). Who clears +0x214 is not known.
- **C16 read**: the descriptor-gated blocks (B24, B28, B36, B42) are independent of each
  other: each tests its own descriptor's byte +0x08 and falls through to the next block.
- **C17 derived** (call sites above, C5, C6, C8, C13): per-draw inputs are arg2 (skin
  and its +0x28 matrix), arg3 (bone count word), arg5's property (flags, type, +0xA0),
  arg7 (world rotation, translation, scale), and `this`: +0x34, the shader class,
  this+0x14 (the renderer, read at 0x007C92A1, 0x007C9AE4, 0x007C9CF0) and this+0x18
  (0x007C928D). The renderer is a per-`this` input, not a global, unless `[this+0x14]`
  is shown to equal a global renderer (**unverified**). renderer+0x940 is written per
  draw by 0x00765480 (C5, pseudocode) and read at 0x007C9AE4, so it is a per-draw
  input too. The other inputs are globals or the shadow light: passId, renderMode, g,
  the offset vector, the two light directions, P, L (+0x10, +0xF5, +0x100, +0x150,
  +0x1B4, +0x214), the renderer's +0x980/+0x9C0 (per `this`, see above), the device
  `[0x00B43104]+0x280`, the four descriptor bytes, and the table behind 0x007B4280
  (0x00B42F54, C22, pseudocode). Whether those are constant per frame or per pass is
  **unverified** (their writers are not in this export).
- **C18 derived** (C17): what a per-draw cache could key on: Minv, 0x00B454D8, 0x00B44F08
  and 0x007C9140's output are functions of (world or skin.+0x28, offset, light table,
  P); they repeat exactly when the same object is drawn again in another pass with
  unchanged globals. They do not repeat across objects. The palette call is already
  gated by 0x007655F0's own stamp (0x007655F0.md), so repeated calls per skin cost the
  gate only (derived from that note, not from this function).
- **C19 derived** (instruction counts per path, not measured): fixed work per general
  draw is 0x00765480, Minv (one D3DXMatrixInverse on the skinned path, the cheaper
  0x00718A80 otherwise), up to two TransformNormal + Normalize, 0x007C9140 (up to three
  TransformCoord), one TransformCoord or 0x0043F350, up to one Multiply + two
  Transpose, and in passes 0x177..0x17A six device calls (plus Multiply, Inverse,
  Transpose and 6x Normalize + Transform on a cache miss). Which of these dominates the
  measured 15 % in 0x007C9140 / 7.6 % in the palette builder is not separated.
- **C20 read**: pseudo.c types `DAT_00b42e90` as a pointer (`puVar8`); the instructions
  compare it as a signed integer (`CMP EDI,0x180; JL`, 0x007C97E6) and use it as an
  unsigned range (`LEA ECX,[EDI-6]; CMP ECX,3; JA`, 0x007C9353). It is an integer id.
- **C21 read**: 0x0043F350 is called with ECX = local +0x20 (the vector P - translation)
  at 0x007C9841 and its x87 result is dropped (`FSTP ST0` 0x007C9846). Unverified
  (pseudocode): it normalizes the vector in place and returns the length (zeroes it
  when the length is <= 1e-6).
- **C22 read**: `0x007B4280(index)` is called cdecl (`ADD ESP,4` 0x007C9B56) and only
  its zero / non-zero result is used. Unverified (pseudocode + knowledge/
  shadow-light-list-remove.md): it returns `[0x00B42F54 + 4 index]`, the ShadowSceneNode.

## Open questions

- Which function calls vtable slot +0x34 of these shaders per geometry, and how many
  times per frame per geometry (the call count is the lever). Needs a search for
  `CALL [reg+0x34]` sites with a shader `this`, or a runtime count.
- What 0x00B42E90 / 0x00B42EAC enumerate (pass ids 6..9, 0x77, 0x85, 0x177..0x17A,
  0x180..0x187; mode 5) and who writes them.
- What `g` (0x00B44EE4) and P (0x00B46658..60) are, and their writers.
- C9: the writer of 0x00B465A8 and a name that covers both uses (direction and w).
- Who clears `L+0x214` (the clip-plane cache), and what `[0x00B42EB8]+0x0C` is
  (an iterator, a "current light" holder).
- Whether `[0x00B43104]` is the same object as OBVR's renderer `[0x00B3F928]`
  (both reach the device at +0x280) and whether `this+0x14` is that object too.
- Whether the device slot +0xDC is `SetClipPlane` (d3d9.h vtable order; not opened).
- Who uploads 0x00B454D8, 0x00B44F08/18, 0x00B45498, 0x00B45560, 0x00B44F98 to the
  device, and whether the descriptor bytes at +0x08 mean "used by the bound shader".
- The method name: does slot 13 correspond to Gamebryo's
  `NiShader::SetupTransformations` (eight arguments, the parameter roles proposed
  above)? A Gamebryo 2.x header or xOBSE's shader declarations would settle it.
