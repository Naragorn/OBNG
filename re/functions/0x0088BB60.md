## Purpose

Appends one 8-byte record `{ id, colour }` to a growable array that lives in the bhkWorld at
`this+0x6C` (data), `+0x70` (count), `+0x74` (capacity | flags). `id` is `[arg1+8] + 0x14` - an
address inside the Havok object that the Bethesda wrapper `arg1` holds - or 0 when `arg1` or
`[arg1+8]` is null. `colour` is `arg2` unchanged. When count equals capacity the array is grown
first through 0x008A6EE0 (heap, doubling).

The array is a deferred queue: the only reader found, 0x0088A790 (called once, from bhkWorld vtable +0x80
0x0088C440 at 0x0088C5CA), walks it from the back and hands each record to 0x008A7830 with
`ECX = [0x00BA7DA0]` as `(colour, id, 0)`, then sets the count to 0 (**read (EXE)**). Every caller
builds `arg2` with the ARGB packers 0x008AEB80 / 0x008AEBB0 (their pseudocode; 0x0088D5D3 read in asm).
Proposed meaning: a per-world queue of "set this collidable's debug colour" requests, flushed to the
debug display's handlers once per world update (**derived** from the above; the debug-display meaning of
`[0x00BA7DA0]` is the reading of 0x00896000.md and 0x0088B850.md, both in progress).

Nothing here reads or writes the clock (no float instruction, no global read in the body; **read**).

## Can two threads run this at once for two different phantoms?

No, not as it stands. Two phantoms in the same world append to the one array of the one bhkWorld
(Claim 6/8, derived). The append is an unlocked load-store of `size` (0x0088BB98 load, 0x0088BBA4 `ADD`
without `LOCK`) and a store at `data[size]`: two threads can write the same slot and lose a record, or
both see `size == capacity` and both grow, each freeing the same old buffer (double free) or one writing
into a buffer the other has just freed (use after free). On growth the old block is freed through the
*calling* thread's allocator (TLS `+0x19C`), which may not be the one that allocated it (cross-thread
free) - whether that allocator tolerates a foreign block is **unverified**. The drain 0x0088A790 in
bhkWorld vt+0x80 also reads and zeroes `size` without a lock; if a worker appended while the world
update drained, records would be lost or replayed.

What would make it safe, cheapest first (all **unverified** against a run): (1) keep the call on the
main thread after the parallel part, e.g. let each worker record `{id, colour}` in its own small buffer
and append them in actor order afterwards - order is not observable except in the debug display; (2) skip
the call entirely when nothing reads the records (the drain drops them when `[bhkWorld+0x14] == 0`, and
`[0x00BA7DA0]`'s handler list may be empty) - needs the measured value of both; (3) a lock around the
append, which costs a lock per controller update.
