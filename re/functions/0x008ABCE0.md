## Purpose

Computes `out = angVel x (p - com) + linVel` for one body, where
`motion = [this+0x50]`, `com = motion+0x60`, `linVel = motion+0xD0`,
`angVel = motion+0xE0` - i.e. the velocity of the body's material at world
point `p` (**read**, 0x008ABCE3-0x008ABD32; the mapping of +0xD0/+0xE0 to
linear/angular velocity is **read** in `knowledge/corpse-becomes-zombie.md`,
"its hkMotion at +0x50 ... linear velocity +0xD0, angular +0xE0"; +0x60 as the
centre of mass is **unverified**, see Open questions).

It touches one subsystem only: the Havok motion state of the body passed in
`ECX`. No clock, no lock, no global, no heap, no call.

## Control flow

No branches. One straight path 0x008ABCE0 -> 0x008ABD38 (**read**; `jump_tables`
in data.json is empty).

Lane detail the rebuild's tests should cover (**derived** from the shuffle
immediates 0xC9 = lanes (1,2,0,3) and 0xD2 = lanes (2,0,1,3) at 0x008ABD00,
0x008ABD07, 0x008ABD11, 0x008ABD18):

- x = w.y*r.z - w.z*r.y; y = w.z*r.x - w.x*r.z; z = w.x*r.y - w.y*r.x, with
  `r = p - com` and `w = angVel`; then `+ linVel` lane-wise.
- w lane = (ww*rw - ww*rw) + linVel.w, with `ww = angVel.w` and
  `rw = p.w - com.w`; both products are the same lane-3 product (shuffle
  immediates 0xC9 and 0xD2 both keep lane 3), subtracted at 0x008ABD1F, then
  added to linVel.w at 0x008ABD2C (**derived** from those instructions and the
  SSE rules; not run):
  - `ww*rw` finite, MXCSR round-to-nearest: the difference is +0.0, so the lane
    is +0.0 + linVel.w - equal to linVel.w except that -0.0 becomes +0.0, and a
    denormal linVel.w becomes 0 under DAZ/FTZ.
  - `ww*rw` finite, MXCSR round-down: the difference is -0.0, so -0.0 survives.
  - `ww*rw` inf or NaN - including finite factors whose product overflows, and
    `rw` itself being inf - inf: the lane is NaN.
  - A NaN or inf in linVel.w propagates on its own.
  A bit-identical rebuild must reproduce the subtract-then-add order, not just
  copy linVel.w. Test flows: finite, overflowing product, non-finite operands,
  linVel.w = -0.0, and MXCSR rounding mode and DAZ/FTZ.
- Aliasing: `point` is fully read (0x008ABCED) before `out` is first written
  (0x008ABD22), so `out == point` gives the same result (**derived** from the
  instruction order). Test flow: aliased and separate buffers.
- `out` is written twice; an observer on another thread could see the
  intermediate cross product (**derived** from 0x008ABD22 and 0x008ABD32).

Pseudocode note: pseudo.c writes the w lane as `ec*f8 - ec*f8`, which agrees
with the instructions; it splits the vector ops into scalar lines but shows no
disagreement with asm.s.

## Claims

1. The function is a `__thiscall` leaf with `RET 0x8` and no callees. **read** (0x008ABD38; meta.json callees `[]`).
2. It computes `out = motion[+0xE0] x (p - motion[+0x60]) + motion[+0xD0]` with `motion = [this+0x50]`. **read** (0x008ABCE3-0x008ABD32).
3. +0xD0 and +0xE0 of the motion are the linear and angular velocity. **read** in knowledge/corpse-becomes-zombie.md (not re-read here in the binary).
4. +0x60 is the world centre of mass. **unverified** (follows only from the formula's shape; no second source).
5. The only writes outside the function's own stack are to `*out`, at 0x008ABD22 and 0x008ABD32; `PUSH EBP` at 0x008ABCE0 also writes the own stack slot (group (a): EBP is saved). **read**.
6. It reads no global, TLS slot, lock, or clock. **read** (no absolute or FS operand; data_refs empty).
7. Two threads can run it at once for two different bodies, and also for the same body, without a data race inside the function, provided nobody writes that body's motion at +0x60/+0xD0/+0xE0 or `[this+0x50]` concurrently and the two calls use different `out` buffers. **derived** from claims 5 and 6.
8. `AND ESP,0xFFFFFFF0` at 0x008ABD2F has no effect. **read** (ESP restored at 0x008ABD35 with no stack access between).
9. 74 samples land here only under the controller (seed name; run obng-profile-gate-guards/20261114-215120 per the slice manifest). Not re-measured here.

## Can two threads run this at once for two different phantoms?

Yes, as far as this function goes (**derived**, claims 5-7). Outside its own
stack slot it writes only the caller-supplied output vector and reads only the given body's motion. What stands
against it is not in this function but around it: (1) a concurrent writer of the
same body's motion state (the solver/integrator, `setLinearVelocity` via motion
vtable +0x54, `setAngularVelocity` +0x58, or the main thread's node-to-Havok push
0x0089EAE0) would give a torn read of a 16-byte vector - **unverified** whether any
such writer runs during the controllers' phase; (2) a shared `out` buffer would
race, since `out` is written twice. Neither (c), (d) nor (e) is touched.
