## Purpose

Copies `count` elements from a source into a destination, both strided,
described by a 0x28-byte descriptor passed as the only argument, and returns
`count * countedBytes` (summed or multiplied, see Control flow). The
mechanism (strided copy, optional UInt16 index gather, zero-fill on a null
source, counted total) is **read** from the instructions below. That the
elements are vertex-stream elements, and so the name
`CopyVertexStreamElements`, is **unverified**: this export carries no
caller (meta.json `callers: []`), no strings and no data references; it
rests on the seed (OBVR `StreamCopyLogic.h`) and on Ghidra pseudocode of
0x0076F590 and 0x00771300. A generic strided gather/fill helper is not
excluded by this body. Settled by instruction-checking the table fill at
0x00771356 and the call site in 0x0076F590. Three paths, chosen in this
order (**read**, 0x0076E634, 0x0076E672):

1. source (+0x10) null: zero-fill, `memset(dest, 0, countedBytes)` per element.
2. index table (+0x0C) set: indexed gather, `memcpy(dest, source +
   index[i] * sourceWords * 4, elementBytes)` per element.
3. otherwise a straight strided run: inline dword moves when elementBytes is
   8, 12 or 16, `memcpy` per element for any other size.

Subsystems touched: none besides the CRT's `memset`/`memcpy` (**read**,
meta.json callees; data_refs empty). The function reads no global, so it
neither reads nor writes the game clock (**read**, meta.json `data_refs: []`,
data.json empty; **derived**: every memory operand in asm.s is based on EDI,
ESI, EBX, EAX or ESP).

## Calling convention and parameters

- cdecl, one stack argument, plain `RET` (no `RET N`): the caller cleans
  (**read**, the six `c3` exits).
- ECX is not an input: it is overwritten at 0x0076E624 before any read
  (**read**), so this is not thiscall.
- Frame: `SUB ESP,0xC` (0x0076E610), then PUSH EBX/EBP/ESI/EDI; the argument
  sits at [ESP+0x20] after the prologue and is loaded into EDI at 0x0076E617
  (**read**).
- Locals (after the prologue, **read**): [ESP+0x10] the running total
  (zeroed at 0x0076E62C, returned in EAX at every exit); [ESP+0x14]
  sourceWords on the indexed path (0x0076E681) or the loop counter on the
  generic straight path (0x0076E701, 0x0076E739); [ESP+0x18] destStride on
  the straight path (0x0076E6E7).
- The function overwrites its own argument slot [ESP+0x20]: with the index
  table pointer at 0x0076E630 (every path), then with countedBytes at
  0x0076E6DF (straight path) (**read**). Legal under cdecl; a caller that
  re-reads its pushed argument after the call would see a changed value
  (**derived** from those two stores).
- The descriptor is only read, never written: every `[EDI+...]` operand is a
  load (MOV/MOVZX/CMP/ADD into a register) (**read**, all 21 EDI operands in
  asm.s).
- Returns EAX = the total (**read**, the `MOV EAX,[ESP+0x10]` before each
  exit: 0x0076E664, 0x0076E6C4, 0x0076E73F, 0x0076E77F, 0x0076E7B9, 0x0076E7E7).

Unconditional: 0x0076E685 `JMP 0x0076E694` enters the indexed loop past the
reload of the index table pointer (EAX already holds it) (**read**).

`JBE` after `CMP word,0` or `TEST EAX,EAX` is taken only on zero: CF is 0 in
both cases (**derived** from the x86 flag rules for CMP with 0 and TEST).

Per-path loop bodies (**read**):

- Zero-fill (0x0076E642-0x0076E662): `memset(ESI, 0, [EDI+0x1C])`; ESI +=
  [EDI+0x20]; total += [EDI+0x1C] (re-read after the call, 0x0076E64E);
  BX += 1. Reads +0x1C, +0x20, +0x08 per iteration from the descriptor.
- Indexed (0x0076E690-0x0076E6C2): src = source + (u32)(indices[i] *
  sourceWords) * 4 (32-bit `IMUL`, then `LEA [EBX+EAX*4]`, both modulo 2^32);
  `memcpy(ESI, src, [EDI+0x14])`; ESI += [EDI+0x20]; total += [EDI+0x1C].
  sourceStride (+0x18) is not used on this path.
- Generic straight (0x0076E710-0x0076E73D): `memcpy(ESI, EBX, [EDI+0x14])`;
  ESI += saved destStride; total += saved countedBytes; EBX += sourceStride.
- 8/12/16 straight (0x0076E7D4 / 0x0076E7A0 / 0x0076E760): total = count *
  countedBytes computed once (32-bit `IMUL`, 0x0076E7CB / 0x0076E791 /
  0x0076E755) before the loop; then per element 2/3/4 dword loads and stores
  in ascending offset order, EBX += sourceStride, ESI += destStride.
- Padding inside the body, no effect: `NOP` 0x0076E70F, `MOV EDI,EDI`
  0x0076E75E, `LEA EBX,[EBX]` 0x0076E79A.

## Claims

1. The function is cdecl with one stack argument and the caller cleans the
   stack (**read**: six `RET` without immediate; argument at [ESP+0x20]
   after a 0x1C-byte prologue, 0x0076E617).
2. ECX carries no input (**read**, written at 0x0076E624 before any read).
3. The return value is the running total in [ESP+0x10], which starts at 0
   (**read**, 0x0076E62C and the six loads before the exits).
4. When source (+0x10) is null, the zero-fill path runs regardless of the
   index table (**read**, B1 at 0x0076E634 precedes the index test at
   0x0076E670).
5. The zero-fill path's memset size is countedBytes (+0x1C), not
   elementBytes (+0x14) (**read**, 0x0076E642 and 0x0076E64E load
   [EDI+0x1C], pushed at 0x0076E645 as memset's third argument; +0x14 is
   not read on this path). pseudo.c agrees (`_Size = *(param_1 + 0x1c)`).
6. The zero-fill path adds countedBytes to the total once per element
   (**read**, 0x0076E654).
7. The indexed path copies elementBytes per element from source +
   indices[i] * sourceWords * 4 and adds countedBytes per element; it ignores
   sourceStride (**read**, 0x0076E694-0x0076E6B7; +0x18 is read only at
   0x0076E6DC on the straight path).
8. sourceWords is read as a 16-bit word (**read**, `MOVZX ... word ptr
   [EDI+0x4]` 0x0076E624); count is a 16-bit word (**read**, every +0x08
   access is a word access).
9. The straight run has inline copies for exactly elementBytes 8, 12 and 16
   (**read**, B7-B9); every other elementBytes, including 4, takes the
   generic `memcpy` loop (**read**, fall-through at 0x0076E6FF).
10. On the 8/12/16 straight paths the total is count * countedBytes,
    computed once with a 32-bit `IMUL` (**read**, 0x0076E7CB, 0x0076E791,
    0x0076E755); on the generic straight path it is the sum of countedBytes
    over the elements (**read**, 0x0076E72B). Both are equal modulo 2^32
    (**derived** from the two).
11. When count is 0, every path returns 0 and calls neither memset nor
    memcpy and writes nothing to dest (**read**, B2, B5, B10, B12, B14, B16
    all branch before the first call or store; **derived** with the total
    note under Control flow).
12. dest (+0x24) is never null-tested (**read**, loaded at 0x0076E621, no
    compare on ESI). When dest is null and count > 0, the 8/12/16 straight
    paths always store to address 0 plus offsets (**read**, first stores
    0x0076E762, 0x0076E7A2, 0x0076E7D6). On the zero-fill, indexed and
    generic paths a write to address 0 plus offsets happens only when the
    per-element size is nonzero: countedBytes on zero-fill (0x0076E642),
    elementBytes on the indexed (0x0076E694) and generic (0x0076E710) paths
    (**derived** from 11 and the loop bodies; that memset/memcpy with size 0
    writes nothing is **unverified** for the CRT at 0x00981630 and
    0x009812C0).
13. The type code at +0x00 is not read (**read**, no `[EDI]` / `[EDI+0x0..3]`
    operand in asm.s).
14. The function reads no global and has no data references, so it does not
    touch the frame clock or any other engine state outside the descriptor,
    the source, the index table and the destination (**read**, meta.json
    `data_refs: []`, data.json empty).
15. The descriptor is never written (**read**, all EDI operands are loads).
16. Only some descriptor fields are re-read inside the loops (**read**):
    zero-fill re-reads +0x1C (0x0076E64E), +0x20 (0x0076E651) and +0x08
    (0x0076E65E). Indexed re-reads +0x14 (0x0076E694), +0x1C (0x0076E6B1),
    +0x20 (0x0076E6B4) and +0x08 (0x0076E6BE), but caches indices (the
    argument slot [ESP+0x20], 0x0076E630/0x0076E690), source (EBX,
    0x0076E61B) and sourceWords ([ESP+0x14], 0x0076E681). Generic re-reads
    only +0x14 (0x0076E710) and +0x08 (0x0076E71F); countedBytes, destStride
    and sourceStride come from the stack copies (`[ESP+0x2C]` 0x0076E723 and
    `[ESP+0x24]` 0x0076E727 with three pushed arguments, i.e. the slots
    [ESP+0x20] and [ESP+0x18]) and EBP (0x0076E735). On every path dest
    (ESI), source, indices and sourceWords are cached. A copy whose
    destination overlaps the re-read descriptor fields would therefore
    change the loop (**derived**); whether that
    can happen is **unverified** (the descriptor is on the caller's stack
    per OBVR's reading).
17. The 8/12/16 paths copy dword by dword in ascending order, so they
    differ from `memcpy` only when source and destination overlap
    (**derived** from 0x0076E760-0x0076E773 and siblings; CRT memcpy's
    overlap behaviour is **unverified**).

### Against OBVR's StreamCopyReference (`../OBVR/src/render/StreamCopyLogic.h`)

18. **Mismatch, zero-fill size.** OBVR's reference and its StreamCopyFast
    memset `d.elementBytes` per element; the instructions memset
    countedBytes (Claim 5). The totals agree (both add countedBytes per
    element) (**read** of the OBVR file; **derived** against Claim 5/6).
    The in-game check (202000 copies, 0 mismatches) cannot detect this when
    countedBytes >= elementBytes, or when the bytes [countedBytes,
    elementBytes) of each element were already zero: `StreamCopyChecked`
    runs the engine first, then the fast copy over the same destination,
    and compares only `StreamCopyDestSpan`, which ends at
    `(count - 1) * destStride + elementBytes`; the fast copy rewrites only
    elementBytes per element, so the engine's extra zeroes survive or lie
    outside the span. When countedBytes < elementBytes, the fast copy zeroes
    bytes the engine left alone, inside the span, and the memcmp against the
    scratch would report a mismatch whenever those bytes held nonzero data
    before the copy (**derived** from `../OBVR/src/render/StreamCopy.cpp`
    lines 49-58). The 0 mismatches are also consistent with the zero-fill
    path never running (the caller gate below), in which case the check
    never had a chance to see it. Also, in the decompiled
    caller 0x0076F590 the routine is called only when the source local
    (`local_18`, descriptor +0x10) is non-zero (`if (local_18 != 0)` before
    `(*pcVar3)(&local_28)`), which would make the zero-fill path unreachable
    from that caller (**unverified**: Ghidra pseudocode of
    `re/export/rea-all/functions/0x76f590.c`, not instruction-checked).
    The mismatch matters for a rebuild only if some caller passes a null
    source with countedBytes != elementBytes (**derived**).
19. **Match, every other path.** Indexed: source address, size, dest step and
    total agree (**derived**, Claim 7 against `StreamCopyReference`).
    Straight 8/12/16: OBVR uses memcpy, the engine dword moves - same bytes
    for non-overlapping buffers (Claim 17); total count * countedBytes in
    both (Claim 10). Generic: summed total in both. Path order (source test
    before index test) agrees (Claim 4). Count 0 returns 0 in both and in
    StreamCopyFast (**derived**).
20. OBVR's StreamCopyFast adds an element size 4 inline case on both the
    indexed and straight paths; the engine has none (Claim 9). This is an
    optimisation, not a difference in result (**derived**).

21. The routine is reached through a function table, not a direct call
    (meta.json `callers: []`, **read**). The decompiled 0x00771300 assigns
    `LAB_0076e610` when the source format index equals the destination

    `LAB_0076e4b0` otherwise (cases 1-4), and conversion routines

    same-format copy (**unverified**: Ghidra pseudocode of

22. 0x0076F3B0, which `knowledge/skinned-vertex-streams.md` calls "the

## Open questions

1. Does any caller pass a null source (+0x10) to 0x0076E610? The decompiled
   0x0076F590 suggests not; the second packer entry 0x0076FE20 and any other
   user of the table were not checked. Settles whether Claim 18 can matter.
2. Can countedBytes differ from elementBytes for this routine? In
   0x0076F590's pseudocode countedBytes comes from a per-type table at
   0x00B42708 and elementBytes is set per case (for case 4: elementBytes 12,
   sourceStride 16) - unverified, and 0x00B42708 has no entry in this
   export's data.json.
3. The meaning of sourceWords: the decompiled caller writes the same value
   it uses as the routine-table column (`param_6`) into +0x04 (unverified).
   Whether that always equals elementBytes / 4 decides whether the indexed
   source step equals the element size.
4. Does `_memcpy` 0x009812C0 handle overlapping buffers like memmove? Only
   relevant if overlapping streams exist (Claim 17).
5. The 9 bytes 0x0076E687-0x0076E68F between Ghidra's two body ranges are
   not in the export; presumably alignment padding (unverified).

Callees worth their own slice: none inside this function (only CRT
`memset`/`memcpy`). Worth their own slice around it: the copier 0x0076F590
(builds the descriptor, picks the routine, gates on the source), the table
filler 0x00771300, the sibling routines 0x0076E430 and 0x0076E4B0 (the other
two entries for formats 1-4) and the converter 0x0076F3B0 (Claim 22).
