## Purpose

Classifies how the character proxy is supported along a given direction and
writes the result into a surface-info record (read, the whole body):

1. Havok timer begin "TtcheckSupport" with RDTSC (0x008AE117-0x008AE14D).
2. 0x008AD070(this, collector) - the only call that receives the collector
   (0x008AE153-0x008AE159). Not followed here; it is the only candidate for a
   world query in this function (see group c).
3. Three arrays allocated on the thread's Havok stack memory: constraints A
   (0x40-byte entries, capacity `[this+0x64] + [this+0x78] + 10`), plane
   interactions B and saved velocities C (0x10-byte entries each, capacity
   `[this+0x64] + A.size`) (0x008AE15E-0x008AE320).
4. For each manifold entry i (`[this+0x74]`, stride 0x30, count `[this+0x78]`):
   virtual `this->vtbl[+0xC](&manifold[i], &A[i], 0)` then
   0x008AC3C0(index i in EAX, &A in EDI, `[this+0xA4]`, `&this+0x40`)
   (0x008AE1E3-0x008AE236).
5. A solver input built on the stack: position 0, velocity = direction, max
   surface velocity = splat `[this+0x68]`, up = `[this+0x40]`, two time
   steps 0x3C888889 (1/60 s as float, derived from the bit pattern), constraint
   pointer = A.data, count = A.size (0x008AE320-0x008AE3A8).
6. Every listener `[this+0x80][i]`, i from `[this+0x84]-1` down to 0, gets
   `vtbl[+0x4](&this->manifold (this+0x74), &input)` (0x008AE3B1-0x008AE3C9).
7. A, B, C grown to the (possibly listener-changed) constraint count, each
   constraint's velocity (+0x10) copied to C and zeroed in A
   (0x008AE3D6-0x008AE4AA).
8. 0x008EC790(&input, &output) - the simplex solve (name derived, see Claims)
   (0x008AE4AC-0x008AE4B9).
9. Surface normal (+0x10) and velocity (+0x20) of the out record set to 0; the
   support state at +0x00 decided from output velocity against direction and
   `[this+0xA4]`; when not 0, the planes of touched constraints that face the
   direction (plane . direction < -0.08) are summed into the normal (then
   normalised) and their saved velocities into the velocity (then averaged)
   (0x008AE4BE-0x008AE74D).
10. Havok timer end "Et" with RDTSC; the three stack arrays released in reverse
    order, heap-freed when they grew (0x008AE753-0x008AE884).

Clock: it reads RDTSC twice (0x008AE13D, 0x008AE781), only when the monitor
stream has room, and writes the low dword into that stream only (read). It
reads and writes no game-clock global (read: the data refs in meta.json are
the TLS index, the allocator fallback, four float constants and two strings).

## Read-and-write map (the manifest's five groups)

**(a) Own object (`this` = the proxy, and what it points to)**
- Reads `this` +0x00, +0x40, +0x64, +0x68, +0x74, +0x78, +0x80, +0x84, +0xA4 (read, table above).
- No direct write to `this` (read: every `[ESI+x]` access with ESI = this, 0x008AE15E-0x008AE54D, is a load; ESI is reassigned at 0x008AE62D).
- Passes `this+0x74` (the manifold) non-const to every listener (read, 0x008AE3B1/0x008AE3C4); whether a listener writes it: unverified (not followed).
- Writes the caller's out record (parameter 2) +0x00, +0x10, +0x20 (read). In the caller this is `controller+0x260` (re/functions/0x008AE890.md, in progress).
- Hands the caller's collector to 0x008AD070 (read); what is written into it: unverified (not followed).

**(b) Other actors / references**
- None touched by this function's own instructions (read: no access outside this, the parameters, the TLS block, the allocator, locals).
- Reached only through callees: the manifold entries (`this->vtbl+0xC` reads them, they describe other bodies - unverified), the listeners (unverified), 0x008AD070 (unverified).

**(c) Havok world, bodies, phantoms**
- No world query in this function's own instructions (read: no world/phantom pointer loaded; the only world-shaped input is the collector).
- The only candidate is 0x008AD070, which receives `this` and the collector (read, 0x008AE153-0x008AE159); that it queries the world (closest points of the phantom into the collector, then a manifold update): unverified, not followed. This is the answer the slice question "what world queries it makes" needs, and it lies one level down.

**(d) Globals, singletons, shared lists**
- `[0x00BA9DE4]` TLS index (xOBSE `kTlsIndex`, re/symbols/xobse.csv; read 0x008AE117, 0x008AE164, 0x008AE75A), with `FS:[0x2C]`.
- TLS block +0x19C read; +0x1A4 read and written; +0x1A8 read (per thread).
- `[0x00BA7D9C]` fallback allocator, read when TLS +0x19C is null (0x008AE191, 0x008AE299, 0x008AE2FB, 0x008AE7A5, 0x008AE7CB, 0x008AE7F4, 0x008AE81A, 0x008AE843, 0x008AE869). Through it the shared allocator's +0x20 is written (bump and reset). File value 0 (data.json): set at run time.
- Read-only constants (data.json): `0x00A372D0` four dwords 0x7FFFFFFF (abs mask), `0x00A37080` 0.001f, `0x00A2F948` 1.0f, `0x00A97C9C` -0.08f; immediates 0x3C888889 (x2), 0x40400000 (3.0f), 0x3F000000 (0.5f), 0x3A83126F (0.001f).
- Strings `0x00A97CA0` "TtcheckSupport", `0x00A9610C` "Et" (stored as pointers in the monitor stream).

**(e) Heap**
- Three stack allocations from the allocator (bump at +0x20, slow path `vtbl+0xC` at 0x008AE1B7/0x008AE2BD/0x008AE31D).
- Up to four grows by 0x008A6E40 (0x008AE268, 0x008AE3F2, 0x008AE425, 0x008AE458); whether it allocates from the heap: unverified (not followed); that it clears capacity bit 31 when it moves the buffer is derived only from the release path testing that bit.
- Releases: stack reset (+0x20) with `vtbl+0x10` when the base equals +0x28; heap free 0x008A75D0 with 0x14 when bit 31 is clear.

## Claims

1. **read** - `this` in ECX (0x008AE115), three stack arguments, `RET 0xC` (0x008AE88A).
2. **read** - The function writes the TLS monitor stream twice with RDTSC (0x008AE13D, 0x008AE781), each only when +0x1A4 < +0x1A8; nothing in the function reads the stored TSC back.
3. **read** - The begin marker compares through the TLS block loaded at 0x008AE11D and writes through EDI = that block; the end marker compares through a fresh load (0x008AE760) but writes through the block saved at F+0x2C (0x008AE76F). **derived** - on one thread both are the same block.
4. **read** - Constraint array capacity = `[this+0x64] + [this+0x78] + 10`, bytes requested `((n << 6) + 0x10) & ~0xF` (0x008AE16A, 0x008AE19C-0x008AE1A2); B and C capacity `[this+0x64] + A.size`, bytes `(n+1)*16` (0x008AE274-0x008AE2A8, 0x008AE2D8-0x008AE30A).
5. **derived** (from claim 4 and 0x008AE240-0x008AE255) - the user-plane reserve (rows 6-8) is not taken when `[this+0x64]` and A.size are unchanged between 0x008AE15E and 0x008AE240, because cap - size = userPlanes + 10 then. That condition is not guaranteed: **read** - 0x008AC3C0 receives the A header in EDI (`LEA EDI,[ESP+0x24]` at 0x008AE20C with two pushes pending = F+0x1C), and A.size is re-read from memory after each call (0x008AE217) and before the reserve test (0x008AE238). **unverified** - per re/export/rea-all/functions/0x8ac3c0.c (pseudocode, a reading aid only) 0x008AC3C0 appends a max-slope plane to A (size + 1, grow via 0x008A6EE0 when full). If so, cap - size = userPlanes + 10 - appended, and the reserve is taken when more than 10 slope planes were appended, or when `this->vtbl+0xC` or 0x008AC3C0 change `[this+0x64]`. Settled by reading 0x008AC3C0's instructions.
6. **read** - The extraction loop bound re-reads `[this+0x78]` each iteration (0x008AE21F). **read** - A.size is not written by this function's own instructions in the extraction loop; it is re-read from the header at 0x008AE217 and 0x008AE238. **unverified** - 0x008AC3C0 gets the header (0x008AE20C) and may change A.size (see claim 5); settled by reading 0x008AC3C0's instructions.
7. **read** - Solver input constraint pointer F+0xA8 (input +0x48) is written once (0x008AE327) and output plane-interaction pointer F+0xD4 (output +0x24) once (0x008AE3A8), both before the listeners and before the grows at 0x008AE3F2/0x008AE425/0x008AE458; the save loop (0x008AE480) and the touched loop (0x008AE625) reload the data pointers from the array headers. **read** - every listener receives the input by address (`LEA EAX,[ESP+0x60]` at 0x008AE3BF); the output is not passed. **derived** (from these reads) - each pointer can be stale only when its own array is grown: A when the count exceeds `[this+0x64] + [this+0x78] + 10` (0x008AE16A), B when it exceeds `[this+0x64] + A.size` (0x008AE2E5), and in either case only if 0x008A6E40 actually moves the buffer (unverified, not followed). F+0xD4 is then certainly not refreshed. F+0xA8 is stale only when a listener raises input.count without repointing input.constraints itself; if the listener repoints it, the solver reads the listener's buffer while the save loop writes the grown A. Whether any listener raises the count or repoints the pointer: unverified (listeners not followed).
