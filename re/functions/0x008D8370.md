## Purpose

For each entry of an array of 8-byte pairs (two broad-phase handle pointers), asks a filter object
whether the two owners may collide, and when it says yes, hands the pair to an agent-factory object
picked from a table in `this` by the two handles' type bytes, through that object's vt+0x08 (R for
the mechanics, 0x008D8390-0x008D83D0; "filter", "agent factory" and "create agent" are proposals, D
from the shape of the calls and from the sibling 0x008D83E0 calling vt+0x0C on the same table for
removed pairs, which 0x008DE950 passes as the "removed" array - re/functions/0x008DE950.md, in progress).
That vt+0x08 means "add" rather than some other per-pair action, and that `this` is a dispatcher, is U:
the export carries no strings, data refs, RTTI or direct callees (meta.json), the sibling 0x008D83E0 is
not in this export, and 0x008DE950.md is in progress. The shape also matches Havok's typed broad-phase
dispatcher `addPairs(pairs, numPairs, filter)` with an 8x8 handler table and handle bytes m_type +4 /
m_ownerOffset +5, but that is recall and could not be verified here (U). What settles it: the 0x008DE950
call site showing which broad-phase output array it passes, plus the vtable contents of one table entry,
where slot +0x08 against +0x0C shows the add/remove roles.
It does no allocation, takes no lock and reads no clock of its own (R: the body has no other call, no
RDTSC, no fixed-address access).

## Could two threads run this at once for two different phantoms?

This body itself holds no shared write: it touches only registers and its own and its caller's stack
(R, claim 8), so two concurrent runs of the body alone do not conflict (D). What stands against running
it concurrently is entirely in its callees and caller: (1) the agent object's vt+0x08 creates and
registers collision agents and pairs in tables shared by the world (Up/U); both phantoms' new pairs can
name the same other body, so both threads may touch that body's agent or overlap lists; strictly, the
filter vt+0x00 may write too (U); (2) the caller 0x008DE950 reaches it inside a world lock counter
`[world+0x88]` that is incremented and decremented without LOCK (0x008DE950.md claim 11, in progress);
(3) the body reads the pair array and the handles' bytes without a lock (R 0x008D8390-0x008D83BC).
Verdict: not shown safe. The body itself is thread-safe (D, claim 8). Concurrent use depends on the
unverified writes of agent vt+0x08 (and, strictly, filter vt+0x00) and on the caller's non-atomic lock
counter (in progress) - D/U. Reached through 0x008DE950 it is not safe if that caller's `[world+0x88]`
gate and counter are confirmed non-atomic (D from read instructions in 0x008DE950, in progress); safety
under the other eight callers is U. What settles it: the reached table entries' vt+0x08 (and the filter's
vt+0x00) read for shared writes, and the finished 0x008DE950 lock reading.
