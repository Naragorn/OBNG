## Purpose

Applies one shader constant map against one shader program for one draw
(one partition of one pass): it remembers the program in the map, looks up the
geometry's `__NDL_SCMData` extra data once, then walks the map's entry
pointer array in index order and hands each live entry to the handler its
type nibble selects. Two kinds of entries are uploaded directly to the D3D9
device from here; all others go to a virtual slot of the map class, whose
implementation differs for the vertex and the pixel map.

## Calling convention and parameters

`__thiscall`, eleven 4-byte stack arguments, callee cleans: `RET 0x2C` at
0x009A903A (read). ECX = `this` (the map), moved to ESI at 0x009A8E39 and kept
there to the end (read). Frame: `SUB ESP,8; PUSH EBP; PUSH ESI` (0x009A8E30..
0x009A8E38), then `PUSH EBX; PUSH EDI` before the loop (0x009A8E66, 0x009A8E6B).
With ESP0 = ESP at entry: index at [ESP0-8] (zeroed 0x009A8E5C), extra-data
pointer at [ESP0-4] (stored 0x009A8E52), result flag in the **arg1 slot**
[ESP0+4] (set to 1 at 0x009A8E48; arg1 itself is kept in EBP). Inside the loop
the arg10 slot [ESP0+0x28] is reused for the entry's register (0x009A8E8E) and
the arg9 slot [ESP0+0x24] for `[entry+0x30]` (0x009A8ED7 / 0x009A8F0D). The
type-0x10000000 sub-gate 1/2 paths push both scratch values to the device:
0x009A8EDB -> push 0x009A8EE7 and 0x009A8EE8 -> push 0x009A8EEC (sub-gate 1),
0x009A8F11 -> push 0x009A8F1D and 0x009A8F1E -> push 0x009A8F22 (sub-gate 2);
that is how `[entry+0x30]` and `[entry+0x1C]` reach the device as pConstantData
and StartRegister (read). Once the scratch is written, nothing reads those
slots as the original a9/a10: every slot call takes a9 from EBX (loaded
0x009A8E67) and a10 from EDI (loaded 0x009A8E6C) (read).

Returns in EAX (0x009A902C..0x009A9033): `flag == 0`, i.e. **0 when every
dispatched entry returned 0, 1 when any entry failed or had an unknown type**.
pseudo.c agrees (`return !bVar2`). SetupShaderPrograms discards it
(0x0077A1F0.md C13).

## Claims

- **C1 (read)** 0x009A8E30 is slot +0x40 of all three map vtables 0x00AB2A4C
  (`NiD3DShaderConstantMap`), 0x00AB2BAC (`NiD3DSCM_Vertex`) and 0x00AB297C
  (`NiD3DSCM_Pixel`) (.rdata pointer read; RTTI through COL+0x0C). It is shared
  code: whether a vertex or a pixel map runs it is decided only by which map
  object the caller passes and therefore which slots +0x54..+0x6C it reaches.
- **C2 (read)** Before the loop it stores a1 at `[this+0x20]` (0x009A8E3F) and
  calls `NiObjectNET::GetExtraData` 0x006FF9C0 with ECX = a2 (0x009A8E3B) and
  the name pointer read from 0x00B29F84 (0x009A8E42/0x009A8E47); the result is
  kept at [ESP0-4] (0x009A8E52).
- **C3 (read, with 0x009A56D0.md C11)** The "lock" is the lookup itself:
  0x006FF9C0 (`RET 4`) enters the critical section 0x00B3F600, records the
  owner thread at 0x00B3F678 and a recursion count at 0x00B3F67C,
  binary-searches the geometry's extra-data array `[obj+0x10]` / count
  `[obj+0x14]` by name, and leaves the section (0x009A56D0.md C11, read at
  instruction level in that slice). Here it runs **once per apply, not per
  entry**, and unconditionally - also when the map has no entries (B1 comes
  after the call) - (read: the call at 0x009A8E4D precedes the count test at
  0x009A8E58), **provided the name pointer `[0x00B29F84]` is non-null at run
  time**: 0x006FF9C0 tests its name argument (`CMP [ESP+4],0` at 0x006FF9C0)

  (1 628 calls) and 0x007830C0 0.07 ms (2 328 calls).
- **C18 (derived from C2, C15 and 0x0077A1F0.md B1)** a2 is passed to
  0x006FF9C0 without a null test here; SetupShaderPrograms skips its own lookup
  for a null geometry (its B1) but still forwards it to this function. A null
  a2 would reach `[obj+0x14]` inside the lookup (0x009A56D0.md C11). Whether a
  null geometry ever arrives is unverified; precondition for a rebuild.
- **C19 (read)** The base class's slots +0x50..+0x6C are all 0x00982D85,
  which pushes the encoded pointer 0x00BAA5EC, calls it if non-null and then
  calls 0x0098D5B8 with 0x19 (objdump 0x00982D85..0x00982D99). That this is
  the CRT `_purecall` (`_RT_PUREVIRT` = 25) is derived from that shape and
  unverified against a CRT symbol; it means a plain `NiD3DShaderConstantMap`
  is never applied with live entries of these types.
- **C20 (read; pseudocode disagreement)** pseudo.c shows the call as
  `FUN_006ff9c0(PTR_s___NDL_SCMData_00b29f84)` without its receiver; the
  instructions load ECX = a2 at 0x009A8E3B and 0x006FF9C0 uses ECX
  (`in_ECX` in its own pseudocode). The instructions win: the lookup is on the
  geometry. pseudo.c also hides the stack-slot reuse (flag in the arg1 slot,
  scratch in the a9/a10 slots); its argument lists for every call match the
  pushes. Ghidra's `param_N` is the stack argument N-1 here.
- **C21 (derived; per pass vs per draw)** From this body alone, the inputs that
  can differ between two applies of the same map in the same pass are the
  arguments (program a1, geometry a2, skin a3, partition a4, property state
  a6 and effect state a7 - the a6/a7 names are proposals, see the parameter
  table - plus the role-less a5, a8, a9; the pass index a10 does not change
  within a pass) and the memory the entries
  point to; the entries' gate fields (+0x08, +0x14, +0x18, +0x1C, +0x24) and
  the array are not written here (C15). Type-0x10000000 entries with
  sub-gate 1/2 upload `[entry+0x30]`, which takes no argument at all (read).
  For the defined entries, ids 1-4, 9-10, 13-16, 21-22 (P, V, V x P and their
  variants) read only the renderer's +0x980 / +0x9C0 (0x009A56D0.md Purpose
  table) (read there). That either group is a per-pass or per-binding
  candidate is **unverified**: it holds only if nothing rewrites the
  `[entry+0x30]` buffers or the renderer's +0x980 / +0x9C0 inside a pass. To
  settle it: a writer search on the `[entry+0x30]` buffers and on renderer
  +0x980 / +0x9C0 within a pass, or a probe that hashes those inputs per apply
  inside one pass, or one that records the device uploads and counts repeated
  identical (method, start, count, bytes) per pass. World-, skin-, bone-,
  material- and time-dependent ids are per draw.

## Open questions

1. Which entry types and how many entries a typical Oblivion vertex and pixel
   map holds (cheapest step: extend the pass-steps probe to count entries per
   type and per defined id at 0x009A8E9E). This decides which slot targets are
   worth mapping and how much a per-pass cache saves.
2. The meaning of `[entry+0x24]` (non-zero lets an entry with register -1
   through) and whether register -1 ever reaches a device upload (C8).
3. Whether the `[entry+0x30]` buffers of type-0x10000000 entries are ever
   rewritten at runtime (a writer search for the entry class) - if not, those
   uploads are redundant after the first per program binding.
4. What the stored `[this+0x20]` (last program) is read by - a writer/reader
   search over the slot targets.
5. Whether SetupShaderPrograms' 2 331 calls a frame against 4 564 applies is
   two maps per call minus the skipped maps (0x0077A1F0.md B3-B6) plus the
   SpeedTree path 0x0080FC20, or whether a third caller exists (an xref search
   on `[vtbl+0x40]` over the map classes).
6. Whether 0x006FF9C0 has any side effect beyond the critical-section words
   (needed for the lazy lookup in C5; read its instructions).

## Layout requests

- `NiD3DShaderConstantMap` (0x00AB2A4C; subclasses `NiD3DSCM_Vertex`
  0x00AB2BAC, `NiD3DSCM_Pixel` 0x00AB297C): +0x00 vtable; +0x10 entry pointer
  array (`entry**`, stride 4); +0x16 u16 entry count; +0x20 last applied
  program; +0x28 `IDirect3DDevice9*`. Virtual slots: +0x40 ApplyConstants
  (0x009A8E30), +0x54 defined, +0x58 constant (program path), +0x5C attribute
  (13 args), +0x60 global, +0x64 operator, +0x68 (not called here), +0x6C
  object. The type names per slot except "operator" are proposals from the
  dispatch order (unverified).
- Constant-map entry (class name unverified): +0x08 u8 live; +0x10 predefined
  id (0x009A56D0.md); +0x14 u32 type flags (high nibble: 1 constant,
  2 defined, 3 attribute, 4 global, 5 operator, 6 object - the nibble values are
  read, the names unverified); +0x18 u32 constant target (1 vertex, 2 pixel);
  +0x1C i32 start register (-1); +0x20 u32 register count; +0x24 u32 (gate,
  meaning unverified); +0x30 `const float*` data.
- For a 64-bit clean rebuild: the map, entry, program, geometry and device
  are 32-bit engine handles behind ports; the offsets above go in as
  `static_assert`ed constants in the `<Name>.h` header only.
