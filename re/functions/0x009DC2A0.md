## Purpose

The construction of the main loop's TimeInfo at 0x00B33E90 (xOBSE's
`g_timeInfo`, re/symbols/xobse.csv:1560) at startup, with the TimeInfo
constructor's body inlined and `GetTickCount()` as the start tick.

Answer to the slice question ("Is this the construction of the global
TimeInfo at startup (GetTickCount into +0x14)? What is the callee?"):

- **Yes, it writes the full constructor state into g_timeInfo** (derived, see
  claim C6): every field the constructor 0x0047D150 writes through `ECX` is
  written here at the same offset from 0x00B33E90, with the same width and the
  same value, and +0x14 receives the return value of `GetTickCount`.
- **The callee is KERNEL32 `GetTickCount`**, called indirectly through the
  import slot 0x00A280D0 at 0x009DC2A0 (read). The constructor 0x0047D150 is
  **not** called; its stores are inlined (read: the body has one call only).
- That it runs "at startup" (from the CRT's initialiser table) is
  **unverified**: meta.json lists no callers (see Open questions).
- That it is the *static initialiser* of g_timeInfo, which the name
  `StaticInit_g_timeInfo` proposes, is **unverified**. Read: it builds a
  TimeInfo at 0x00B33E90 with the same stores as 0x0047D150 and the current
  tick, which rules out reading it as a getter, an update (compare 0x0047D170)
  or a freeze. Not ruled out: a reset called later at runtime through a
  pointer, because meta.json `callers` is empty and the export has no pointer
  to 0x009DC2A0. The bare `void(void)` shape, the position next to 0x009DC2D0
  (EH frame and `_atexit`) and the empty caller list fit a CRT `_initterm`
  entry, but that is not proven. What would settle it: find 0x009DC2A0 as a
  dword (bytes `a0 c2 9d 00`) inside the .rdata `__xc_a..__xc_z` initialiser
  table, and search the whole image for references to 0x009DC2A0.

## Open questions

1. Who calls 0x009DC2A0? (C14) Cheapest step: a data export of every
   occurrence of the pointer value 0x009DC2A0 (bytes `a0 c2 9d 00`) in the
   image; if it sits in the `__xc_a..__xc_z` range that `_initterm` walks,
   C14 becomes read.
2. With +0x10 = 0 and +0x14 = the start tick after this initialiser, does the
   first update 0x0047D170 subtract +0x14 from the tick before comparing with
   +0x10, or is the first frame's delta the raw tick (and so clamped to 166 ms)?
   That is answered by 0x0047D170's mapping (in progress), not by this body.
3. +0x04 (`clampMs`) is 0 after construction: where is the iFPSClamp step
   written into g_timeInfo? Not here (read: +0x04 gets +0.0) and not in
   0x0047D150 (same store); another writer is open.
4. The three padding bytes +0x01..+0x03 are never written by either
   initialiser; does any code read them (e.g. a word or dword read of
   +0x00)? Open.

## Layout requests

For `src/engine/time/TimeInfo.h`:

- Confirms (second code path, C6/C7) offsets, widths and float-ness only: a
  1-byte `frozen` at +0x00, +0x01..+0x03 never written by construction
  (`pad[3]` proposed; padding unverified until no reader is found), `clampMs`
  m32 float at +0x04, `clampCarryMs` m32 float at +0x08, `frameSeconds` m32
  float at +0x0C, 4-byte integer stores to `lastMs` at +0x10 and `startTick`
  at +0x14. Not confirmed here: signedness (uint8/uint32) - stores of 0 or of
  a tick do not carry it; it needs the readers in 0x0047D170 or, for +0x14,
  GetTickCount's DWORD return; int vs float at +0x10 (dword 0 is also 0.0f);
  size 0x18 - "nothing written beyond +0x17" holds for these two bodies only,
  the size rests on `FormHeap_Allocate(0x18)` at 0x005AD2E7. Suggested extra
  `static_assert`s: `offsetof(TimeInfo, clampMs) == 0x04`,
  `offsetof(TimeInfo, clampCarryMs) == 0x08`, `offsetof(TimeInfo, lastMs) == 0x10`.
- `startTick` for the global instance is `GetTickCount()` at the time this
  initialiser runs (read, 0x009DC2A0/0x009DC2C8).
- New constants (proposal): `kTimeInfoStaticInit = 0x009DC2A0` (this
  function) and `kGetTickCountImportSlot = 0x00A280D0` (the import slot; read
  here and in Ghidra's import naming - a second source still to be named).
- `kTimeInfoAddress = 0x00B33E90` already rests on xOBSE; this function adds
  the binary side of that agreement (read, 0x009DC2B6).
