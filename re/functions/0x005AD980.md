## Purpose

One tick of the loading screen, callable from code that is busy loading and
therefore not running the main loop's update step (0x0040D800; the "busy
loading" context is derived from C2, not measured):

1. Find the loading menu: the tile menu for menu type 0x3EF
   (kMenuType_Loading) and its Menu object. Leave if either is null.
2. Advance the **loading menu's own TimeInfo** (the pointer at Menu+0x54)
   with `GetTickCount` through the TimeInfo update 0x0047D170. This is not
   `g_timeInfo` (0x00B33E90): the constructor 0x005AD0D0 allocates a fresh
   0x18-byte TimeInfo for the menu. The update 0x0047D170 does, however,
   overwrite the shared globals 0x00B39DB0/0x00B39DB4 on every call,
   whatever instance it runs on (C15).
3. From that clock's `lastMs` (+0x10), decide whether the loading bar
   advances one step (+0x64), and count down a timer (+0x40) by the elapsed
   milliseconds divided by the double at 0x00A2FC70 (unit of the timer
   unverified; seconds if that constant is 1000.0).
4. When the step changed, or the timer ran out, or the caller forces it,
   push the step to the menu tile as trait 0xFB1 (user3); on timer expiry
   or force call 0x005AD780 and re-arm the timer from the setting at
   0x00B14158; then, if the InterfaceManager exists, call 0x00583F40 on it,
   call the interface-pass wrapper 0x00579260(0) and 0x005792B0, between
   two calls on `g_ioManager`. Whether this produces a drawn 2D frame is
   decided inside 0x00579260, not here (C8).
5. Record the time of this call, and when running on the main thread, tail
   jump into 0x0060D0A0 on `g_osGlobals` (purpose unverified; a message pump
   is the guess).

Answer to the slice question ("why does this path update the clock outside
the update step?"): **this function's own instructions do not update
`g_timeInfo` 0x00B33E90.** They run the TimeInfo update method on a private
TimeInfo owned by the loading menu, as a stopwatch for the loading bar and
the screen timer (C1). Two limits on that answer:

- The update method itself writes the shared globals 0x00B39DB0 and
  0x00B39DB4 on every call (C15), so the loading menu's calls do leave a
  trace in frame-clock state that the main loop's update also writes. Who
  reads those globals is unknown (0x0047D170.md, open question 1).
- The callees 0x005AD780, 0x00583F40, 0x00579260, 0x005792B0, 0x00432860,
  0x00432890 and the tail target 0x0060D0A0 are not exported. Whether any of
  them reads or updates `g_timeInfo` is unverified (open question 4).

The loading situation is read (menu type 0x3EF, LoadingMenu strings in the
constructor) and corroborated by the caller TESSaveLoadGame::LoadGame
0x00465860 (xOBSE, inferred). The other five callers are not exported.

## Calling convention and parameters

- **cdecl, one stack argument, no meaningful return value.** (derived)
  - `ret` without an immediate at 0x005ADB3E: the caller cleans (read).
  - The only argument read: `CMP byte ptr [ESP+0x1C],0` at 0x005ADA3C.
    At that point ESP = entry ESP - 0x18 (SUB 8 at 0x005AD980, PUSH EBX
    0x005AD983, PUSH/ADD of the 0x3EF argument nets 0, PUSH EBP/ESI/EDI
    0x005AD9AA..AC, and the `PUSH EAX` at 0x005AD9BF is popped by
    0x0047D170, which ends in `ret 4` per OBVR FrameClock.cpp:13), so
    `[ESP+0x1C]` = `[entry ESP+4]`, the first argument, read as a byte
    (derived from the read stack arithmetic).
  - ECX is not an input: it is written (0x005AD99B) before any read (read).
  - Ghidra's meta.json signature says `FUN_005ad980()`, no parameters;
    pseudo.c says `(char param_1)`. The instructions side with pseudo.c.
  - EAX at the exit 0x005ADB3A is not a defined result: it is 0 when B1 or
    B2 exits early (`TEST EBX,EBX` / `TEST EAX,EAX` + `JZ` at
    0x005AD993/0x005AD995 and 0x005AD9A2/0x005AD9A4), and the
    GetCurrentThreadId result when B18 exits (0x005ADB1E..0x005ADB29); on
    the tail-jump path it is whatever 0x0060D0A0 returns (read for the
    first two; whether any caller uses EAX is unverified, callers not
    exported). Treated as `void`.
- Parameter 0: `bool forceRefresh` (proposed name). A nonzero byte forces
  the refresh branch and the 0x005AD780 call even when the step did not
  change and the timer has not run out (read, 0x005ADA3C..0x005ADA48).
  Whether callers push it as a full dword is unverified (callers not
  exported).
- Callee-saved registers: EBX, EBP, ESI, EDI pushed and popped (read).
- Two exits:
  - `0x005ADB3A: pop ebx; add esp,8; ret` (read).
  - Tail jump at 0x005ADB35 to 0x0060D0A0 with ECX = `[0x00B33398]`
    (g_osGlobals), after restoring ESP to the entry value (read). So
    0x0060D0A0 returns straight to this function's caller, which requires it
    to end with a plain `ret` and take no stack arguments (derived;
    0x0060D0A0's epilogue is unverified).
- Locals: `[entry-4]` is a float scratch (the timer, then the step as
  float); `[entry-5]` is the byte `refresh` (read, 0x005ADA0E..0x005ADA48,
  0x005ADA7E).

Flow notes for the rebuild:

- B3 increments without a cap; B5/B6 respect `slowStepCap`. With the
  constructor's -1 cap (0x005AD131), B5/B6 never fire until something
  raises the cap (derived; who writes +0x3C later is unverified).
- `sinceStep` is measured from `stepChangedMs`, which moves only when
  `shownStep` catches up (B12). So once `targetStep` moves ahead and the
  redraw is skipped (B11, B13), B3 keeps incrementing on every call
  (derived).
- `lastTickMs` is written on every path that reached B2's not-taken side,
  including all early tails into T1 (read).
- The rebuild's test for the B15-not-taken path can only assert that the
  wrapper 0x00579260 is called with 0; it cannot assert that a frame is
  drawn, because that depends on state outside this function (C8).

## Open questions

1. Values of the constants 0x00A2FC78 (float), 0x00A2FC70 (double) and
   0x00A6C4C8 (double). Expected 2^32, 1000.0 and something at or below 100;
   unverified, the export carries no data bytes. 0x00A2FC70 decides the
   unit of `screenTimeLeft` (+0x40) and of the setting 0x00B14158 (seconds
   only if it is 1000.0). Cheapest step: export the bytes at those three
   addresses.
2. Names of the settings at 0x00B14158, 0x00B14160, 0x00B14168, 0x00B14170
   (the name pointers at +4 of each). Same export step.
3. Who calls this, on which thread, and with which `forceRefresh`? Callers
   0x00578E00, 0x005ADB40, 0x00462B20, 0x0057E150, 0x005ADEC0, 0x00465860
   are not exported. The `mainThreadID` check at 0x005ADB25 suggests the
   function expects to run on more than one thread (derived: the branch
   would be pointless otherwise; unverified by callers). Whether a call
   actually yields a 2D frame depends on 0x00579260's guards (C8): per OBVR
   GameAddresses.h:1289-1307 the pass is skipped while the loading-thread
   handle 0x00B33434 names a live thread, on whatever thread the wrapper
   runs. So the earlier reading "the 2D pass is driven from a second
   thread" is not supported; the open question is whether, during a load,
   any call of this function finds the loading thread finished and so
   draws. Cheapest step: export 0x00579260, 0x0040FDA0 and the six callers.
4. What 0x005AD780 does on a forced or expired refresh (next loading

## Layout requests

For `src/engine/time/TimeInfo.h` (the slice's shared header):

- `TimeInfo` is instantiated more than once: the global at 0x00B33E90 and
  one per LoadingMenu (heap, 0x18 bytes, constructor 0x0047D150 taking the
  start tick). The header should model it as a type, not only as the global.

  them as `g_timeInfo`-only state.
