## Purpose

Leaves one level of the clock freeze. The byte at +0x00 is a nesting
counter: this function decrements it when it is nonzero, and when the
decrement reaches zero it reads `GetTickCount` once and rewrites +0x10 and
+0x14 as `now - field`. The first half 0x0047D120 applies the same
`now - field` transform on the 0 -> 1 transition, so across one outermost
bracket both fields come out shifted forward by the frozen stretch
D = t_unfreeze - t_freeze (mod 2^32). It does not touch +0x04, +0x08 or
+0x0C, and it does not "only clear a flag".

## Claims

1. **+0x00 is a byte nesting counter, not a boolean** (derived): this
   function decrements it by 1 (0x0047D0F9) and acts only when it reaches
   0 (0x0047D0FD); the first half 0x0047D120 increments it by 1 (`ADD
   CL,0x1` at 0x0047D127) and acts only when it was 0 (`JNZ` at
   0x0047D12E). Read in both bodies.
2. **The decrement is guarded at zero** (read, 0x0047D0F5/0x0047D0F7): an
   unbalanced extra call leaves the counter at 0 and writes nothing.
3. **Only the outermost call reads the clock** (read): `GetTickCount` at
   0x0047D0FF is reached only on F3.
4. **When the counter reaches 0, +0x10 := now - +0x10 and +0x14 := now -
   +0x14** (read, 0x0047D105..0x0047D110; pseudo.c agrees).
5. **Across one outermost bracket, +0x10 and +0x14 are both shifted forward
   by D = t_unfreeze - t_freeze (mod 2^32)** (derived from claim 4 and
   0x0047D120's identical transform at 0x0047D136..0x0047D141:
   t2 - (t1 - x) = x + (t2 - t1)). Emulator: start 1000, last 500, freeze
   at 1510, unfreeze at 3510 gives +0x14 = 3000 and +0x10 = 2500.
6. **The answer to the slice question: it restores both +0x10 and +0x14,
   and the shift of +0x14 removes the frozen stretch from the update's
   milliseconds-since-start** (derived from claim 5 and 0x0047D170's
   `SUB EDX,[ECX+0x14]` at 0x0047D176: ms = tick - startTick, which drops
   by D).
7. **The shift of +0x10 over-corrects in variable mode** (derived from
   claim 5 and 0x0047D170: variable mode takes ms - +0x10 at 0x0047D1F3 and
   stores ms into +0x10 at 0x0047D23E, so +0x10 is a value relative to
   +0x14, not an absolute tick). With a = time from the last update to the
   freeze, b = time from the unfreeze to the next update, the first
   update after the bracket computes (a + D + b) - 2D = a + b - D instead
   of a + b. Consequences, when variable mode (+0x04 == 0) and
   multiplier 1.0:
   - when a + b > D, the frame reads as min(a + b - D, 166) ms - shorter
     than the time actually not frozen: a positive value above the ceiling
     kFrameCeilingMs 0x00A3D14C (166.66667f) is replaced by 0xA6 = 166 as
     well (`FCOMP` / `TEST AH,0x41` / `MOV ESI,0xA6` at
     0x0047D213..0x0047D220). The ms count is then scaled by 0x00A30E40
     (f64 0.0010000000474974513, `FMUL` at 0x0047D238) and by
     fGlobalTimeMultiplier 0x00B06704 (`FMUL` at 0x0047D247) before it lands
     in +0x0C. The formula holds only when the last update before the freeze
     ran with counter +0x00 == 0 and took the variable path (so +0x10 was set
     to ms at 0x0047D23E, not to the fixed-path sum built at 0x0047D1E6), no
     update ran inside the bracket, and the bracket is a single outermost
     pair on the same instance between two updates (each further bracket
     subtracts its own D) (derived from the reads named here);
   - when a + b == D, the zero test at 0x0047D1F6 makes it 1 ms;
   - when a + b < D, the 32-bit difference is negative, the `JGE` at
     0x0047D20B falls through to the 2^32 fix-up and the value compares
     above the ceiling 166.66667f (0x00A3D14C), so it reads as 0xA6 =
     166 ms - the same as with no bracket at all for any D above the
     ceiling.
   Emulator, chained 0x0047D120 -> 0x0047D0F0 -> 0x0047D170 on one
   instance: a = 10, D = 5, b = 10 gives +0x0C = 0.015f (no bracket:
   0.025f); a = 10, D = 2000, b = 10 gives 0.166f (no bracket: 0.166f).
   Whether this is the designers' intent is unverified.
8. **In fixed-step mode the +0x10 shift has no effect on the seconds**
   (derived from 0x0047D170: when +0x04 != 0 the path 0x0047D19F..0x0047D1EE
   recomputes EDX from +0x10 + the rounded step and the seconds from +0x04;
   ms - +0x10 is not computed). The +0x14 shift still changes the value
   written to g_currentTickMs 0x00B39DB0 at 0x0047D186.
9. **While the counter is nonzero, +0x14 does not hold the start tick**
   (derived from 0x0047D120 at 0x0047D13B/0x0047D141): it holds t_freeze -
   startTick, so an update that runs inside the bracket writes
   tick - (t_freeze - startTick) to g_currentTickMs 0x00B39DB0 (0x0047D176,
   0x0047D186) - not the milliseconds since start. Whether any update runs
   inside a bracket in the game is unverified.
10. **Nothing outside +0x00, +0x10, +0x14 is written; +0x0C is not reset**
    (read: the only stores are 0x0047D0FB, 0x0047D10D, 0x0047D110).
11. **Callers** (read, meta.json; instruction addresses read in the
    callers' asm.s under re/export/frame-clock/): TESObjectREFR::LoadBaseFormModels
    0x004E1580 (MOV ECX / CALL: `MOV ECX,0xB33E90` at 0x004E18C1, `CALL
    0x0047D0F0` at 0x004E18C6) and GameMessageBoxA 0x004949E0 (MOV ECX /
    CALL: `MOV ECX,0xB33E90` at 0x00494E59, `CALL 0x0047D0F0` at
    0x00494E5E), both with ECX = 0x00B33E90 (re/functions/0x004E1580.md, re/functions/0x004949E0.md
    - in progress). Two further call sites 0x00406169 / 0x004061AA lie in

    calls).
12. **pseudo.c agrees with the instructions** (read): same condition order,
    same `now - field` transform, same offsets. The only difference is
    typing (`char *` for `this`), which does not change behaviour.

## Answers to the slice questions

- *Does it restore +0x10 or +0x14 so the frozen stretch does not count as
  a frame, or does it only clear the flag?* It rewrites both, and only on
  the outermost unfreeze (claims 3-5). Combined with the first half, both
  fields move forward by the frozen stretch. The +0x14 shift removes the
  stretch from the update's milliseconds; the +0x10 shift removes it a
  second time, so in variable mode the first update after a short bracket
  reads as min(a + b - D, 166) ms (values above kFrameCeilingMs 0x00A3D14C,
  166.66667f, are replaced by 0xA6 = 166 at 0x0047D213..0x0047D220), and
  after a bracket longer than the surrounding frame time it reads as the
  166 ms ceiling. This holds under the conditions listed in claim 7: the
  last update before the freeze took the variable path with counter 0
  (+0x10 set to ms at 0x0047D23E), no update ran inside the bracket, and
  the bracket is a single outermost pair on the same instance; +0x0C is
  then scaled by fGlobalTimeMultiplier 0x00B06704 at 0x0047D247 (claim 7,
  derived, emulator run on the exported bytes).

## Open questions

1. Is the double subtraction (claim 7) intended? Only the game can show
   what a message box or a model load does to the next frame's seconds;
   an in-game differential check would settle it (unverified).
2. Does any TimeInfo update run on `g_timeInfo` while the counter is
   nonzero (e.g. inside GameMessageBoxA's message loop)? If it does, claim
   9's g_currentTickMs value is live; nothing here shows it (unverified).
3. Which halves do 0x00406169 and 0x004061AA call, and do they balance?
   An unbalanced unfreeze is absorbed (claim 2); an unbalanced freeze
   would leave the clock frozen (derived from claim 1), and 0x0047D120
   does not guard the byte against wrapping past 0xFF (its export).
4. Do the callers read EAX after the call? (unverified; not checked at
   0x004E18C6 / 0x00494E5E.)
5. knowledge/frame-clock.md states "frozen writes 0.0f and leaves +0x10
   alone (so the next unfrozen frame sees the whole frozen stretch,
   clamped)". That holds for the update alone; with this bracket the next
   frame sees a + b - D or the ceiling (claim 7). The knowledge file and
   OBVR's `src/game/FrameClockLogic.h` (which carries the same layout
   reading) should pick this up; not edited from here.

## Layout requests

- +0x10 and +0x14: note that while `freezeDepth != 0` both hold
  `t_freeze - value` (elapsed form), and that the outermost unfreeze turns
  them back shifted by the frozen stretch (claims 5, 9).

  replace "bodies not yet mapped" for this entry.
- `kGetTickCountIatSlot = 0x00A280D0` if the rebuild routes the tick
  source through a seam (read, 0x0047D0FF); both halves of the bracket use
  the same slot.
