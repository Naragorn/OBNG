## Purpose

It draws one geometry as a whole (no skin partitions) with a shader, pass by pass. It reads
no clock and touches no global variable. In instruction order:

1. **Shader choice** (0x007672F7-0x00767319): when a1 (geometry) is non-null, cast
   `[a1+0xBC]` to `NiD3DShaderInterface` (0x00560920 with RTTI 0x00B42858); when a1 is null
   or the cast fails, use the renderer's default shader `this+0xA94`.
2. **Pipeline open**: shader slot 10 (+0x28); a non-zero result returns at once. Then slot 11
   (+0x2C).
3. **Pass loop**: slot 18 (+0x48) opens the first pass, slot 19 (+0x4C) the next. Per pass,
   once (there is no inner partition loop): slot 12 (+0x30), slot 13 (+0x34), slot 15 (+0x3C,
   returns the buffer record), slot 14 (+0x38), the slot-1 call on `[[this+0x8AC]+0xFF0]`,
   then the device draw(s), then slot 16 (+0x40).
4. **Draw**: when `record+0x30` (the index buffer, re/functions/0x00763130.md) is non-zero,
   one `IDirect3DDevice9::DrawIndexedPrimitive` (slot 82) per entry of the record's array
   (`record+0x44` entries); when it is zero, one `IDirect3DDevice9::DrawPrimitive` (slot 81).
5. **Pipeline close**: slot 17 (+0x44), then `[this+0x8AC]` slot +0xFC with 0.

Compared with DrawSkinnedPrimitive 0x00767520 (re/functions/0x00767520.md), the shader slot
sequence per pass is the same (12, 13, 15, 14, the +0xFF0 slot-1 call, draw, 16), with the
partition argument 0 in slots 13, 15, 14 and 16, and the buffer record from a6 instead of
`partition+0x28`. What 0x00767520 does and this function does not: the null-skin early
return, the bone gate, the world-bound copy to this+0x658, the per-pass flags clear of
`data+0x2E`, the null test of slot 15's result. What this function does and 0x00767520 does
not: the DrawPrimitive arm, and the primitive type and vertex count taken from the record
(+0x38, +0x14) instead of the partition.

### The eye question: what a second draw would need to redo

- **E1 read**: between the return of the `[[this+0x8AC]+0xFF0]` slot-1 call (0x0076740E) and
  the draw call (0x00767462 indexed, 0x007674A1 non-indexed) the body reads `record+0x30`,
  `+0x44`, `+0x48`, `+0x3C`, `+0x14`, `+0x34`, `+0x38`, `this+0x280`, the device vtable entry
  (`+0x148` / `+0x144`) and the u16 lengths array `[record+0x48][i]` (0x00767433). Between the
  draw and slot 16 (0x007674C5): the start/index arithmetic and the loop test
  (0x00767464-0x00767484), then the argument setup for slot 16 (0x007674A3-0x007674C3, loads
  and pushes only); on the DrawPrimitive arm 0x007674A3-0x007674C3 is the whole window.
  No call, no store to a non-stack address in either window.
- **E2 derived** (E1, C1): inside this body, a second draw with identical arguments right after
  the first needs nothing from this body re-run: the bound streams and index buffer (slot 15),
  the shader programs (slot 14) and whatever the slot-1 call commits stay as they are. Slot 16
  (0x007674C5) runs once per pass, after that pass's draws; slot 17 (0x007674F8) and
  `[[this+0x8AC]]+0xFC(0)` (0x0076750C) run once per call, after the pass loop ends (exit at
  0x007674D2), not once per pass (read). What the three do is **unverified** (their targets
  are not read).
  This body sets no eye-dependent state itself: no SetViewport, no constant upload, no clip
  plane (C1).
- **E3 derived** (C6 + 0x007C9230.md C14, C15 and its struct rows +0x980/+0x9C0): for the
  shaders whose slot 13 is 0x007C9230, slot 13 reads renderer+0x980/+0x9C0 (read there) and
  calls 0x00765480 with the world transform. 0x007C9230.md marks +0x980/+0x9C0 as
  view/projection only **unverified**. Its clip-plane device calls (`[[device]]+0xDC`,
  SetClipPlane by the header count above) run only in passes 0x177..0x17A, and the matrices are
  read there only on a cache miss: on a hit (C15 there, cache at L+0x214) the planes come from
  L+0x1B4, so a second eye could get stale planes unless L+0x214 is cleared (derived from
  0x007C9230.md C15). Slot 14 (0x0077A1F0, step 3) may also carry view-dependent constants
  (unverified). A constant upload in slot 13 is not shown. That a second eye's draw needs
  "SetViewport" and "the upload of the view-dependent constant entries" is a premise of the
  stereo design (a render-target switch is the alternative), **unverified**: no read fact here
  shows it. Whether view-dependent uploads reach the device directly or through a deferred
  buffer that the `[[this+0x8AC]+0xFF0]` slot-1 call commits is **unverified**; if the latter,
  the slot-1 call must run again before the second draw. Slot 16/17 and +0xFC do not need to
  run twice (E2), unless one of them resets state the second draw relies on (unverified, their
  targets are not read).
- **E4 derived** (C4, B8): with an index buffer and several array entries, the draw is a loop
  of DIPs; a per-DIP eye switch would flip constants and viewport `arrayCount` times. Running
  the whole DIP loop (0x00767428-0x0076747E) once per eye, with the start index reset, needs
  one switch per eye per pass.

## Where pseudo.c disagrees with the instructions

- Slot 11 (0x0076736D): pseudo.c passes `unaff_ESI`, `unaff_EBP`, `unaff_EBX`; the pushes are
  (a1, a3, a6, this+0xC, this+0x10, a4, a5), the same as slot 10. The instructions win.
- Slots 12, 13, 14, 16, 17 (0x007673A0, 0x007673C4, 0x007673FB, 0x007674C5, 0x007674F8):
  pseudo.c shuffles the arguments (e.g. slot 13 `(param_2, unaff_ESI, 0, param_7, ...)`; slot
  17's last two pseudo.c arguments are `iVar11, uVar12`, where the pushes give a4, a5). The instructions give
  slot 13 = (a1, a3, 0, ESI, this+0xC, this+0x10, a4, a5); the table above is from the pushes.
- pseudo.c shows a1 (`param_2`) overwritten in the DIP loop; in the instructions EBP is
  overwritten and restored from the unchanged stack slot at 0x00767480.
