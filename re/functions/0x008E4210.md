## Purpose

It compares the node's new integer bounds on this axis (newMin, newMax) with the stored values of the neighbouring
endpoints (0x008E422A, 0x008E4305, 0x008E43DF, 0x008E44BE - not with the node's own stored positions); only when a new
value crosses a neighbour's value does it bubble the node's min or max endpoint through the sorted endpoint array
[arg1+0x64], one neighbour at a time (insertion-sort step), and
- fixes up the neighbour's stored endpoint position (node +0x02 or +0x06) for every endpoint it passes,
- when it passes an endpoint of the opposite kind and the two nodes' positions on the two other axes overlap, appends
  the pair (own handle, other handle) to the "begun overlaps" array (arg7) or the "ended overlaps" array (arg8).

It **is** broad-phase code and it **writes broad-phase state**: the endpoint array of this axis, the moving node and
every neighbour node it passes (read, 0x008E4246.. see Struct accesses). It reads and writes no global, no TLS slot and no
clock (read: no absolute memory operand, no FS: access, no RDTSC in asm.s; data.json empty).

Note on the overlap test: it compares the nodes' stored **positions** (endpoint indices) on the two other axes, not
coordinates, as 16-bit differences ORed together; `TEST AH,AH / JS` rejects when any difference has bit 15 set
(read, e.g. 0x008E424F-0x008E4281). Derived: the test is guaranteed to equal an interval-overlap test while every
stored position is below 0x8000. With more endpoints it misjudges only those pairs whose position difference on
another axis reaches 0x8000 or more; it is not wrong in general.

## Claims

1. The function updates one axis (endpoint array [arg1+0x64]) of a sort-and-sweep broad phase for one node - **read**
   (the four insertion loops, 0x008E4235-0x008E456A) for the mechanism; "third of three axes" **derived** from the
   sibling per-axis functions 0x008E3C30 (+0x4C) and 0x008E3E90 (+0x58) called next to it by 0x008E4590 (pseudocode).
2. It writes broad-phase state shared by all nodes: the endpoint array and the neighbour nodes' stored positions -
   **read** (write addresses in group (c)).
3. Begun overlaps go to arg7 (L1, L2), ended overlaps to arg8 (L3, L4) - **read** for which array; "begun/ended"
   **derived** from the direction of the move (a min passing below another node's max, or a max passing above its min,
   starts an overlap on this axis).
4. When L2/L3 run before L4, the max endpoint is placed before the min moves up, so the min never passes its own max
   in L4 - **derived** from the loop order (read) and the bounds newMin <= newMax (**unverified**: no check here).
5. No bounds check on the endpoint array: termination relies on sentinel endpoints at both ends - **derived** (read: no
   index compare against a size); the sentinels themselves are **unverified**.
6. No global, TLS, lock or clock is touched in this body - **read**.
7. Pseudocode and asm agree on every path I checked; pseudo.c loop 1 reads `puVar3[-4]` before stepping the pointer
   where asm steps EBX first and reads [EBX-4] (0x008E42CC/0x008E42D3) - the same address (**read**).
8. Positions are compared as signed 16-bit differences; the test is guaranteed correct while every stored position is
   below 0x8000, and with more endpoints it misjudges only pairs whose position difference on another axis reaches
   0x8000 or more - **derived** from 0x008E424F-0x008E4281.
9. No intended return value (EAX = leftover endpoint pointer: EBX+4 from 0x008E4567 at the RET 0x008E457E, EDI+4 from
   0x008E44B9 at the RET 0x008E458A - **read**); void is **unverified** until 0x008E4590's asm shows the caller ignores
   EAX.

## Could two threads run this at once for two different phantoms?

No, not on the same broad phase. Against it (read): every call writes the shared endpoint array of the axis
(13 write sites) and the stored positions of every neighbour node it passes (8 write sites); two moving nodes whose
endpoint ranges touch would corrupt the sorted order and each other's positions. In addition, if the caller shares
arg7/arg8 between the nodes it updates, their size field is written unlocked (unverified who owns them), and the grow
path goes into an allocator through 0x008A6EE0 whose thread memory selection is unverified. Nothing in this body takes
a lock. Derived: this belongs on the main thread (or behind one broad-phase lock) - consistent with the slice's plan to
keep the broad phase's updates on the main thread. It does not read the controller or phantom directly, so it does not
by itself stand in the way of running narrow-phase work in parallel as long as no worker moves a broad-phase AABB.
