## Purpose

For every point of the proxy's contact manifold (`[this+0x74]`, count `[this+0x78]`, 0x30-byte
entries), it (1) looks up property key 0x1300 on the touched object's owner and, when present,
hands the property's value to every listener's vt+0x10; (2) when the touched object is an entity
(collidable type byte == 1) whose byte +0x92 is 0, computes a push impulse along the contact
normal from the relative point velocity, a penetration term, an effective-mass division, a clamp
and a gravity term, hands position/normal/impulse to every listener's vt+0x14, wakes the body
(0x008A6410) and applies the impulse directly through the body's motion vt+0x60. R for each step
at the addresses in Control flow.

It writes no global, no TLS slot and no heap block in its own body: every store is to its own
stack (R: all stores are `[ESP+..]` or through EDX/ECX/EAX loaded by `LEA ..,[ESP+..]`,
0x008AC6BE-0x008ACAA9, the last two being the loop-counter stores `[ESP+0x20]` at 0x008ACAA5 and
`[ESP+0x28]` at 0x008ACAA9). All writes to other objects happen in callees.

Clock: no RDTSC and no clock global in the body (R, whole asm.s). Time enters only as the step
info argument: `[arg1+0x08]` (step time, used as dt) and `[arg1+0x0C]` (used as inverse dt) (R
0x008AC6B3, 0x008AC850, 0x008AC949, 0x008AC9B3).

## Claims

1. The impulse is applied **directly**, not queued: motion vt+0x60 is called at 0x008ACA91 with
   no world field and no lock counter (`[world+0x88]` or other) read anywhere in the body. - **R**
   (whole asm.s: the object reads are this, contact, collidable, owner, body, motion, plus the
   listener array and each listener's vtable (0x008AC740-0x008AC750, 0x008ACA50-0x008ACA5D), the
   motion vtable (0x008AC886, 0x008ACA7D), the step-info argument (0x008AC6B3, 0x008AC850), the
   gravity argument (0x008AC9B9) and four float globals (data.json); none of them is a world field).
   Consequence: a raised `[world+0x88]` changes nothing in this function. - **D**. Whether the
   callees (0x008A6410, motion vt+0x60) consult it - **U** (not followed; 0x008A6410's rea-all
   pseudocode shows no such read).
2. The same pair "0x008A6410(body); motion vt+0x60(impulse, point)" is what the world's queued
   operation type 0x1B runs (re/functions/0x008D8830.md row 0x1B, 0x008D8BF0.md row 0x1B) - so
   motion vt+0x60 is the apply-point-impulse operation. - **D** from those files (their pseudo.c
   reading, U at instruction level there).
3. deltaV = (point velocity of the body - proxy velocity) . n * (-0.9), with point velocity =
   motion+0xD0 + motion+0xE0 x (position - motion+0x60). - **R** 0x008AC7BB-0x008AC829;
   -0.9 from data.json 0x00A97BDC.
4. When distance < 0: deltaV += distance * [arg1+0xC] * 0.4. - **R** 0x008AC83B-0x008AC85B; 0.4 from
   data.json 0x00A47E6C.
5. When deltaV < 0: magnitude = deltaV / (motion+0xC0 + (r x n) . (I^-1 (r x n))), clamped to
   >= -([this+0x6C] * dt), impulse = magnitude * n (all four lanes). - **R** 0x008AC883-0x008AC994.
   That motion vt+0x3C fills the world inertia-inverse matrix and 0x0088FE00 is a 3x3
   matrix-vector product (thiscall, ECX = out, args matrix, vector) - **D** from 0x0088FE00's
   rea-all pseudocode and the use; motion vt+0x3C's target is **U** (not resolved).
6. Gravity term: t = dt * (g . n); when projected velocity < 0, t -= projected velocity; when

### Two threads at once?

Concurrent safety is not shown - which is not the same as shown unsafe. Read facts: the body
writes only its own stack, takes no lock, reads foreign body velocities (0x008AC7C2 / 0x008AC7CF),
calls unknown listeners (0x008AC75B, 0x008ACA6D), and runs the wake 0x008A6410 and motion vt+0x60
for every contact that passes F7-F9, even at zero impulse (F11, F16) (R). Two concrete races follow
only if callee behaviour that is unverified holds: (1) two proxies touching the same dynamic body
both run motion vt+0x60 on it; if vt+0x60 is a read-modify-write of the velocities (Claim 2, D
from pseudo.c readings), the other thread's reads at 0x008AC7C2 / 0x008AC7CF race with it and the
result is order-dependent; (2) if 0x008A6410 -> 0x008CBC00 appends to the world-wide array without
a lock (Claim 9, U), two different bodies' wakes race too. (3) The listeners' vt+0x10/+0x14 are
unknown game code (U). (4) No world lock is consulted in the body, so raising `[world+0x88]` for a
parallel phase does not turn these writes into queued operations inside this function (R, Claim 1).
Conclusion - **D** from unverified callee behaviour: unsafe unless motion vt+0x60,
0x008A6410 -> 0x008CBC00 and the listeners are shown to be thread-safe. What would settle it:
motion vt+0x60's target(s) and 0x008A6410 / 0x008CBC00 read at instruction level, and the
listeners at `this+0x80` resolved. What would make it parallel: record (body, impulse, point) per thread and apply them on
the main thread after the join in a fixed order (proposal, class B), plus resolving the listeners.
