## Purpose

For one render pass record `rp` (arg1) and one pass id `pass` (arg2), the function:

1. reads the renderer pointer [0x00B3F928] once, at entry (0x007A9827);
2. publishes the pass id, zero-extended from 16 bits, to [0x00B42E90] (0x007A9836) and the
   record pointer to [0x00B42EB8] (0x007A983B);
3. asks the record's geometry `g = [rp+0x00]` for its shade/shader property
   `prop = g->GetProperty(4)` (0x007A9845);
4. only when `prop` is non-null and `1 <= prop->vt[+0x54]() <= 10` (the lighting
   shader property family, C9):
   - copies the float `[prop+0x94]` into a local (0x007A9870-0x007A9876);
   - unless the pass id is 6..9, 0x154 or 0x155, calls 0x007ECB20() (0x007A9890),
     which by its pseudocode resets eight light slots of the constant table at 0x00B46498
     (unverified, C11);
   - runs a byte counter `i` from 0 and calls `0x007EE390(i, [rp+0x0C][i], prop+0x94 value)`
     (0x007A98B3) while `i < [rp+0x08]`; both `[rp+0x08]` (count, 0x007A9897 / 0x007A98BE) and
     `[rp+0x0C]` (array pointer, 0x007A98A5) are re-read from the record on every iteration
     (read), so the iteration count equals the entry count at entry only if 0x007EE390 does
     not modify the record (unverified, C15). 0x007EE390 by its pseudocode writes light `i`'s
     constants (unverified, C12);
5. always calls the geometry's vtable slot +0x84 (slot 33) with the renderer pointer read
   in step 1 (0x007A98CE). For NiTriShape / NiTriStrips that slot is 0x00717690 / 0x00719B60,
   which reach `NiDX9Renderer::Do_RenderShape` 0x007693E0 under their gate
   (re/functions/0x007693E0.md C4).

So this function is the shader accumulator's per-record draw step that sits between a
pass driver and the geometry's render entry: the accumulator-side counterpart of the
direct slot-33 loop in 0x0070BF30 that NiDrawScene uses when no accumulator is set
(re/functions/0x0070C000.md C2). The pass id and the record it leaves in the two globals
are what the code below the render entry reads: 0x007EE390 reads [0x00B42EB8]
(pseudocode), and the shader's SetupTransformations 0x007C9230 early-outs on pass ids 6..9
read from [0x00B42E90] (knowledge/culling-and-draw-setup.md, step 3). Both globals are
also written by ten other functions (rea-all grep, C20).

No clock is read or written by this function's own instructions: the only absolute data
addresses are the three above (data.json, read). Whether a callee reads a clock is not
checked at instruction level (unverified); the pseudocode of 0x00707530, 0x007ECB20 and
0x007EE390 references no timer global or timer import.

Subsystems touched, in order (read, from the call order in asm.s):

1. Renderer global read (0x007A9827).
2. Render-state globals written: pass id, current record (0x007A9836, 0x007A983B).
3. Scene graph: property list walk of the geometry (0x00707530, 0x007A9845).
4. Shader property: virtual shader-type query twice (0x007A9857, 0x007A9865), float +0x94 (0x007A9870).
5. Light constants: reset (0x007ECB20, 0x007A9890), per-light write (0x007EE390, 0x007A98B3).
6. Draw: geometry slot 33 (0x007A98CE) -> Do_RenderShape.

## Calling convention and parameters

- **`__thiscall`, `this` unused, `RET 8`** (callee removes two stack arguments).
  - `RET 0x8` at 0x007A98D4 (read).
  - Two of the five callers load ECX before the call: `MOV ECX,EBP` 0x007ACDE2, `MOV ECX,EBX`
    0x007ACECA (0x007AC9A0), `MOV ECX,EBX` 0x007AD4B1 and 0x007AD9CB (0x007AD270) (read, those
    functions' asm.s). 0x007ACF40, 0x007ABAC0 and 0x007AA130 are not in this export and were
    seen only in pseudocode (unverified whether they load ECX).
  - At the callee this convention behaves the same as `__stdcall` with two arguments, since
    ECX is never read (derived from C1 and C2); the `__thiscall` name rests on the two callers
    above.
  - The body never reads ECX before overwriting it with `MOV ECX,[ESI]` at 0x007A9841 (read),
    so `this` has no effect on the result (derived from the read instructions).
- Stack at entry (ESP0 = ESP at the first instruction):

| Argument | Location | Register in body | Type | Evidence |
|---|---|---|---|---|
| arg1 `rp` | [ESP0+4] | ESI from 0x007A982E (`MOV ESI,[ESP+0x10]` after three pushes) to the end | `BSShaderProperty::RenderPass*` (xOBSE name; layout C5) | read |
| arg2 `pass` | [ESP0+8] | BX from 0x007A9821 (`MOV BX,word ptr [ESP+0xC]` after one push) | 16-bit pass id; only the low word is read (read). Callers push 32 bits: `PUSH EDI` 0x007ACDE0 / 0x007ACEC8, `PUSH EDI` with EDI = 0x17D 0x007AD4AF, `MOVZX ECX,word ptr [ESI+0x4]; PUSH ECX` 0x007AD9C5-0x007AD9C9 (read in callers) | read |

- The arg2 stack slot is reused as a float local after BX holds the pass id:
  `FSTP float ptr [ESP+0x18]` at 0x007A9876 with ESP = ESP0-0x10, i.e. [ESP0+8] (read; offset
  arithmetic derived from the four pushes).
- Callee-saved registers EBX, EBP, ESI, EDI are pushed at 0x007A9820/26/2D/35 and popped at
  0x007A98D0-0x007A98D3 (read). EBP holds the renderer pointer from 0x007A9827 to the final
  call (read).
- Return: the function writes no EAX after the slot +0x84 call (read), so EAX on return is
  whatever slot +0x84 left. Ghidra types the function `void`; no caller use of EAX was checked
  (unverified). Treat as `void`.
- Callees' conventions as used here:
  - 0x00707530: `__thiscall` (ECX = geometry, 0x007A9841), one argument (`PUSH 0x4`), callee
    cleans - no `ADD ESP` after 0x007A9845 (read). `RET 4` read in re/functions/0x007C6100.md.
  - Property vtable +0x54: `__thiscall` (ECX = prop, 0x007A9855/0x007A9863), no stack argument
    (read: nothing pushed, no `ADD ESP` after).
  - 0x007ECB20: no argument pushed, no `ADD ESP` after (read); ECX at that point is the
    property (last loaded at 0x007A9863), whether it uses ECX is unverified (its pseudocode
    shows `void (void)`).
  - 0x007EE390: `__cdecl`, three arguments, caller cleans: pushes at 0x007A98A4 (slot for the
    float, filled by `FSTP [ESP]` 0x007A98A8), 0x007A98B1 (entry), 0x007A98B2 (index), then
    `ADD ESP,0xC` at 0x007A98BB (read).
  - Geometry vtable +0x84: `__thiscall` (ECX = geometry, 0x007A98C3), one argument (`PUSH EBP`
    0x007A98CD), callee cleans: the pops and `RET 8` follow with no `ADD ESP` (read); matches
    0x00717690/0x00719B60 ending in `RET 0x4` (re/functions/0x007693E0.md, objdump).

Notes on the flags (read): the `FLD`/`FSTP` pair at 0x007A9870/0x007A9876 sits between
`CMP BX,0x6` and `JC`; x87 loads and stores do not change EFLAGS, so B4 tests the `CMP BX,0x6`
result (derived from the x86 definition of FLD/FSTP). `XOR BL,BL` at 0x007A9895 destroys the
low byte of the pass id held in BX; BX is not read again afterwards (read).

Test flows a rebuild needs (derived from B1-B9):

1. No type-4 property (B1) -> no reset, no light writes, slot +0x84 called once with the renderer.
2. Shader type -1 or 0 (B2) -> same as 1.
3. Shader type 11..15 (B3) -> same as 1.
4. Shader type 1..10, pass 0..5 -> reset, then the light loop.
5. Shader type 1..10, pass 6..9 -> no reset, light loop.
6. Shader type 1..10, pass 10..0x153 or > 0x155 -> reset, light loop.
7. Shader type 1..10, pass 0x154 / 0x155 -> no reset, light loop.
8. `lightCount` 0 (B8), 1, and N (B9), entries passed in array order with index 0..N-1;
   plus a callee that changes `[rp+0x08]` or `[rp+0x0C]` during the loop - the original re-reads
   both per iteration (0x007A98BE, 0x007A98A5), so an instruction-faithful rebuild must too.
9. In every flow: [0x00B42E90] = pass & 0xFFFF and [0x00B42EB8] = rp before any callee runs;
   the renderer passed to slot +0x84 is the value of [0x00B3F928] at entry, even if a callee
   changed the global.
10. `GetShaderType` is called twice (0x007A9857, 0x007A9865), not cached (read) - a rebuild that
    calls it once is equivalent only if the slot has no side effect; knowledge/shadow-light-list-remove.md
    reads every slot +0x54 body as a constant return (derived).

## Open questions

- What the pass ids enumerate: 3 (0x007AA130), 6..9 and 0x154/0x155 (no light reset here;
  6..9 also short-circuit SetupTransformations), 0x17D (0x007AD270), 0x48/0x49, 0x16E/0x16F,
  0x160..0x162, 0x156..0x158 (0x007AC9A0's remaps and tests). BSShaderAccumulator's 419-entry
  per-pass list array (C17) bounds them below 0x1A3. 0x007B4920 (xOBSE's "see 007B4920" for
  RenderPass::type) is a switch whose cases are empty in the release build (rea-all), so the
  names are gone; a debug build string table or Bethesda's shader pass enum would settle it.
- Whether skipping the reset in passes 6..9 / 0x154 / 0x155 leaves the previous record's light
  slots in the constant table on purpose (passes that do not read light constants) or relies on
  the per-light writes covering every slot: settled by reading which constant registers the
  shaders of those passes read.
- 0x007ECB20 and 0x007EE390 at instruction level (C11, C12): the slot +0x1C value 0x1B of the
  geometry's shader (which NiD3DShader subclass), the argument count mismatch to 0x007EDCD0,
  and the table 0x00B46498 layout (entry 0 ambient?, 1..8 colours?, 9..16 and 0x11..0x18
  positions or directions?) together with its uploader to the device.
- The meaning of BSShaderLightingProperty +0x94 (a fade / dimmer factor is the reading from
  0x007ED6C0's use, unverified).
- Whether `this` (the accumulator) is passed by the three callers seen only in pseudocode
  (0x007AA130, 0x007ABAC0, 0x007ACF40) - irrelevant to this body (C2) but relevant to the name.
- Who calls 0x007AC9A0 in the scene pass (no direct caller in Ghidra; a BSShaderAccumulator
  vtable slot is the likely route - unverified) and why its second call site (0x007ACECC)
  carries 93 % of this function's attributed samples against 7 % for the first (0x007ACDE4).
- The caller of the 1 354 samples truncated at eight frames and of the 9 with stale next words
  (C21): a deeper sampler walk would attribute them.

Callees worth their own slice (by the measured share, C22):

1. The slot-33 draw below it (0x00717690 -> 0x007693E0), already mapped; the cost there is
   Do_RenderShape's.
2. **0x007EE390 -> 0x007ED6C0 / 0x007EDCD0 / 0x007ECAE0** - the per-light constant writers
   (about 2.3 % of the pass, x87 colour math per light per record; a per-pass cache candidate
   when the same light set repeats across records).
3. **0x00707530 GetProperty(4)** (about 1.4 %): a property-list walk with one virtual call per
   property, repeated per record although the property of a geometry rarely changes - and also
   called by 0x007ACF40 for the same geometry right before (C19, unverified).
4. 0x007ECB20 (0.4 %) - small; map together with 2.
