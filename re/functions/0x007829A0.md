## Purpose

Given a request of `bytes`, the function makes sure the ring object (ECX) owns a D3D dynamic
vertex buffer big enough, then hands out a slice of it:

1. **Grow** (0x007829A8-0x007829D1): when the ring's capacity `[ring+0x08]` is below
   `bytes`, the current buffer `[ring+0x10]` is Released (if present), the pointer cleared,
   and the capacity set to `bytes` when `bytes` is a multiple of 16, otherwise to
   `(bytes & ~0xF) + 0x20`.
2. **Create** (0x007829D4-0x00782A0D): when `[ring+0x10]` is null, `device->CreateVertexBuffer(
   capacity, usage, [ring+0x04], 0, &[ring+0x10], 0)` with usage 0x208 or 0x218; on a
   non-negative HRESULT the cursor `[ring+0x14]` is set to 0.
3. **Reserve** (0x00782A14-0x00782A58): when `forceDiscard == 0` and `capacity - cursor >=
   bytes`, the slice starts at the cursor, the cursor advances by `bytes`, and the flags are
   0x1000; otherwise the slice starts at 0, the cursor becomes `bytes`, and the flags are
   0x2000. A slice that starts at offset 0 always gets 0x2000.
4. Return the buffer pointer `[ring+0x10]`.

It is not a lock: no Lock/Unlock call is in the body. The flags go back to the caller, which
stores them in the chip at +0x10 (objdump 0x0077E550, 0x0077E639) where PackStream's lock
reads them (re/functions/0x0076FE20.md, earlier slice).

## Claims

C1. **read** - The function returns the whole buffer pointer (0x00782A5E) and writes the
slice offset into `*outOffset` (0x00782A2B or 0x00782A44) and lock flags into `*outLockFlags`;
a request is a slice `[offset, offset+bytes)` of one shared buffer, not a buffer of its own.

C2. **read** - The write cursor is `[ring+0x14]`. Append path (B7 and B8 not taken): offset =
cursor (0x00782A2B), cursor += bytes (0x00782A31), flags = 0x1000 (0x00782A34). Wrap path:
offset = 0 (0x00782A44), cursor = bytes (0x00782A4A), flags = 0x2000 (0x00782A4D).

C3. **read** - Whenever the offset written is 0, flags end as 0x2000 (B10, 0x00782A53-0x00782A58).
**derived** (C2, B6): the first slice after a successful create starts at 0 and is therefore
DISCARD, even when it fits.

C4. **read** - The wrap path contains no call (0x00782A3C-0x00782A4D): nothing is told that
the earlier slices of this buffer are being reused. Holders of earlier slices are not
notified, released or re-locked by this function. **unverified**: what D3D9 does to the
contents of earlier slices when the next lock of this buffer passes DISCARD (Microsoft's
D3DLOCK_DISCARD contract was not fetched in this run), and whether the lock 0x00776C90 passes
the chip's flags to `IDirect3DVertexBuffer9::Lock` unchanged (0x00776C90.md, in progress).

C5. **read** - DISCARD (0x2000) is handed out in three cases: forceDiscard != 0 (B7), the
request does not fit behind the cursor (B8), or the offset is 0 (B10). Otherwise 0x1000
(D3DLOCK_NOOVERWRITE per the Wine header). No other flag value is written.

C6. **read** - Capacity is rewritten only inside the B1 fall-through, i.e. when
`capacity < bytes` (0x007829A8-0x007829AC). New capacity = `bytes` for a multiple of 16
(B3 taken, 0x007829C9 `JZ`), else `(bytes & ~0xF) + 0x20` (0x007829CB-0x007829CE).
**derived** (B1, B3): capacity only grows, assuming no 32-bit wrap - for an unaligned
`bytes >= 0xFFFFFFE1` the `ADD` at 0x007829CE wraps and the new capacity is below `bytes`.
**derived** (B3): this clarifies knowledge/skinned-vertex-streams.md line 125 ("rounded to
16, plus 32"): an aligned request is kept as is (nothing added); an unaligned one becomes
floor16(bytes) + 32 = ceil16(bytes) + 16. Read as "rounded down to 16, plus 32" the
knowledge text is right for unaligned requests; it is wrong for aligned ones, or if
"rounded" means rounded up. **read (objdump)**: the constructor 0x0077E0A0 applies the same
rounding to its first argument (0x0077E0B8-0x0077E0D0), and both constructor calls pass
0x800 (0x0077E4BD, 0x0077E5A2), so a new ring starts at capacity 2048. **derived**: capacity
is therefore the larger of 0x800 and the largest request seen (as rounded above), not "the
largest request seen" alone.

C7. **read** - On growth the old buffer is Released (0x007829BB) and the pointer cleared
(0x007829C0) before the new one is created; the cursor is not touched in the grow block.
**derived** (C2, B6): after a successful re-create the cursor is 0 and the next slice is
DISCARD at offset 0. Chips created earlier still hold the old buffer pointer at chip+0x08
(caller stores it at 0x0077E538 / 0x0077E621, objdump); whether a chip holds its own COM
reference to it is **unverified** (the chip constructor 0x004BFD40 shows no AddRef in its
rea-all pseudocode; the release slot 0x0077E020 calls 0x0068F970 on chip+0x08 - its meaning
is unverified).

C8. **read** - Usage is 0x208 when softwareProcessing == 0, else 0x218 (0x007829E2-0x007829E9);
pool argument 0 (0x007829FD), shared-handle 0 (0x007829FA). The arguments are pushed right
to left: 0x007829FA `PUSH 0` = pSharedHandle, 0x007829FC `PUSH EDI` = ppVB, 0x007829FD
`PUSH 0` = Pool, 0x007829FF `PUSH EBP` = FVF, 0x00782A00 / 0x00782A04 Usage / Length,
0x00782A05 `PUSH EAX` = this. **derived** (Wine header):
0x208 = D3DUSAGE_DYNAMIC | D3DUSAGE_WRITEONLY, 0x218 adds D3DUSAGE_SOFTWAREPROCESSING; pool 0
= D3DPOOL_DEFAULT.

C9. **read** - On a negative HRESULT (B6 taken) the cursor is left as it was and the function
still runs the reserve step and returns `[ring+0x10]`. **derived**: the result can be a slice
of a null buffer. For a freshly constructed ring the cursor was never initialised: the
constructor zeroes +0x00..+0x10 only (0x0077E0BA-0x0077E0C5, objdump) of a 0x18-byte block,
so +0x14 is whatever the allocator left. Whether CreateVertexBuffer leaves `*ppVB` null on
failure is **unverified**.

C10. **read (exe scan + objdump)** - The only caller 0x0077E430 is `NiDynamicGeometryGroup`
vtable slot +0x18 (vtable 0x00A8B03C, see Identity). The sibling classes' slot +0x18 is a
different function: `NiStaticGeometryGroup` (vtable 0x00A8AF5C) 0x0077DB20,
`NiUnsharedGeometryGroup` (vtable 0x00A8AF88) 0x0077DE40 (exe scan). **derived**: only
streams owned by a `NiDynamicGeometryGroup` get their buffer from this ring.
**derived** with re/functions/0x0076FE20.md (earlier slice, held) table row 0x00776C40:
`ReallocateChip(record, i)` calls `owner->vt[+0x1C](record, i)` then `owner->vt[+0x18](record,
i)`; for a dynamic group those are 0x0077E020 (release, exe scan 0x00A8B058) and 0x0077E430.
**derived**: a lock-path pack reaches this function through 0x00776C40 only when the
record's owner `[record+0x04]` (read at 0x00776C4B, per 0x0076FE20.md) is a
`NiDynamicGeometryGroup`; a static or unshared owner dispatches slot +0x18 to 0x0077DB20 or
0x0077DE40 instead. 0x0076FE20 calls 0x00776C40 per stream i, while 0x007774C0 calls
0x00776C40(record, 0), stream 0 only (0x007774C0.md C1). **unverified**: that a geometry
whose consistency nibble is 0x8000 always has a dynamic-group owner - nothing read here ties
the nibble to the owner class, so 0x0076FE20.md open question 1 stays open (0x007774C0.md C1
likewise). A read of where `[record+0x04]` is set for 0x8000-nibble geometry, or a runtime
check of the owner's vtable at 0x00776C4B for such packs, settles it. Other callers of

C11. **read (objdump)** - 0x0077E430 has two arms, chosen by the record's stream count

- **More than one stream** (0x0077E47E-0x0077E567): the ring is taken from an array
  `[group+0x30][group+0x4C]`; the index `[group+0x4C]` wraps to 0 when it is not below the word

C12. **derived** (C5, C6, C11) - For multi-stream records every allocation (forceDiscard = 1)
gets a slice at offset 0 that restarts the pooled ring with DISCARD: the slice is
`[0, bytes)`, and the buffer's capacity is the larger of 0x800 and the largest request so
far (0x007829A8-0x007829D1), so it can be larger than `bytes`; for single-stream records the allocation appends with
NOOVERWRITE into the ring shared by every record of the same FVF (or stride) and gets DISCARD
when that ring wraps or was just (re)created.

C13. **derived** (C2, C5, C7, C8, C10, C11) - For the cross-frame pack cache (manifest
purpose), and only for records whose owner `[record+0x04]` is a `NiDynamicGeometryGroup`
(C10; that 0x8000-nibble geometry always has such an owner is **unverified**): such a stream
gets a new slice on every reallocation through 0x0077E430. The chip is re-pointed
(0x0077E538-0x0077E542, 0x0077E621 onward) or newly created (0x0077E517, 0x0077E608), and in
the multi-stream arm the chip is shared by pool index across records, not owned by one
record. The previous pack's bytes can be invalidated per ring by: a DISCARD slice of that
ring (C5); growth of that ring, which Releases the old buffer (0x007829BB) and creates a new
one (0x00782A06) without any DISCARD on the old one (C7); and a device reset, since the pool
is D3DPOOL_DEFAULT (0x007829FD, C8; the reset behaviour of DEFAULT-pool buffers is
**unverified** here). A necessary condition for skipping a pack is therefore: the
reallocation is skipped too, and no DISCARD slice, no growth and no device reset has hit that
ring since. That this condition is sufficient is not shown. It is the kind of condition
OBVR's StreamReuse tracks (knowledge/skinned-vertex-streams.md lines 157-160).
**unverified**: the conclusion rests on the D3D9 / DXVK contract for buffer contents after
`D3DLOCK_DISCARD` and `D3DLOCK_NOOVERWRITE`, and on 0x00776C90 passing chip+0x10 to
`IDirect3DVertexBuffer9::Lock` unchanged; neither is in this export. Settled by reading
0x00776C90 at instruction level and fetching Microsoft's D3DLOCK_DISCARD / NOOVERWRITE
documentation (or DXVK's d3d9 buffer lock implementation).

C14. **unverified** - knowledge/skinned-vertex-streams.md line 123 says the ring "creates
every dynamic vertex buffer the engine makes, 2048 to 120384 bytes". The 2048 lower bound is
consistent with C6 (constructor 0x800); the 120384 upper bound and "every" were not checked in
this run (no measurement, and other CreateVertexBuffer call sites were not searched).

## Open questions

1. Does 0x00776C90 pass chip+0x10 to `IDirect3DVertexBuffer9::Lock` unchanged, and does it lock
   `[chip+0x0C, +bytes)` (0x00776C90.md, in progress)? Settles whether C5's DISCARD reaches D3D.
2. How long is the ring pool in the multi-stream arm (`[group+0x34]`), and how many dynamic
   groups exist (one per renderer?) - decides how many allocations a pooled buffer survives.
   A read of the group's constructor, or a runtime count at 0x0077E4A6, settles it.
3. Does a chip hold a COM reference to its vertex buffer (C7)? Read 0x0068F970 and 0x004BFD40
   at instruction level.
4. Is `[ring+0x14]` ever used uninitialised (C9)? Only if a first create fails; a runtime
   check of the HRESULT at 0x00782A08 settles whether that happens at all.
5. Calls per frame: the manifest's measurement (fourteen volatile packs a frame) suggests at
   least fourteen calls a frame from the 0x8000 path; a counter at 0x007829A0 split by
   forceDiscard would measure it (**unverified**).

Smaller functions worth their own slice: 0x0077E430 (`NiDynamicGeometryGroup` slot +0x18,

## Layout requests

- `DynamicVertexBufferRing` (0x18 bytes, constructor 0x0077E0A0): +0x00 u32 unknown, +0x04 u32
  fvf, +0x08 u32 capacity, +0x0C u32 device handle, +0x10 u32 vertex-buffer handle, +0x14 u32
  cursor. Engine pointers as `std::uint32_t` handles; `static_assert` offsets and size.
- Stream chip (0x20 bytes, constructor 0x004BFD40 pseudocode, unverified at instruction level):
  +0x04 ring, +0x08 vertex buffer, +0x0C offset, +0x10 lock flags, +0x14 bytes (stores read in
  0x0077E430, objdump).
- Buffer record (fields read by 0x0077E430, objdump): +0x08 FVF / ring key, +0x10 u8
  softwareProcessing, +0x18 vertex count, +0x1C stream count, +0x20 stride array, +0x34 base
  vertex (offset / stride).
- `NiDynamicGeometryGroup` (fields read by 0x0077E430, objdump): +0x08 device, +0x0C ring map,
  +0x1C chip map, +0x2C/+0x30 ring array (+0x34 u16 its size), +0x3C/+0x40 chip array, +0x4C
  rotating pool index.
- Constants: lock flags 0x1000 / 0x2000; usage 0x208 / 0x218; initial capacity 0x800;
  alignment mask 0xF and +0x20.
