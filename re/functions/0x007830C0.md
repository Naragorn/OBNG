## Purpose

Uploads one constant-map entry to the Direct3D 9 device as a vertex shader
constant. The argument defaults are filled from the entry (data pointer from
entry+0x30, register count from entry+0x20 or 1). A lazily initialised
identity table (0x00B428D8, filled by 0x00783C70) maps the entry's type byte
(entry+0x14) to a type id; type 1 goes to device vtable +0x188, type 3 to
+0x180, every other type to +0x178. All three are called with
(device, entry+0x1C start register, data, count), and the function returns
`hr >= 0` in AL.

By d3d9.h order those three slots are SetVertexShaderConstantB (98),
SetVertexShaderConstantI (96) and SetVertexShaderConstantF (94); OBVR's
`D3D9Types.h` confirms 94 independently, while 96 and 98 are derived (C5).
The function compares nothing and caches nothing: every call that reaches
the device call uploads (read, C9). Its inclusive cost is therefore the
D3D9 runtime (plus OBVR's detour on the F path when OBVR is loaded), not
its own ~30 instructions (derived, C10).

## Calling convention and parameters

`__thiscall`, callee cleans 12 bytes (`RET 0xC` at 0x0078313A, 0x00783160,
0x00783178). This arrives in ECX (`MOV EBP,ECX` 0x007830CE). Saved
registers: EBX, EBP, ESI, EDI (0x007830C0..0x007830C9).

| 2 | [ESP+8] | 0x007830C1 (`[ESP+0xC]` after one push) -> EBX | `const void*` | `data` | 0 means "use entry+0x30" (0x007830C5..0x007830D2) |
| 3 | [ESP+0xC] | 0x007830D5 (`[ESP+0x1C]`) -> ESI | `uint32` | `count` | 0 means "use entry+0x20, or 1 if that is 0" (0x007830D9..0x007830E4) |

Return: `bool` in AL only (`XOR ECX,ECX; TEST EAX,EAX; SETGE CL; MOV AL,CL`,
e.g. 0x0078312E..0x00783137). The upper 24 bits of EAX keep the HRESULT's
upper bits (read), so callers must test AL only; 0x009A56D0 does
(`TEST AL,AL` 0x009A60E4).

Note: the function spills the type dword into the caller's slot of
argument 2 (`MOV [ESP+0x18],EAX` 0x007830F3) and reloads it after the
0x00783C70 call (0x007830FE). Argument 2 has already been copied to EBX, so
this is register pressure, not a semantic write (read).

## Control flow

Each row is one test flow for a rebuild.

| # | Branch | Condition | Address | Effect |
|---|---|---|---|---|

| B7 | Int | `typeTable[...] == 3` (`CMP EAX,3` 0x0078313D, `JNZ` 0x00783149 not taken) | 0x0078314B..0x00783160 | `device->vtbl[+0x180](device, reg, data, count)` |
| B8 | Float (default) | any other table value | 0x00783163..0x00783178 | `device->vtbl[+0x178](device, reg, data, count)` |
| B9 | result | `hr >= 0` (`SETGE`) | 0x00783133 / 0x00783159 / 0x00783171 | AL = 1 when hr >= 0, else 0 |

The three arguments after the device are pushed once before the type branch
(`PUSH ESI; PUSH EBX; PUSH EDI` at 0x00783117..0x00783119); each branch
pushes only the device (0x0078312A, 0x00783148).

Pseudocode disagreement: pseudo.c shows the Bool call as `(*vtbl+0x188)(piVar2)`
and the Int call with no arguments. The instructions push start register,
data and count before the branch at 0x0078311A, so all three device calls
take the same four arguments. The instructions win.

## Open questions

- Per draw: which NiD3DShaderConstantMap / NiD3DSCM_Vertex virtual loops over the entries and calls slot +0x54 (0x009A56D0), and how many entries a typical shadow-light vertex map has. Candidates are the NiD3DSCM_Vertex slots 0x009A61E0, 0x009A6370, 0x009A7F90, 0x009A65B0, 0x009A83B0 (vtable 0x00AB2BAC, slots 22-27); none of them was read. This decides "uploads per draw".
- Which entries upload unchanged values every draw (the lever behind OBVR's SetVsConstantF cache): this needs the map's per-entry loop, plus a measured census of (register, data) per draw. Nothing in 0x007830C0 tells changed from unchanged values (C9).
- Whether Oblivion's shader packages create NiD3DVertexShader or NiD3DHLSLVertexShader programs (C3). Only the former reach this function.
- The class of `[this+0x24]` (likely NiDX9RenderState: a 0x1000-byte object with the device at +0xFF8 and the renderer at +0xFFC, from 0x0077F840). The vtable or RTTI of 0x0077F840's `this` was not looked up.
- The order of SetVertexShaderConstantI / B within slots 96..99 against d3d9.h itself (C5).
- The AttributeType enum (C8): needs a Gamebryo header or another code path that names type values.
- How the sampler unwinds through frame-pointer-less functions (C14), and the exclusive / D3D9 / OBVR split of this function's 21.9 %.

## Callees and smaller slices worth their own work

- 0x00783C70 - fills the type identity tables (C6). Trivial; it needs no slice.
- Device slots +0x178 / +0x180 / +0x188 - D3D9 runtime, not engine code.
- Worth a slice: the NiD3DSCM_Vertex vtable 0x00AB2BAC (the per-entry loop, and 0x009A56D0's siblings at slots 22-27). The per-draw upload count, and with it the redundant-upload lever, lives there, not here.
- Worth a slice: 0x00783180 (slot 11, SetVertexShaderConstantArray; 0x009A56D0 calls it at 0x009A5B33). It probably has the same shape with an array index (unverified).

## Layout requests

A shared header (e.g. `src/engine/render/ShaderConstants.h`) would need:

- `NiD3DShaderConstantMapEntry` (name unverified): `uint32 type` at +0x14 (only the low byte is used), `uint32 shaderRegister` at +0x1C, `uint32 registerCount` at +0x20, `uint32 dataSource` (32-bit handle) at +0x30; plus +0x10 predefined id (from 0x009A56D0), +0x0C key and +0x24 variable name (from 0x007837F0, unverified).
- `NiD3DShaderProgram`: `uint32 renderState` (handle) at +0x24; vtable slots 10..13 = Set{Vertex,Pixel}ShaderConstant{,Array} as in C2/C4.
- Render-state-like object: `uint32 device` (IDirect3DDevice9 handle) at +0xFF8, `uint32 renderer` at +0xFFC.
- Device slot constants: 94 (F, OBVR-verified), 96 (I), 98 (B); pixel 109 (F, OBVR-verified), 111, 113.
- Globals: `kTypeTable = 0x00B428D8` (14 x uint32), `kTypeTableBytes = 0x00B4294C` (14 x uint8), `kTypeTableReady = 0x00B4295B` (uint8).
