## Purpose

Turns one `GetTickCount` value into the frame's length in seconds at +0x0C,
the value every time-driven update in the frame advances by. Three modes:

1. **Frozen** (+0x00 nonzero): +0x0C = 0.0. Nothing else in the object
   changes; in particular +0x08 and +0x10 are not touched (read, 0x0047D18F
   jumps straight to the store at 0x0047D24D).
2. **Fixed step** (+0x04 not equal to 0.0, the iFPSClamp mode per
   knowledge/frame-clock.md, unverified here): the frame is +0x04
   milliseconds long whatever the tick says. The tick is not used for the
   frame's length or for +0x10. +0x10 is advanced by the whole-millisecond
   part of `(float)(carry + step)`, and the fraction is kept at +0x08 for the
   next frame. +0x10 therefore advances by about the step per frame on
   average; it is not exact, because `carry + step` is rounded to float on
   every frame before the truncation and that rounding is never carried
   (claim 13).
3. **Variable** (+0x04 == 0.0): `delta = (tick - start) - last` in 32-bit
   integer arithmetic, converted to float as **unsigned**; 0 reads as 1, a
   delta above the float at 0x00A3D14C reads as 166 (0xA6), otherwise the
   delta is used as is. +0x10 is set to the real `tick - start`, not to
   `last + clamped delta`. With the expected constants (0x00A3D14C =
   166.67, 0x00A2FC78 = 2^32; both unverified, open question 2) a negative
   delta reads as 166.

In modes 2 and 3, +0x0C = `(float)((float)(ms * k) * multiplier)` with `k`
the double at 0x00A30E40 (expected 0.001, unverified) and the multiplier read
from the float at 0x00B06704 (an INI setting's value, see
`re/functions/0x009DC2D0.md` claim 5).

Every call, in every mode and for every instance, first copies 0x00B39DB0 to
0x00B39DB4 and stores `tick - start` into 0x00B39DB0.

## Calling convention and parameters

- `__thiscall`. `this` in ECX: first use `SUB EDX,[ECX+0x14]` at 0x0047D176,
  ECX never loaded inside the body (read). Callers set ECX right before the
  call: `MOV ECX,0xb33e90` at 0x0040D8A6, `MOV ECX,EDI` at 0x005AD9C0 and
  0x005AD325 (read, caller exports).
- One stack argument at `[ESP+4]` on entry: the tick, `MOV EDX,[ESP+4]` at
  0x0047D170. Every caller pushes the return value of the import at
  0x00A280D0 (`PTR_GetTickCount_00a280d0` in 0x005AD980's meta.json) just
  before the call: 0x0040D89F/0x0040D8A5, 0x005AD9B9/0x005AD9BF,
  0x005AD322/0x005AD324 (read). So the argument is a `GetTickCount` value
  (derived).
- Callee cleans the stack: `RET 0x4` at 0x0047D253 (read).
- Returns nothing meaningful. EAX holds leftovers (status word or the
  truncated step), the x87 stack is empty on return: `FLDZ` at 0x0047D174 is
  popped by `FCOMP` at 0x0047D195 or by `FSTP` at 0x0047D24D, every later
  load is popped by an `FSTP`/`FCOMP`/`FISTP`/`FSUBP` (derived from the
  instruction sequence). Proposed C signature:
  `void __thiscall Update(UInt32 tickMs)`.
- Local frame: `SUB ESP,0x8` at 0x0047D17E, two dwords used as a 64-bit
  `FISTP` target at `[ESP]`. The caller's argument slot (`[ESP+0xC]` after the
  `SUB`, `[ESP+0x10]` after `PUSH ESI` at 0x0047D1F0) is reused as scratch for
  the float sum, the saved control word and the int-to-float conversions
  (read: 0x0047D1A5, 0x0047D1AD, 0x0047D1D1, 0x0047D203, 0x0047D227). The tick
  is consumed into EDX before any of that (0x0047D170). Callers do not read
  the slot after the call (`RET 4` removes it).
- Registers: EDX, EAX clobbered; ESI saved and restored on the variable path
  only (0x0047D1F0 / 0x0047D237); the fixed path never touches ESI (read).
- The x87 control word is changed temporarily: `OR EAX,0xC00` at 0x0047D1B8
  sets rounding control (bits 10-11) to truncate, `FLDCW [ESP]` at
  0x0047D1C0, restored by `FLDCW [ESP+0xC]` at 0x0047D1CD (read). Precision
  control is not touched (read: these are the only two `FLDCW`). Whether the
  caller's precision control can change the stored bits: see claim 20.

## Answers to the slice questions

1. **0x00B39DB0 / 0x00B39DB4**: 0x00B39DB0 holds `tick - startTick` of the
   instance updated last (milliseconds since that clock's start, not the raw
   tick); 0x00B39DB4 holds the value 0x00B39DB0 had before that call (claims
   3-6, read/derived). So yes, this and the previous value, but in the
   instance's own time base, and shared between instances. **Who reads them:
   not answerable from this export** (claim 7). Needs an xref listing of both
   addresses.
2. **iFPSClamp path**: the frame's length is the fixed step at +0x04; the
   carry at +0x08 holds the fractional milliseconds left after +0x10 is
   advanced by `trunc((float)(carry + step))`, so the integer clock at +0x10
   keeps pace with the fixed step over many frames, up to the per-frame float
   rounding of `carry + step`, which is not carried (claims 11-13). The real
   tick only goes into the two globals.
3. **Negative-delta path**: the instruction pattern is the compiler's
   unsigned-to-float conversion (read), so the delta is a UInt32 and a
   negative int32 becomes `delta + [0x00A2FC78]` before the ceiling compare.
   If the constants are the expected 2^32 and 166.67 (unverified), a delta
   where the tick is behind +0x10 reads as 166 ms (claim 16, flow F10). The
   same pattern sits on the fixed path (B3) and on the final multiply (B7,
   dead if the ceiling is below 2^31).

## Open questions

1. Who reads 0x00B39DB0 and 0x00B39DB4? Cheapest step: an xref export of the
   two addresses (one Ghidra headless run over `re/export`).
2. The constant values: 0x00A2FC78 (expected 4294967296.0f), 0x00A30E40
   (expected 0.001 as double), 0x00A3D14C (expected 166.666...f per OBVR).
   Claims 9, 14, 16, 17, 20, 21 and flows marked (c) depend on them.
   Cheapest step: export the 16 bytes at each address with the slice.
3. What 0x0047D150 writes (expected: +0x14 = tick, +0x10 = 0, +0x00/+0x04/
   +0x08 = 0). Export it; it is the constructor-like initialiser the rebuild
   needs for its test fixtures. It also decides carry0 for claim 13.
4. Where +0x00 (frozen) and +0x04 (fixed step) are written, and whether +0x04
   really is `1000 / iFPSClamp`. Needs xrefs on 0x00B33E90/0x00B33E94.
5. Precision control at the call site in the game is not known (Direct3D 9
   sets single precision unless created with FPU_PRESERVE; unverified for
   Oblivion). Claim 20 shows it does not change +0x08, nor +0x0C for ms
   1..166 and steps `1000/fps`; an unusual +0x04 value could still differ
   through double rounding at 0x0047D238. The differential check in the real
   process settles it for the values the game actually uses.
6. What the second TimeInfo (owner built in 0x005AD0D0, updated in
   0x005AD980) is for: the slice question for those two functions.
7. Whether 0x00401F00 can return 0 (claim 28). Needs its export.
