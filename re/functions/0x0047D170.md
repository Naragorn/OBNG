## Purpose

Turns one `GetTickCount` value into the frame's length in seconds at +0x0C,
the value the frame's time-driven updates advance by (consumer: `FLD
[0x00B33E9C]` at 0x0040D8B0 and five more reads in 0x0040D800). Three modes,
chosen by +0x00 and +0x04:

1. **Frozen** (`byte [this+0x00] != 0`): +0x0C = 0.0f; +0x04, +0x08, +0x10
   are not touched.
2. **Fixed step** (`[this+0x04] != 0.0f`, NaN included): the frame is +0x04
   milliseconds long whatever the tick says. +0x10 advances by
   `trunc((float)(carry + step))` and the fraction stays at +0x08.
   +0x0C = `(float)((float)(step * k) * multiplier)`.
3. **Variable** (`[this+0x04] == 0.0f`, -0.0 included):
   `delta = (tick - [this+0x14]) - [this+0x10]` (UInt32 arithmetic);
   `ms = delta == 0 ? 1 : min(delta, 166)` with delta read as **unsigned**;
   +0x10 = `tick - [this+0x14]`;
   +0x0C = `(float)((float)(ms * k) * multiplier)`.

`k` = the double at 0x00A30E40 (= `(double)0.001f`), multiplier = the float
at 0x00B06704 (`fGlobalTimeMultiplier`, knowledge/frame-clock.md, read in
0x009DC2D0's export in the frame-clock slice).

Every call, in every mode and on every instance, first copies 0x00B39DB0 to
0x00B39DB4 and then stores `tick - [this+0x14]` into 0x00B39DB0.

## Calling convention and parameters

- `__thiscall`; `this` in ECX: first use `SUB EDX,[ECX+0x14]` at 0x0047D176,
  ECX is never written inside the body (read). The callers load ECX right
  before the call: `MOV ECX,0xb33e90` 0x0040D8A6, `MOV ECX,EDI` 0x005AD9C0
  and 0x005AD325 (read, frame-clock caller exports).
- One stack argument at `[ESP+4]` on entry, read into EDX at 0x0047D170
  (read). Each caller calls `[0x00A280D0]` (`PTR_GetTickCount_00a280d0`,
  KERNEL32 GetTickCount per the sibling meta.json files) and pushes EAX right
  before the call: 0x0040D89F/0x0040D8A5, 0x005AD9B9/0x005AD9BF,
  0x005AD322/0x005AD324 (read). So the argument is a GetTickCount value
  (derived).
- Callee cleans: `RET 0x4` at 0x0047D253 (read); the emulator reports
  `stack_delta` 4 in all seven committed cases (measured).
- No meaningful return value. EAX holds a leftover (status word or the
  truncated step; the emulator shows 0x100, 0x4000, 0x0, 0x10 for different
  cases, measured). The x87 stack is balanced on return: the `FLDZ` at
  0x0047D174 is popped by `FCOMP` 0x0047D195 or by `FSTP` 0x0047D24D; every
  later load is popped by `FSTP`/`FCOMP`/`FISTP`/`FSUBP` (derived from the
  instruction sequence).
- Local frame: `SUB ESP,0x8` 0x0047D17E (8 bytes, the `FISTP qword` target
  at `[ESP]`); the caller's argument slot (`[ESP+0xC]` after the SUB,
  `[ESP+0x10]` after `PUSH ESI` 0x0047D1F0) is reused as scratch for the
  float sum, the saved control word and the int-to-float conversions
  (0x0047D1A5, 0x0047D1AD, 0x0047D1D1, 0x0047D203, 0x0047D227; read). The
  tick is already in EDX by then.
- Registers: EAX, EDX clobbered; ESI pushed/popped on the variable path only
  (0x0047D1F0 / 0x0047D237); the fixed path does not touch ESI (read).
- x87 control word: `FNSTCW` 0x0047D1AD, `OR EAX,0xC00` 0x0047D1B8 (RC =
  toward zero), `FLDCW [ESP]` 0x0047D1C0, restored by `FLDCW [ESP+0xC]`
  0x0047D1CD (read). Only RC changes and only around the `FISTP` at
  0x0047D1C3; every other operation uses the caller's control word.

## Answers to the slice questions

1. **Negative delta.** A delta that is negative as int32 (tick below
   `start + last`) is converted as unsigned: `FILD` gives d, the `FADD
   [0x00A2FC78]` at 0x0047D20D adds 4294967296.0f (data.json), giving
   `d + 2^32` in [2^31, 2^32], always above the ceiling 166.66667f, so B6
   falls through and ms = 166 (0xA6) (claim 16; measured F8..F11 for d =
   -1980, -1, INT_MIN, at PC 64 and 24: all give 0x3E29FBE8). 0x3E29FBE8 is
   the unscaled store at 0x0047D241; the final +0x0C (0x0047D24D) equals it
   only when fGlobalTimeMultiplier (0x00B06704) is 1.0f, as in these cases;
   in general it is `(float)(0x3E29FBE8-as-float * multiplier)` (claim 19). +0x10 then
   moves back to `tick - start` (F8: 3000 -> 1020). The third fix-up at
   0x0047D231 is **unreachable** (claim 17). The fix-up at 0x0047D1DB on the
   fixed path is reachable for a step at or below -1 (F15: the carry becomes
   -2^32 = 0xCF800000) or a sum at or above 2^31 (F17: correct unsigned
   reading); whether the game ever writes such a step is unverified.
   Negative deltas are reachable in the game through the outermost bracket
   pair when D > r (claim 30, with its conditions) and through leaving fixed mode (claim 14) - both derived.
2. **Carry +0x08 outside this function.** In every function exported for
   the frame-clock and time-info slices, +0x08 is read only at 0x0047D19F;
   the other accesses are the zero-initialising writes in 0x0047D150 and
   0x009DC2A0 (claim 26, read). Image-wide this is **unverified**: an
   absolute read of 0x00B33E98 would show in a Ghidra xref listing (none was
   exported for it), and an instance-relative read (`[reg+0x8]` on a
   TimeInfo pointer) cannot be found by xrefs at all. Cheapest step: export
   the xrefs to 0x00B33E98 and 0x00B33E94; for the relative case, the
   LoadingMenu instance is the only other known one and 0x005AD980 does not
   read it.

## Open questions

1. Who writes +0x04 (the fixed step), and is it `1000 / iFPSClamp`? No
   exported function writes a nonzero value (0x0047D150 and 0x009DC2A0 write
   0.0f). Cheapest step: export the xrefs to 0x00B33E94.
2. Does the game update g_timeInfo between the two halves of the bracket
   (claim 31), and how long are D and r in practice (claim 30)? A shadow
   read in the game, or a chained emulator case (bracket with a GetTickCount
   stub, then this function) settles the engine side.
3. The game's x87 control word (rounding mode and precision). Claims 21/22
   make +0x0C and +0x08 independent of precision control for the reachable
   inputs, but not of the rounding mode.
4. The scratch cases F8..F19 should go into
   `tools/difftest/cases/0x0047D170.json` (and case 5's name be corrected,
   claim 27) so the rebuild's tests and the differential check share them.
   Not edited from here.
5. Whether the allocator called from 0x005AD0D0 can return 0 (claim 28).
6. The emulator's default x87 control word: unicorn reports 0x0000 before
   the first run, so the masking that made F16 (NaN) run without a trap is
   unverified; the game's mask is unverified too.
