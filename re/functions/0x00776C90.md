## Purpose

Locks a range of a D3D buffer and hands the caller a **system-memory
staging block** instead of the mapped pointer. In order (all read, addresses
in Control flow):

1. Calls the buffer's virtual Lock (vt+0x2C) with the caller's offset, size
   and flags unchanged, the mapped pointer landing in a stack local.
2. On a negative HRESULT returns 0 and touches no manager state.
3. Otherwise enters the manager's critical section (+0x80), records the
   owning thread id (+0xF8) and increments a lock depth (+0xFC), stores the
   mapped pointer (+0x48) and the size (+0x4C).
4. Grows the one staging block (+0x40, capacity +0x44) when the size
   exceeds the capacity: FormHeap_Free the old block, FormHeap_Allocate a
   new one of exactly `size` bytes.
5. When neither flag bit of 0x3000 is set, copies `size` bytes from the
   mapped D3D range **into** staging (a read-back); when either is set,
   staging is left as it is.
6. Returns the staging pointer +0x40, with the critical section still held.

The unlock 0x00776D80 (read, `re/export/packing-lifetime/0x00776D80/asm.s`)
then copies staging -> mapped with +0x4C bytes, clears +0x48/+0x4C,
decrements +0xFC, clears +0xF8 when the depth reaches 0, leaves the
critical section and calls vt+0x30 Unlock. The section stays held until a
release on the same manager; two release sites are read: 0x00776D80 and an
inlined copy of the same sequence in 0x007774C0 (memcpy 0x007779E8,
LeaveCriticalSection `[0x00A28074]` 0x00777A08, vt+0x30 0x00777A14). The
lock and its release therefore bracket one critical section across the
caller's write (derived from those two release sites).

No clock (TimeInfo) field is read or written (read: the only memory
operands are the stack, `[vb]`, `[vtable+0x2C]`, `[this+0x40..0x4C]`,
`[this+0x80]`, `[this+0xF8]`, `[this+0xFC]` and the two import slots).

zeroed at 0x00776CB4 (`[ESP+0x20]` at ESP0-0x24), passed by address as
Lock's 4th argument (`LEA EDX,[ESP+0x10]` at 0x00776CA1, ESP0-0x14+0x10 =

Inner calls: vt+0x2C is called with 5 pushed arguments and nothing cleans
them after the call; the stack is balanced at 0x00776CC2 (four pops + RET
0x10 match the four entry pushes), so the callee pops all 5 (stdcall,
derived from 0x00776CBC..0x00776CC8). EnterCriticalSection pops its own
argument (derived: `POP EBX` at 0x00776CF3 restores the EBX pushed at
0x00776CCB). FormHeap_Free / FormHeap_Allocate are cleaned together by the
caller (`ADD ESP,0x8` 0x00776D05, cdecl, read). memcpy is cdecl (`ADD
ESP,0xC` 0x00776D25, read).

Returns in EAX: 0 when the Lock HRESULT is negative (0x00776CC4), else the
staging pointer `[this+0x40]` (0x00776D28) (read).

## Control flow

Three branches, five flows (read; the rebuild tests each flow).

| ID | At | Condition | Taken | Not taken |
|---|---|---|---|---|
| B1 | 0x00776CC0 `JGE 0x00776CCB` | Lock HRESULT (EAX, `TEST EAX,EAX` 0x00776CBE) >= 0 | continue at 0x00776CCB | 0x00776CC2: restore EDI/ESI/EBP, EAX = 0, `RET 0x10` - no critical section, no field written |
| B2 | 0x00776CF4 `JNC 0x00776D0E` | `[this+0x44] >= size` (unsigned: CMP 0x00776CEA, carry clear) | skip the regrow | 0x00776CF6..0x00776D0B: FormHeap_Free([this+0x40]); [this+0x40] = FormHeap_Allocate(size); [this+0x44] = size |
| B3 | 0x00776D14 `JNZ 0x00776D28` | `(flags & 0x3000) != 0` (TEST 0x00776D0E; immediate from the instruction bytes `f7 c5 00 30 00 00`) | skip the read-back | 0x00776D16..0x00776D25: memcpy([this+0x40], mapped, size) |

Flows:

1. B1 fails -> return 0.
2. B1 ok, B2 fits, B3 flag set -> staging returned as is (old contents).
3. B1 ok, B2 fits, B3 no flag -> staging filled from the mapped range.
4. B1 ok, B2 grows, B3 flag set -> fresh FormHeap block returned
   uninitialised.
5. B1 ok, B2 grows, B3 no flag -> fresh block filled from the mapped range.

The writes +0xFC++, +0xF8, +0x48, +0x4C happen on every flow except 1,
before B2 (0x00776CDF..0x00776CF0, read).

## Answers to the slice questions

- **Flags:** passed through unchanged (C1); the function never picks
  DISCARD or NOOVERWRITE itself and never moves the offset (C2). The 0x3000
  test only skips the read-back of the mapped range into staging (C4).
  Which flags and ranges a chip carries is decided upstream (C3) - the
  question moves to 0x007774C0 and the ring manager 0x007829A0.
- **Staging memory:** one FormHeap block per manager, kept and regrown to
  exactly the size that triggered the growth (C6, C7); it equals the largest
  lock seen only if nothing else writes +0x40/+0x44 (C6a, unverified). The
  critical section guards that single block and the mapped-pointer/size
  pair across lock -> caller write -> release (C10, C11).
- **Manager state across a lock/unlock pair:** lock sets +0x48 = mapped,
  +0x4C = size, +0xF8 = thread id, +0xFC += 1, possibly +0x40/+0x44
  (regrow), holds +0x80; unlock copies, zeroes +0x48/+0x4C, +0xFC -= 1,
  zeroes +0xF8 at depth 0, leaves +0x80. +0x40/+0x44 survive the unlock.
- **For the pack cache (lever L3):** whether a skipped pack must also skip
  the lock is a condition on the flags (derived from C4, C8, C9 and the
  unlock's unconditional memcpy 0x00776D8F). With a 0x3000 flag whose
  semantics require the buffer's old bytes to survive (NOOVERWRITE, if
  0x1000 is NOOVERWRITE - C5, unverified), lock/unlock without a write
  overwrites the range with staging (C8), so the lock must be skipped too.
  Under DISCARD the old contents are already undefined at the D3D level
  (unverified, same D3D header question as C5). Without a 0x3000 flag the
  lock reads the range back, so lock/unlock without a write is
  content-preserving but costs the read-back (C9). And the probe hash at the unlock's
  entry (Probes.cpp, hashing +0x40 for +0x4C bytes) sees exactly the bytes
  written to D3D on every flow that reached the unlock (derived from the
  unlock's unconditional memcpy).

## Open questions

1. Which flags each caller passes (0x007774C0 passes `[chip+0x10]`;
   0x00766880, 0x00769030, 0x00777240, 0x00776E90 not read here) - does any
   path lock without a 0x3000 bit and pay the read-back (C9)?
2. Does any caller lock with a 0x3000 bit and write fewer than `size`
   bytes (a dirty-mask partial pack in 0x0076FE20)? If so, the unlock
   writes stale staging bytes into the D3D buffer (C8) - either a latent
   bug or the dirty mask is always full when such flags are set.
3. Do callers check the 0 return and skip the unlock (C14)?
4. Does any thread nest two locks through the same manager (C12)?
5. Is there one manager for the renderer or one per record
   ([record+0x0C] per 0x0076FE20.md, in progress)? With one shared manager
   all packing threads serialise on +0x80 for the whole write.
6. Does FormHeap_Free 0x00401F20 accept NULL (first regrow, when +0x40 is
   presumably 0 - initial value unverified)?
7. What reads +0xF8 / +0xFC besides the unlock (C13)?
8. What occupies +0x98..+0xF7 between the CRITICAL_SECTION and +0xF8?
