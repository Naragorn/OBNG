## Purpose

Copies a 64-byte (4 x 16-byte) transform given by pointer into `this+0x70..+0xAF`. When the object is in a
world (`[this+0x08] != 0`), it asks the object's shape (`[this+0x14]`) through virtual slot +0x0C for an
AABB of the new transform, padded by half the world's collision tolerance (`[[[this+0x08]+0x74]+0x08] *
0.5f`), into a 32-byte stack buffer, and hands that AABB to 0x008DE950 (on `this`), the Havok world's
broad-phase update step. It reads and writes no clock.

Sibling 0x008ABAC0 is the same shape but writes only `this+0xA0..+0xAF` (one 16-byte vector) and adds a
second float parameter to the tolerance; that pairing (whole 64-byte block vs. +0xA0 only) is why the
proposed name is setTransform (unverified, see C9 and Identity).

## Calling convention and parameters

- `__thiscall`: `this` in ECX, moved to ESI at 0x008ABA51 (read).
- One stack argument `[EBP+0x8]` = pointer to the 64-byte source transform (read 0x008ABA49).
- Callee cleans the stack: `RET 0x4` at 0x008ABAAE (read).
- Frame: `PUSH EBP / MOV EBP,ESP / AND ESP,0xFFFFFFF0 / SUB ESP,0x24` (0x008ABA40-0x008ABA46); EBX, ESI, EDI
  saved; epilogue `MOV ESP,EBP / POP EBP` (read).
- Return value in EAX (read): F1: EAX = arg1 (srcTransform), loaded at 0x008ABA49 and not changed before
  the return at 0x008ABAAE. F2: EAX is whatever 0x008DE950 leaves (the last write before it is
  `MOV EAX,EBX` at 0x008ABA9E, consumed as its argument). Whether any caller uses EAX: unverified.

## Control flow

No other branches, no loops, no jump tables (data.json `jump_tables` empty). Inside 0x008DE950 further
branches exist (world lock counters +0x88/+0x8C nonzero -> error 0x11 via 0x00898820, read in its asm.s at
0x008DE963-0x008DE988); they belong to its own map.

Test flows for a rebuild: F1 (null world: only the 64 bytes change), F2 (world set: tolerance read, vcall with
(src, tol*0.5, buf), 0x008DE950 with buf). Note for F2: the vcall receives the caller's `src` pointer, not
`this+0x70` (read 0x008ABA9A PUSH EAX with EAX = [EBP+8]); the sibling passes `this+0x70` (0x008ABAFB). The
contents are equal after the copy, so the difference is observable only if the vcall writes through it.

## Claims

- C1 (read): `this` arrives in ECX (0x008ABA51) and one 4-byte stack argument is popped by `RET 0x4`
  (0x008ABAAE).
- C2 (read): the body copies the 64 bytes at `[arg1]` into `this+0x70..+0xAF` with four MOVAPS loads and
  stores (0x008ABA4C-0x008ABA71) before any test, so the copy happens on both flows.
- C3 (derived from C2): MOVAPS faults on a non-16-byte-aligned address, so when this function returns
  normally both `arg1` and `this+0x70` were 16-byte aligned. A rebuild must keep or check that alignment.
- C4 (read): when `[this+0x08] == 0` the function returns after the copy (JZ 0x008ABA7E to 0x008ABAA8).
- C5 (read): when `[this+0x08] != 0` it computes `[[[this+8]+0x74]+8] * [0x00A3D65C]` on x87
  (0x008ABA83, 0x008ABA89), with [0x00A3D65C] = 0.5f (data.json), stores it as a float stack argument
  (FSTP over the pushed ECX slot, 0x008ABA97) and calls `[[this+0x14]]+0x0C` with ECX = [this+0x14] and
  stack args (arg1 pointer, tolerance*0.5, &buffer) in that order from first to last (0x008ABA95-0x008ABA9B).
- C6 (derived from the frame at 0x008ABA43-0x008ABA46 and the pushes at 0x008ABA4F/0x008ABA50/0x008ABA7D):
  the buffer at ESP+0x10 after the pushes lies 0x20 below the aligned frame top, so it is 16-byte aligned and
  the compiler reserved 32 bytes for it, up to the aligned frame top - room for one min/max AABB pair of
  16-byte vectors. Above it lie 0-12 bytes of alignment padding and the saved EBP. That is where the local
  ends, not a hard limit on what a callee could write. The true size the vcall writes: unverified (settled
  by resolving the target of [[this+0x14]]+0x0C).
- C7 (read): it then calls 0x008DE950 with ECX = this (0x008ABAA1) and the buffer address as the one stack
  argument (0x008ABA9E-0x008ABAA0); 0x008DE950 ends in `RET 0x4` (0x008DE992, read in its asm.s).
- C8 (derived from C5, C7 and the POP EDI/ESI/EBX at 0x008ABAA8 with no ESP fix-up after either call): both
  callees clean their own stack arguments (12 bytes for the vcall, 4 for 0x008DE950), otherwise the
  register restores would read wrong slots.
- C9 (read, from 0x008ABAC0's asm.s): the sibling 0x008ABAC0 can set +0xA0..+0xAF on its own (0x008ABAD8),
  and passes +0x70..+0xAF as one block (`this+0x70`) to its vcall (0x008ABAFB); this function writes
  +0x70..+0xAF (C2). Meanings (unverified): +0xA0 as the translation/position rests on the sibling's caller
  0x008AC080 being 'set position', which knowledge/actor-frame-map.md:293 marks U; 'rotation' for the 48
  bytes +0x70..+0x9F rests further on the hkTransform layout (marked unverified in 0x008ABAC0.md C6). Settled
  by naming 0x008AC080 from an independent source or by reading a consumer of +0x70..+0x9F. That the object
  is a Havok shape phantom (and not a rigid body) is unverified too: it rests on the sibling's caller and on
  0x008ECC60 reading the same +0x70 block on a phantom.
- C10 (read): the vcall's transform argument is the caller's pointer (EAX = [EBP+8], pushed at 0x008ABA9A),
  not `this+0x70`; the sibling pushes `this+0x70` (0x008ABAFB).
- C11 (read): no access to a clock or time global; the only global read is 0x00A3D65C.
- C12 (read in 0x008DE950's asm.s; race derived): when F2 runs and [world+0x88]+[world+0x8C]==0
  (0x008DE963-0x008DE970), 0x008DE950 increments world+0x88 with plain MOV/INC/MOV (0x008DE995-0x008DE9A2).
  When the sum is nonzero it reports error 0x11 through 0x00898820 and returns at 0x008DE992 without
  incrementing. The decrement is `DEC dword ptr [ECX+0x88]` at 0x008DEB15, also without LOCK. Derived from
  both non-atomic read-modify-writes and from the check-then-increment: two threads running F2 on bodies of
  the same world can both pass the zero check and both increment, so they race on the counter and on the
  guard it implements.
- C13 (read, pseudocode disagreement): pseudo.c shows the copy as sixteen 4-byte moves and drops the
  `this` of both calls (it prints `FUN_008de950(local_30)` without `param_1`). The instructions are four
  16-byte aligned MOVAPS and pass ECX = [this+0x14] and ECX = this; the instructions win.
- C14 (unverified): the virtual +0x0C is the shape's getAabb(transform, tolerance, out).
