## Purpose

Enters one level of the clock freeze on a `TimeInfo`. The byte at +0x00 is a
nesting counter (read: incremented unconditionally at 0x0047D127/0x0047D12C).
Only on the outermost entry (counter was 0 before the increment, test at
0x0047D12A, branch at 0x0047D12E) it calls `GetTickCount` and rewrites +0x10
and +0x14 as "now minus the field": +0x10 := now - +0x10, +0x14 := now - +0x14
(0x0047D136..0x0047D141). Nested entries only increment the counter.

What the rewrite is for (derived, from this function and the sibling export
0x0047D0F0, whose mapping is in progress): the outer exit at 0x0047D0FF..0x0047D110
applies the same "now minus the field" to both fields, so across one bracket
with no other write in between, each field ends at its old value plus the
frozen stretch (t_exit - t_entry). The stretch is shifted out of the clock's
bookkeeping rather than discarded by a flag.

## Calling convention and parameters

- `this` in ECX (read: `MOV ESI,ECX` at 0x0047D121; both callers load
  `MOV ECX,0xB33E90` right before the call - 0x00494A13 -> 0x00494A18 and
  0x004E15CF -> 0x004E15D6 in the frame-clock exports). Ghidra prints
  `__fastcall(char *param_1)`; with no stack argument that is the same
  register contract as `__thiscall`.
- No stack arguments; plain `RET` at 0x0047D145 (ret 0), nothing for the
  caller to clean (read).
- ESI is saved and restored (PUSH 0x0047D120 / POP 0x0047D144). EAX, ECX, EDX
  are clobbered (read).
- Return: none meaningful. EAX holds the old counter in AL on the nested path
  and now - old +0x14 on the outer path (read: 0x0047D123, 0x0047D13B). The
  caller 0x004E1580 overwrites EAX at 0x004E15DB right after the call (read);
  0x004949E0 does not read EAX in 0x00494A1D..0x00494A2B (read); treated as
  `void`.

## Control flow

| ID | Condition | Address | Taken | Fall-through |
|---|---|---|---|---|
| B1 | old counter (AL, before the increment) != 0 | `TEST AL,AL` 0x0047D12A, `JNZ 0x0047d144` 0x0047D12E | nested entry: counter incremented, nothing else, return | outer entry: `GetTickCount`, rewrite +0x10 and +0x14, return |

The increment at 0x0047D127 is unconditional and happens before B1; the flags
for B1 come from the `TEST` at 0x0047D12A on the old value (the `MOV` at
0x0047D12C does not change flags) (read).

Test flows for the rebuild (derived from B1 and the 8-bit `ADD CL,0x1`):

1. counter 0 -> becomes 1; +0x10 = now - old +0x10; +0x14 = now - old +0x14; GetTickCount called once.
2. counter 1 (nested) -> becomes 2; +0x10, +0x14 unchanged; GetTickCount not called.
3. counter 0xFF -> wraps to 0x00 (8-bit add, no check); old value nonzero, so B1 taken: fields unchanged, GetTickCount not called.
4. Unsigned wrap of the subtractions: now < old field -> 32-bit two's-complement result (plain `SUB`, no check), e.g. now 5, field 10 -> 0xFFFFFFFB.

## Claims

1. **read** - +0x00 is a byte nesting counter, not a flag: every call adds 1 (`ADD CL,0x1` 0x0047D127, stored 0x0047D12C), regardless of its old value.
2. **read** - The callee is `GetTickCount` (KERNEL32), called indirectly through the IAT slot 0x00A280D0 at 0x0047D130; it is the only callee (meta.json callees).
3. **read** - GetTickCount is called only when the counter was 0 before the increment (B1, 0x0047D12A/0x0047D12E).
4. **read** - On that path, +0x10 := now - +0x10 (0x0047D136..0x0047D13E) and +0x14 := now - +0x14 (0x0047D13B, 0x0047D141), both 32-bit, no overflow handling.
5. **read** - The function writes no other field and no global (no other store in 0x0047D120..0x0047D145).
6. **read** - thiscall-style: `this` in ECX, no stack arguments, `RET` (ret 0); both known callers pass g_timeInfo 0x00B33E90 (0x00494A13, 0x004E15CF).
7. **read** - pseudo.c agrees with the instructions (increment, test on the old value, the two subtractions); no disagreement found.
8. **derived** (claim 1 + the 8-bit add) - when the counter is 0xFF, a call wraps it to 0 without touching the fields; 256 nested entries without an exit would leave the counter at 0 with the fields in their "frozen" form.
9. **derived** (claims 3-4 + 0x0047D0F0's asm 0x0047D0F3..0x0047D110, mapping in progress) - when one outer Freeze at tick t1 is followed by the matching outer exit at tick t2 with no other write to +0x10/+0x14 in between, each field ends at old + (t2 - t1).
10. **derived** (claim 9 + the update 0x0047D170: `SUB EDX,[ECX+0x14]` 0x0047D176, `SUB ESI,[ECX+0x10]` 0x0047D1F3, `MOV [ECX+0x10],EDX` 0x0047D23E) - when no update runs inside the bracket, the next variable-mode update computes ms = tick - (start + D) and delta = ms - (lastMs + D), i.e. the unfrozen delta minus 2*D, where D = t2 - t1. Both fields are shifted by D, so the stretch is subtracted twice (all shifts mod 2^32). The delta goes negative when 2*D exceeds the unfrozen delta (D beyond half of it); a negative delta takes the 2^32 fix-up (0x0047D20D) and then the ceiling (0x0047D213/0x0047D220, 0xA6). A delta of exactly 0 becomes 1 ms (`MOV ESI,0x1` 0x0047D1F8), and any positive delta over the ceiling is clamped to 0xA6 (0x0047D220). Whether this is the intended effect is not settled here; see open questions.
11. **derived** (claim 4 + 0x0047D176, 0x0047D186) - when an update runs while the counter is nonzero, it computes tick - (t1 - startTick) from the rewritten +0x14 and writes that to 0x00B39DB0 before its frozen test at 0x0047D18C.
12. **unverified** - that GameMessageBoxA 0x004949E0 and LoadBaseFormModels 0x004E1580 are the only callers. meta.json callers lists only those two, and a grep over re/export finds `CALL 0x0047d120` only at 0x00494A18 and 0x004E15D6. But re/slices/time-info/functions.txt line 6 says 0x00406169 reads g_timeInfo and calls the freeze pair (0x004061AF, 0x0040616E), and the manifest places 0x00406169 / 0x004061AA in code with no containing function, which meta.json would not list; the caller list is therefore likely incomplete. Settled by a full-binary scan for E8 rel32 targets resolving to 0x0047D120 plus indirect references to 0x0047D120.

## Open questions

- Claim 10 (delta = unfrozen delta - 2*D, negative once 2*D exceeds the unfrozen delta): does the double shift actually occur in the game, or does something else (an update inside the bracket, another writer of +0x10/+0x14) change the arithmetic? An emulator case (tools/difftest) running Freeze, Unfreeze and Update in sequence on known ticks would settle the arithmetic; whether an update runs inside a bracket needs the callers' frames (GameMessageBoxA is modal - does its message loop drive the main loop's update?).
- The knowledge file says the update writes "this frame's tick" to 0x00B39DB0; the update's instructions write tick - +0x14 (0x0047D176, 0x0047D186), i.e. ms since start. Belongs to 0x0047D170's mapping; flagged here because claim 11 depends on it.
- Callers outside defined functions (0x00406169 / 0x004061AA per the manifest): which function, and do they always pair Freeze with Unfreeze?
- Is the counter ever read outside this pair and the update's `CMP byte ptr [ECX],0x0` at 0x0047D18C (which treats any nonzero depth as frozen)?
