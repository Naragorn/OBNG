measured shadow run, 2026-10-27). Map only, no rebuild in either run.

## Purpose

A pure scheduler over globals. It takes the frame's seconds, adds the time
carried from the last call, and decides how many physics steps this frame
runs (0x00BA7914) and how long each is (0x00BA790C), keeping what it does
not hand out in the carry 0x00BA7910. It calls nothing (**read**), so it
cannot step the world itself (**derived**). It touches no subsystem object:
only fixed globals and its two stack arguments (**read**).

Order of work (**read**, addresses below):

1. Store the raw frame seconds in 0x00B2E2E4 (0x00889817), add the carry
   0x00BA7910 (0x0088981D), store the sum `T` in 0x00B2E2E0 (0x00889823).
2. Clamp `T` to 166.66667 (0x00A3D14C), in seconds here (0x00889829-0x00889844).
3. `T <= 0` (ordered): no steps, step length 0, return (0x008898A2-0x008898C0).
4. Step cap = 2 when the flag argument is non-zero, else 3 (0x00889850-0x0088985D).
5. Dispatch on the update type 0x00BA7918: 0 -> 0x0088996D, 10 ->
   0x00889933, anything else falls through to 0x00889871 (0x00889860-0x0088986B).

Clock reads and writes: the only clock input is argument 1, which the
caller loads from `TimeInfo.frameSeconds` 0x00B33E9C (0x0040D8B0) right
after `TimeInfo::Update` 0x0047D170 (call at 0x0040D8AB) - **read**. The
function writes no clock field; it writes its own time globals 0x00B2E2E4,
0x00B2E2E0, 0x00BA7910 and the outputs 0x00BA7914, 0x00BA790C (**read**).

### Second pass: the measured run against the instructions

The measurement (OBNG.dll probe, run `artifacts/shadow/obng-shadow/20261027-082656`,
OBNG.log lines 10-32, **measured**): update type 0 in every summary; in play
1 step on 99.5 % of the samples, 2 on most of the rest, 3 twice (OBNG.log
lines 18 and 28: `3+:1`); `0x00BA790C` read once per 10 s summary, 0.013333
in all twelve `Probe` summaries (OBNG.log lines 10-32 hold twelve `Probe`
lines, eleven of them paired with a `Shadow` line).

The task stated that "the static reading of the type-0 branch does not
produce these numbers". That premise does not hold; two facts were missing
from it:

1. **The type-0 branch has a half-step path.** When `trunc(T/STEP) == 0`
   and `T >= STEP*0.5`, it runs one step of exactly `T` and clears the
   carry (P4: B10 at 0x008899AD, B13 at 0x008899FF, S = T at 0x00889953,
   N = 1 at 0x00889959, R = 0 at 0x00889963) - **read**. So a fixed 1/60
   step does **not** give 0 steps on some frames for frames between 8.33 and
   16.67 ms; it gives one step of the frame's length on each (**derived**
   from P4 and the read paths; this was already claim 7 of the first
   mapping).
2. **In the measured run `STEP` was not 1/60.** OBVR's `StepPhysicsRate`
   (`OBVR/src/game/HandBodies.cpp:342-360`) writes `1/rate` into 0x00B2E2E8;
   the run's OBVR.log line 474 reads `Hands: the physics step 0.01670 s ->
   0.01333 s (75 Hz)` (again at lines 1648 and 3087; set back to 0.01670 at
   1563 and 3005) - **measured**. The 0.01670 before the write is the INI's
   `fMaxTime=0.0167` (`Oblivion.ini` in the Proton prefix, line 371), not
   the image's 1/60 (**measured**, file read 2026-10-27).

Which of the two produced the measured numbers (**derived**): the frame's
seconds are whole milliseconds times 0.001f (0x0047D170, knowledge/frame-clock.md;
`iFPSClamp=0` in the same Oblivion.ini, so the fixed-step mode is off -
**measured** file content). At 75 Hz the frames therefore read 0.013 or
0.014 s, never 0.013333. Through P4 (STEP = 0.0167 or 1/60) the step
length would read 0.013000 or 0.014000; only through P2 with STEP = 1/75
does it read 0.013333. A float32-per-operation model of the type-0 paths
(PC24 approximated by rounding every result to float; not the emulator)
over 7500 frames of ms-quantised 75 Hz gives: STEP = 1/75 -> P2 on 7498,
P4 on 2, step length 0.013333 on 7498; STEP = 0.0167 or 1/60 -> P4 on all
7500, step length 0.013000/0.014000 only. Since all twelve `Probe` summaries read
0.013333, the measured frames ran **P2 with STEP = 1/75** - one fixed step
of the step OBVR had written, the 13/14 ms quantisation absorbed by the
carry - not P4. This holds under the condition that the summaries fell in
the stretches where OBVR's 1/75 was in place; OBVR.log carries no
timestamps, so the alignment is **unverified**.

## Calling convention and parameters

- **cdecl, two stack arguments, bare `RET`.** The caller pushes two dwords
  (0x0040D8BD, 0x0040D8BE) and cleans with `ADD ESP,0x8` at 0x0040D8CA
  (**read**, frame-clock export). Every exit is `C3` after `ADD ESP,0x8`
  undoing the function's own `SUB ESP,0x8` at 0x00889814 (**read**).
- **No `this`.** ECX is first written at 0x00889850 (`MOV CL,...`) and fully
  defined by `SBB ECX,ECX` at 0x0088985B before any read of the full
  register; no other register is read before it is written (**read**).
- **Return value: none.** The caller does not read EAX after the call
  (0x0040D8C7 loads ECX, 0x0040D8CA adjusts ESP, 0x0040D8CD calls)
  (**read**).

Stack use: two locals at `[ESP]`/`[ESP+4]` hold the 64-bit `FISTP` result
and the modified control word; argument 1's slot `[ESP+0xC]` is reused for
the saved control word and the step count fed to `FILD` (0x008898C9,
0x00889903, 0x0088997D, 0x008899B1) - **read**. The x87 stack is empty at
every `RET` (**derived**, tracked through every path). The control word is
saved before each `FISTP` and restored right after (0x008898C9/0x008898F2,
0x0088997D/0x0088999E) - **read**.

### Type-0 stack trace (the branch the questions are about, **read**)

At 0x0088996D the x87 stack is `[T, 0]`. `FLD STEP` -> `[STEP, T, 0]`;
`FST S` (0x00889973) writes `S = STEP` provisionally; `FLD ST1; FDIV
ST0,ST1` -> `T/STEP` on top; `FISTP` -> `N`. With `N != 0`: `FSTP ST2`
-> `[T, STEP]`; `FILD N; FMUL ST3` -> `N*STEP`; `FSUBP` -> `T - N*STEP`
stored to `R` (0x008899C7); `T - R` stored to `T` (0x008899D9); `R` compared
with `STEP` (0x008899DF). With `N == 0`: `STEP * 0.5` (0x008899F2) compared
with `T` (0x008899F8); P4 overwrites `S = T` (0x00889953), P5 overwrites
`S = 0` (0x00889A11).

### Where pseudo.c and the instructions disagree (the instructions win)

1. **Rounding.** pseudo.c writes `ROUND(T / STEP)`; the instructions set
   rounding control to truncate (`OR EAX,0xC00` at 0x008898DA, 0x00889986)
   before `FISTP` - **read**.
2. **NaN at the ceiling.** pseudo.c's `if (T <= kFrameCeilingMs) ... else`
   would clamp a NaN `T`; B1 jumps past the clamp on unordered - **read**.
3. **NaN at the carry clamp.** pseudo.c's `if (STEP <= R) R = STEP` leaves a
   NaN `R`; B12 falls through on unordered and stores `R = STEP` - **read**.

## Claims

1. **read** - cdecl with two stack arguments (float seconds, byte flag),
   caller cleans 8 bytes (0x0040D8CA), every exit a bare `RET`; no `this`,
   no callee.
2. **read** - argument 1 is `TimeInfo.frameSeconds` 0x00B33E9C, loaded at
   0x0040D8B0 right after `TimeInfo::Update` (call 0x0040D8AB).
3. **read** - the step cap is 3, or 2 when the flag byte is non-zero
   (0x00889850-0x0088985D); it bounds `N` in type 0 and "other" (B6, B9).
4. **read** - type 0 has four outcomes: `N = min(trunc(T/STEP), cap) >= 1`
   steps of `STEP` with the carry `T - N*STEP` (P2), clamped to `STEP`
   (P3); with `trunc == 0`, one step of exactly `T` and carry 0 when
   `T >= STEP*0.5` (P4), else no step and everything carried (P5).
5. **derived** (from claim 4, image or INI `STEP` of about 1/60): when the
   carry is 0 and the frame lasts between `STEP/2` and `STEP` (8.3-16.7 ms),
   type 0 runs one step of the frame's own length (P4) and the carry stays 0,
   so every such frame has one step - not 0 steps on some frames. A fixed
   1/60 step with a carry is not what the instructions do below one step.
6. **derived** (from 0x00889973, 0x0088997B, 0x008899C3, 0x008899DF/E8,
   0x008899F2, 0x00889953): in type 0, `STEP` 0x00B2E2E8 is used five ways:
   provisional step length, divisor for the count, multiplier for the carry,
   clamp on the carry, and (halved) the threshold below which no step runs.
   In P2/P3 the step length is `STEP`; in P4 it is `T`, which is below `STEP`
   when the 24-bit quotient truncates to 0. So in type 0, for finite
   `STEP > 0` with `T/STEP < 2^32`, a step is never longer than `STEP`: it
   is a maximum step length (matching the setting's name `fMaxTime`), not a
   fixed step. The condition matters: with `STEP == 0` or NaN, `FISTP` at
   0x00889991 stores the 64-bit integer indefinite (low dword 0), so `N = 0`,
   B13 0x008899FF takes its `>=`/unordered branch and P4 sets `S = T`, longer
   than `STEP`; a `STEP` below about 3.9e-8 (`T/STEP >= 2^32` at the
   166.67 ceiling) leaves `N` as the quotient's low dword and can reach the
   same P4 (**derived** from the instructions; not run, open question 6). A
   user INI with `fMaxTime=0` would hit the `STEP == 0` case. In "other" types it is only the
   divisor for the count (0x008898D4), and `S = T/N` can exceed it; type 10
   does not read it.
7. **measured** (run 20261027-082656, OBVR.log:474, 1563, 1648, 3005, 3087)
   - during the shadow run OBVR rewrote `STEP` 0x00B2E2E8 from 0.01670 to
   0.01333 (1/75) and back several times; the INI value was
   `fMaxTime=0.0167` and `iFPSClamp=0` (Oblivion.ini lines 371, 52).
8. **derived** (from claims 4 and 7, the ms quantisation of `frameSeconds`
   read in 0x0047D170 per knowledge/frame-clock.md, and a float32 model of
   the type-0 paths - not the emulator): at 75 Hz the measured step length
   0.013333 comes from **P2 with STEP = 1/75** - one step of OBVR's step
   per frame, the frames' 13/14 ms read absorbed by the carry. P4 with
   STEP = 0.0167 would have read 0.013000 or 0.014000. The run therefore
   does not show the game's own 60 Hz planner; whether every summary fell
   while OBVR's 1/75 was in place is **unverified** (OBVR.log has no
   timestamps).
9. **derived** (claim 4, model above) - a 2-step frame in type 0 needs
   `T = frameSeconds + R >= 2*STEP`, and the carry `R` can be anywhere in
   `[0, STEP]`: P3 sets `R = STEP` (0x008899E8) and P2 can leave `R` just
   below `STEP`. Only with the steady-state 75 Hz carry (<= about 0.67 ms,
   STEP = 1/75) does this mean a frame read as 27 ms or more, or 26 ms with
   a carry of at least about 0.67 ms. After irregular frames a normal frame
   also reaches it: in the float32 model, two consecutive 20 ms frames, or a
   14 ms frame after a 13 ms carry, give 2 steps; the trace 13, 13, 14, 60,
   13, 13, 14 ms gives `N = 3` on the 60 ms frame with `R` clamped to `STEP`
   (P3), then `N = 2` on an ordinary 14 ms frame two frames later. So a
   2-step sample does not by itself imply a frame of two display periods;
   it is one way to reach the threshold, a normal frame draining the carry
   of an earlier long frame is the other. The windows with both 2-step and
   3+ samples (OBNG.log lines 18 and 28) fit the second. The flag
   0x00B333B8 never makes 2 steps; it only lowers the cap from 3 to 2.
   Which of the two produced the measured 2-step samples is **unverified**:
   `SamplePlanner` (plugin/src/ShadowTimeInfo.cpp:119-126) reads only
   0x00BA7918 and 0x00BA7914, no per-frame `frameSeconds` or carry, and `S`
   is read once per summary. Settled by open question 1.
10. **derived** (claim 4, model above) - at 90 Hz in type 0 with the game's
    own STEP (1/60 or 0.0167) and carry 0: frames read as 11 or 12 ms take
    P4, one step of 0.011 or 0.012 s each, never 11.1 ms exactly (ms
    quantisation). The P4 step lengths need carry 0: after a long frame, P2
    frames with `S = STEP` run until the carry drains. Never 0 steps holds
    without that condition (`T >= STEP` gives P2, `STEP/2 <= T < STEP` P4). With OBVR's 1/90 they take P2, one step
    of 0.011111 s, the quantisation in the carry. Zero-step frames appear
    only when `T < STEP/2` (P5): with STEP = 1/60 at 120 Hz and above, e.g.
    144 Hz alternates 0 and 1 steps (model: 3750/3750 of 7500 frames).
11. **read** - type 10: one step of a smoothed length `SM += 0.05*(T - SM)`
    (0x00889933-0x00889963), carry reset to 0, `T` kept. **derived**: time
    is not conserved in this type (`T - SM` is neither carried nor run).
12. **read** - any other type: below 1/120 s (0x00A95CA8) the time is
    carried and no step runs (P7); otherwise the carry is reset and `T` is
    split into `max(1, min(trunc(T/STEP), cap))` equal steps (P8, P9).
13. **derived** (from B6/B9 bounding `N <= 3` and `JGE` on `TEST EAX,EAX`) -
    the 2^32 fix-ups at 0x0088990D and 0x008899BD are unreachable (MSVC's
    unsigned-to-float pattern).
14. **derived** (float32 model, STEP = 1/60, a 50 ms frame from carry 0) -
    `T - 3*STEP` can round to a tiny negative carry (-3.7e-9), which the
    next call adds to its frame; whether PC24 x87 gives the same is
    **unverified** (emulator not run).
15. **measured** (plugin/src/ShadowTimeInfo.cpp:119-126, 155-174) - the
    probe samples `M` and `N` inside the `TimeInfo::Update` detour, i.e.
    after 0x0040D8AB and before this function's call at 0x0040D8C2, so each
    sample is the previous call's output, and it fires for every
    `TimeInfo::Update` (any instance), not once per main-loop frame. In play
    the summaries count about 750 samples per 10 s at 75 Hz (one per frame,
    **derived**). The first window's `0:2956 ... 3+:52333` (loading and
    main menu) is therefore not the planner's output per frame; what it
    reflects is **unverified**.
16. **For OBVR** (not edited from here): OBVR's note that type 0 at 90 fps
    leaves "about one frame in three" without a step
    (`OBVR/docs/hand-weapon-collision-spec.md:643-644, 687`,
    `OBVR/src/game/HandBodyLogic.h:326-328, 343`) disagrees with P4 (claims
    5, 10) - **derived**; OBVR's own `StepPhysicsRate` makes P2 the path
    that runs in its sessions (claim 8). OBVR's "Step length = fMaxTime"
    misses P4 (step = `T`) and P5.
