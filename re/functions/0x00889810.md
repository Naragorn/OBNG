## Purpose

This is neither the Havok world step nor a driver that calls it. It is a
pure scheduler over globals: it takes the frame's seconds, adds the time
carried from the last frame, and decides how many physics steps this frame
runs (0x00BA7914) and how long each step is (0x00BA790C), keeping the
time it does not hand out in the carry 0x00BA7910. It calls nothing
(**read**: no `CALL`), so it cannot step the world itself (**derived**).

Order of work (**read**, addresses below):

1. Store the frame seconds (0x00889817), add the carry, store the sum `T`
   (0x00889823).
2. Clamp `T` to 166.66667 (0x00A3D14C) - in seconds here (0x00889829-0x00889844).
3. `T <= 0`: no steps, return (0x008898A2-0x008898C0).
4. Step cap = 2 when the flag argument is non-zero, else 3 (0x00889850-0x0088985D).
5. Dispatch on the update type 0x00BA7918: 0 = fixed step with carry,
   10 = smoothed single step, anything else = the whole time split into
   equal steps (0x00889860-0x0088986B).

### Answers to the slice's question

- **Where the physics step comes from.** In type 0 the step length is the
  global 0x00B2E2E8 (image value 0.016666668 = 1/60, data.json) - **read**
  (0x0088996D-0x00889973). OBVR says it is the runtime copy of
  `fMaxTime:HAVOK` (**unverified** here). In type 10 it is a smoothed
  value 0x00B2E2EC; in the other types it is `T / N`.
- **Is it clamped by the same 166.67 ceiling?** The same constant address
  0x00A3D14C is read (0x00889829) - **read**. But here it is compared
  against seconds (the input is `TimeInfo.frameSeconds`, pushed from
  0x00B33E9C at 0x0040D8B0), while `TimeInfo::Update` 0x0047D170 compares
  it against milliseconds (knowledge/frame-clock.md). So it caps `T` at
  about 167 s, not at 167 ms (**derived**). It is not the effective frame
  clamp of the physics: that is the step cap of 3 (or 2) and, in type 0,
  the carry clamp to one step (**derived**, branches B6/B9 and B12). Why a
  milliseconds constant serves as a seconds limit (a shared literal folded
  by the compiler, or an intended guard for the integer conversion) is
  **unverified**.
- **Is there a fixed-step accumulator?** Yes, in type 0: the carry
  0x00BA7910 takes `T - N*step` and is clamped to one step, so time beyond
  `N` steps plus one step is dropped (**read**, 0x008899AF-0x008899E8).
  It is not a pure fixed step: when `T` is under one step but at least half
  a step, a single step of length `T` runs (**read**, B13 to 0x00889953).

## Calling convention and parameters

- **cdecl, two stack arguments, `RET` with no operand.** The caller pushes
  two dwords and cleans with `ADD ESP,0x8` at 0x0040D8CA (**read**, frame-clock
  export). Every exit is a bare `RET` (`C3`) after `ADD ESP,0x8` that
  undoes the function's own `SUB ESP,0x8` at 0x00889814 (**read**).
- **No `this`.** ECX is first written at 0x00889850 (`MOV CL,...`) and fully
  defined by `SBB ECX,ECX` at 0x0088985B before any read of the full
  register (**read**). No other register is read before it is written
  (**read**).
- **Return value: none.** EAX is left holding scratch (status word or the
  step count) and the caller does not read EAX after the call (0x0040D8C7
  loads ECX, 0x0040D8CA adjusts ESP, 0x0040D8CD calls) (**derived**).

Stack use: two locals at `[ESP]`/`[ESP+4]` hold the 64-bit result of
`FISTP` and the modified control word; argument 1's slot `[ESP+0xC]` is
reused as scratch for the saved control word and for the step count fed
to `FILD` (0x008898C9, 0x00889903, 0x0088997D, 0x008899B1) - **read**. So
the caller's copy of argument 1 is overwritten; the caller does not read it
back (**derived** from 0x0040D8C7-0x0040D8CA).

The x87 stack is empty at every `RET` (**derived** by tracking the stack
through each of the nine paths below). The control word is saved before
each `FISTP` and restored right after (0x008898C9/0x008898F2,
0x0088997D/0x0088999E) - **read**.

### Where pseudo.c and the instructions disagree (the instructions win)

1. **Rounding.** pseudo.c writes `ROUND(T / STEP)`; the instructions set
   rounding control to truncate (`OR EAX,0xC00` at 0x008898DA and 0x00889986)
   before `FISTP`. The step count is `trunc`, not round (**read**).
2. **NaN at the ceiling.** pseudo.c's `if (T <= kFrameCeilingMs) ... else T =
   kFrameCeilingMs` would clamp a NaN `T`; the instructions jump past the
   clamp on unordered (B1, `TEST AH,0x41` with C0 and C3 set) and keep the
   NaN (**read**).
3. **NaN at the carry clamp.** pseudo.c's `if (STEP <= R) R = STEP` leaves a
   NaN `R`; the instructions fall through on unordered (B12, PF=1 for 0x05)
   and store `R = STEP` (**read**).

## Claims

1. **read** - cdecl with two stack arguments (float seconds, byte flag),
   caller cleans 8 bytes (0x0040D8CA), every exit is a bare `RET`; no
   `this`, no callee.
2. **read** - the input is `TimeInfo.frameSeconds`: the caller loads
   0x00B33E9C at 0x0040D8B0 and stores it into the first argument slot at
   0x0040D8BF, right after the `TimeInfo` update call at 0x0040D8AB.
3. **read** - the function writes the raw input to 0x00B2E2E4 (0x00889817)
   and `input + carry` to 0x00B2E2E0 (0x00889823) on every path.
4. **read** - the 166.66667 constant 0x00A3D14C (data.json) is compared
