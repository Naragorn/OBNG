## Purpose

One-time start of Oblivion's Havok layer, guarded by the "Havok is initialised" byte 0x00BA8040:

1. Routes two function pointers 0x00B2EB04 / 0x00B2EB08 to 0x00889770 / 0x006078C0 (an aligned allocate / free
   pair on the game heap object 0x00B02020 - derived, see C3).
2. Makes the memory manager: a 0x2C-byte block from FormHeap (0x00401F00), constructed by 0x008A7060 (base vtable
   0x00A95C00), then given the final vtable 0x00A95C70.
3. Hands it to the base-system init 0x008BBA80 as `(memory, 0, printf 0x00981FC6, 0)`. That init (pseudocode)
   stores the manager as the global 0x00BA7D98, makes a 0x330-byte thread memory for this thread and puts it into
   the TLS slot +0x19C, makes a second one as the global fallback 0x00BA7D9C, and sets 0x00BA8040 = 1.
4. Drops its own reference to the manager (refcount at +0x0C).
5. Gives the calling thread's thread memory (TLS +0x19C, or 0x00BA7D9C when the slot is null) the static stack area
   0x00B47900, 0x60000 bytes, through vtable slot 0 = 0x008A7220 (set stack area).
6. 0x008A83C0: fills three 0x80-byte static tables at 0x00BA7DB0 / 0x00BA7E30 / 0x00BA7EB0 (pseudocode shows
   memset and bit masks - proposal: the collision layer filter matrix, unverified).
7. Allocates 0x18 bytes through the manager (slot +0x10, args 0x18, 0x24), writes the word 0x18 at +4, constructs
   it with 0x0088A570 (vtable 0x00A95CE4, sub-vtables at +8..+0x14) and stores it in 0x00BA7904.
8. A long run of class registrations: 0x00712590(name, factory) for 43 `bhk*` / `hk*` NiObject classes
   (bhkBoxShape .. bhkExtraData). Not listed here.

Clock: the function neither reads nor writes any timer or frame-clock global (read: data_refs in meta.json hold no
clock address).

## Calling convention and parameters

- No parameters (read: no `[ESP+n]` argument read; ECX pushed at 0x0088B07E as a frame slot, not used as this).
- `this`: none.
- Stack: SEH frame with security cookie (0x0088B070..0x0088B08C, handler 0x009D62EB, cookie 0x00B30AAC);
  epilogue restores FS:[0] at 0x0088B41A, `POP ECX; POP ESI; ADD ESP,0x10; RET` at 0x0088B421..0x0088B426.
- Saved registers (read): only ESI is saved (PUSH ESI at 0x0088B07F) and restored (POP ESI at 0x0088B422).
  ECX is not preserved: the PUSH ECX at 0x0088B07E only reserves a local frame slot, which 0x0088B0C4 overwrites
  with the new manager pointer; POP ECX at 0x0088B421 pops the cookie word (EAX = [0x00B30AAC] ^ ESP, pushed at
  0x0088B087), so ECX leaves holding that value; the ECX slot is dropped by `ADD ESP,0x10` at 0x0088B423. The
  convention is unchanged by this, since ECX is caller-saved (volatile).
- Returns with plain `RET` (ret 0), caller-cleaned (no arguments). Return value: none meaningful (EAX is
  whatever the last call left).
- Callee conventions seen at the call sites (read, from stack adjustments):
  - 0x00401F00 FormHeap_Allocate: cdecl, `ADD ESP,4` at 0x0088B0C1.
  - 0x008A7060: thiscall, ECX = block (0x0088B0D4).
  - 0x008BBA80: cdecl, four pushes, `ADD ESP,0x10` at 0x0088B0FC. Note: its pseudocode signature shows two
    parameters; the caller pushes four (`obj, 0, 0x00981FC6, 0`) - the instructions win.
  - vtable slot +0x34 of the manager: thiscall with one push (1) at 0x0088B10A.
  - thread memory slot 0 (0x008A7220): thiscall, pushes size then buffer, no `ADD ESP` after 0x0088B155 -
    callee cleans 8 bytes (read: B1's direct jump at 0x0088B09E and the fall-through both reach 0x0088B416,
    whose `[ESP+0xC]` read and fixed pops need the same ESP on both paths, so no pushed argument may remain).
  - manager slot +0x10: thiscall, pushes 0x24 then 0x18, callee cleans (read, same reason).
  - 0x0088A570: thiscall, ECX = the new block (0x0088B16D).
  - 0x00712590: cdecl (name, factory), cleaned in batches of eight by `ADD ESP,0x40`, the last six by
    `ADD ESP,0x18` at 0x0088B413.

## Open questions

1. Does 0x00BA7D9C (fallback thread memory) ever receive a stack area? If not, a Havok query on a thread without
   a slot would run with start/end 0 - what does the stack allocator then do (overflow path through +0x28 = -1?).
   Next: grep writers of thread-memory +0x20 / +0x2C, and read 0x008A7530 / 0x008A7650 / 0x008A76E0 (slots 2..4).
2. The 2 000 000-byte area per Havok worker vs. 0x60000 for the main thread: what decides the size a query needs
   (the character controller's 750 places in the area)? Measure the high-water mark of +0x20..+0x2C per call.
3. Which Havok world mode is `[obj+0xB4] == 9` (0x0088AEB0) - is the worker pool ever started in the shipped game
   with the default INI? 0x00B2E2D4 = 1 in the file; may be overwritten by an INI setting (unverified).
4. Role of the 0x18-byte object at 0x00BA7904 (0x0088A570, vtable 0x00A95CE4 with four sub-vtables) - proposal:
   the Havok-to-Gamebryo stream / listener object; unverified.
5. Whether the 0x2C memory manager (vtable 0x00A95C70) is itself thread-safe for allocate/free from several
   threads at once (it is shared by every thread memory via +0x10). Slot list 0x00889650.., 0x008A7130, 0x008A7170
   not yet read.
