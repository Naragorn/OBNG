## What it does (read)

Argument in ST0, result in ST0. 0x00982C30 stores the argument as a double on
its frame; 0x00991B88 tests the stored high dword for exponent 0x7FF and
leaves ZF set for inf/NaN; 0x00982C4D then:

1. PUSH EDX; FSTCW [ESP] - the caller's control word is written over the
   low word of the pushed EDX, so the POP EDX at the end restores a garbage
   EDX (measured in FastSqrtOracleTest: 0x5A5A5A5A in gives 0x5A5A027F or
   0x007F007F back). EAX and ECX are clobbered too. Callers rely on none of
   the three.
2. Not inf/NaN: when the word is not 0x027F, 0x00991B15 loads
   (word & 0x0300) | 0x007F - precision control kept, round to nearest,
   every exception masked. Sign set: -0 goes on to the root, any other
   negative to the DOMAIN exit (FSTP; FLD the indefinite NaN; EAX = 1).
   Otherwise FSQRT.
3. After the root: with 0x00BA9DDC zero, EDX = 5 (the function code), ECX =
   "sqrt", JMP 0x00991BAB: word 0x027F - return; the word's PM bit clear -
   FLDCW word, return; FSTSW with PE clear - FLDCW word, return; else EAX =
   8 (INEXACT) and CALL 0x00991AB7.
4. 0x00991AB7 stores ST0 as a double, builds the record {type, name,
   argument, result}, calls __87except(5, record, &word), reloads the double
   and FLDCWs the word when it is not 0x027F. __87except for INEXACT:
   __handle_exc(0x10, &result, word) - with PM set it calls
   _set_statfp(0x20) (FLDPI; FSTP qword: a deliberately inexact store that
   sets the already set PE flag) and returns handled; __ctrlfp(word, 0xFFFF)
   loads the caller's word; __set_errno_from_matherr(8) returns without a
   write (only DOMAIN 1 -> EDOM and 2, 3 -> ERANGE write errno); the cookie
   check. For DOMAIN (a negative argument, a NaN through 0x00991B2C): the
   same path with the indefinite NaN as the result and an errno write.
5. inf/NaN (0x00982CA9): +inf takes the root of the register value (the
   stored image only classifies; a register value beyond the double's range
   reaches here as inf: measured, 2^1100 gives +inf), -inf and NaNs go to
   the error handling with 0x00991B2C's type (1, or 7 for a signalling NaN,
   which __87except turns into 1).

The precision control reaches FSQRT: at PC 24 the register result has 24
significant bits (sqrt(2) = 0xB504F3 << 40, measured on the host; the
emulator's FSQRT ignores PC - see below). The game's words are 0x007F and
0x0C7F (measured, knowledge/frame-clock.md), so every caller gets a 24-bit
root, rounded to nearest whatever the caller's rounding control.

## Why it costs (measured)

The game's words are never 0x027F and have PM set, so every inexact root -
nearly all of them - runs step 4: 1.7 % of the render thread's out-of-pass
samples and 1.2 % of its in-pass samples at Gold Road spot 2 (OBVR's render
sampler, knowledge/render-thread-outside-the-pass.md), about 0.2 ms a frame
(derived), on top of the 0.08 ms the roots themselves take.

## The rebuild (plugin/src/FastSqrtLogic.h, FastSqrt.cpp)

Not a rebuild of the arithmetic - the arithmetic is one hardware instruction
and stays one - but of the dispatch around it: the same store, the same
tests on the stored high dword, FSQRT under the same word, the caller's word
back, and nothing else, for a finite non-negative argument under a word with
every exception masked at PC 24 or 53. Everything else (negative, inf, NaN,
an exception unmasked, PC 64 or the reserved encoding) jumps to the original
through the detour's trampoline and keeps its behaviour to the byte, errno
included. The dispatch preserves ECX and EDX (a superset of the original,
which clobbers them), clobbers EAX, and skips the two FLDCW when the
caller's word already is the square root's (0x007F, 0x027F).

Generated as 133 bytes of machine code by CodeWriter (plugin/src/FastSqrtLogic.h
BuildFastSqrt), so the same bytes run in the tests and in the game.

## Evidence

- Decisions, bytes and the generated code on the host's x87 against a plain
  FSQRT under the square root's word: plugin/tests/FastSqrtLogicTest.cpp
  (200 000 random inputs over six fast words, every flow of the decisions).
- Against the original's own bytes (Oblivion.exe's .text 0x00980000..,
  .rdata and .data mapped at their addresses in the 32-bit test process,
  __set_errno_from_matherr stubbed to record the type): plugin/tests/
  FastSqrtOracleTest.cpp, 1.8 million calls over 0x007F, 0x0C7F, 0x047F,
  0x087F, 0x027F, 0x037F - the 80-bit result, the control word, the
  exception flags, the stack top and the errno writes equal on every call;
  EDX kept by the dispatch on every fast call. The condition codes C0..C3
  differ on about 29 % of the PC-24 calls (the original's FLDPI/FSTP in
  _set_statfp changes C1 after the root); no caller reads them (the next
  FCOM/FUCOM overwrites them). Measured 2026-11-08.
- The emulator layer (tools/difftest/emulate.py) is not used for this
  function: Unicorn 2.1.4's FSQRT ignores precision control (sqrt(2) under
  FPCW 0x007F gives the 64-bit significand 0xB504F333F9DE6484 where the
  hardware gives 0xB504F30000000000; measured 2026-11-08), so it cannot
  decide the result the game's callers get. The host oracle above runs the
  original's bytes on the real x87 instead.
- In the game: [Shadow] Sqrt=1 (FastSqrt.cpp) compares the original and the
  dispatch per call from the same x87 state (FXSAVE/FXRSTOR); the run is
  recorded in re/ledger.md.
