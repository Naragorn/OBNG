## Purpose

Once a frame for each skin instance, it builds that skin's bone palette: one matrix for
each bone, written into a heap buffer that the skin instance record owns. Then it calls a
method of the object at `this+0x8AC` with a flag. The palette goes to the GPU as vertex
shader constants (OBVR's census, knowledge/bone-palettes.md). That upload is not in this
function.

Subsystems, in instruction order:

1. **Stamp gate**: reads the value returned by 0x00422DE0 on `[this+0x8B0]`, compares it
   with the record's stamp, and writes the stamp (read). Whether that value is a frame counter
   is **unverified** (C1).
2. **FormHeap**: frees and allocates the palette buffer when it must grow or the mode changes,
   then initialises the fixed entries in mode 4.
3. **Transform math**: inverts one transform (0x00718A80) and composes two (0x0053D7A0 twice).
4. **Scale test**: a flag test that the instructions can never satisfy (see Claims C9).
5. **Optional skin-to-world matrix** (arg5 != 0): packs it into the record's scratch matrix
   at +0x28 through 0x00761BE0.
6. **Per-bone loop**: composes each bone, runs the same never-true scale test, may compose
   once more (arg5 == 0), then packs a 4x4 element (mode 4) or writes a 4x3 row block
   (every other mode), with a global offset subtracted from the translation.
7. **Renderer callback**: `[[this+0x8AC]]+0xFC(flag)`.

The game clock (TimeInfo, frame seconds) is neither read nor written. The only stamp-like value
is the value 0x00422DE0 returns on `[this+0x8B0]`, which is read twice (0x0076560F, 0x00765623).
The record's stamp +0x18 is written once, at 0x00765638 (read). That this value is a frame
counter is **unverified** (see C1).

## Calling convention and parameters

- `__thiscall`. ECX holds `this`, which is copied to ESI at 0x007655FF and saved at
  `[ESP+0x20]` at 0x0076560B. The callee cleans the stack with `RET 0x14` at 0x0076598D (read),
  so there are **five stack arguments**. The seed's "one argument" is wrong (read: `RET 0x14`;
  pseudo.c also lists param_2..param_6).
- Frame: `SUB ESP,0xE8`, then pushes of EBP, ESI and EDI. EBX is pushed only after the gate, at
  0x00765622. The early exit 0x00765984 skips `POP EBX` to match (read).
- Return: none. Nothing is computed into EAX for the caller. EAX holds whatever the last call
  left (derived from the epilogue 0x00765983-0x0076598D).

## Claims

### The gate (question 2)

- **C1** The build is skipped exactly when `skin->buildStamp` equals the value 0x00422DE0
  returns for `[this+0x8B0]`. The compare is `CMP EDI,EAX; JZ` (0x00765614/0x00765616), an
  equality test with no ordering. Any different value, older **or newer**, leads to a rebuild.
  **read**. The compare, store and skip are read facts; calling the value a frame counter is
  **unverified**: it rests only on knowledge/bone-palettes.md (OBVR), while OBVR's
  GameAddresses.h:1463-1465 describes 0x00422DE0 as the TESObjectREFR vtbl+0x154 getter of the
  niNode at +0x3C, which would make the stamp an identity key. The instructions of 0x00422DE0
  and the type of `[this+0x8B0]` would settle it.
- **C2** A skipped build also skips the `+0xFC` callback (B1 targets 0x00765984, after the
  call). **read**.
- **C3** On a rebuild, 0x00422DE0 is called a second time (0x00765623) and that second result
  is stored to +0x18 (0x00765638). The stamp is the value read after the gate, not the
  one compared. If the two reads can differ, the stamp takes the newer one. **read**
  (whether they can differ: **unverified**).

### Buffer management

- **C4** The buffer is reallocated when `boneCount > capacity` (unsigned JA) or when
  `mode != paletteMode`. Otherwise it is kept, including when the bone count shrank.
  **read** (B3, B4).
- **C5** On reallocation the old buffer is passed to 0x00401F20 unconditionally (0x00765667).
  The pseudocode of 0x00401F20 tests for null before freeing (**unverified** at instruction
  level). The capacity becomes the current bone count, not the old maximum (0x007656FA).
  **read**.
- **C6** Mode 4 allocates `boneCount*0x40` bytes and every other mode `boneCount*0x30`.
  **read** (0x00765676-0x00765687, 0x007656A4-0x007656BA). Mode 4 has one `MUL` by 0x40
  (0x0076567D) guarded by `SETO; NEG; OR` (0x0076567F-0x00765684), which requests 0xFFFFFFFF
  on overflow (**read**). Every other mode computes `boneCount*12` with `LEA EAX,[EBX+EBX*2];
  ADD EAX,EAX; ADD EAX,EAX` (0x007656A4-0x007656A9), which wraps silently, and guards only the
  final `MUL` by 4 (0x007656B0) (**read**). Example: boneCount 0x15555556 gives
  `(uint32)(n*12)` = 8 and requests 0x20 bytes (**derived** from those instructions). A
  bit-exact rebuild must compute `(uint32)(n*12)` and check overflow only on the `*4`. Real bone
  counts never reach this (**derived**).
- **C7** Mode 4 only: on allocation, each 0x40-byte element gets four fixed entries. If arg3 is
  nonzero, floats 12, 13 and 14 are set to 0 and float 15 to 1. If arg3 is zero, floats 3, 7
  and 11 are set to 0 and float 15 to 1. The other twelve floats are not initialised here. The
  other modes' buffer is not initialised. **read** (0x00765699-0x007656F8: ST0 = 0.0, ST1 = 1.0,
  FXCH alternates).
- **C8** arg3 is not part of the reallocation test (0x0076565A-0x00765660, **read**), and the
  fixed entries are written only at allocation (0x00765699-0x007656F8, **read**). So when a
  mode-4 record keeps its buffer (C4) while arg3 changes between calls, this function does not
  set the new arg3's fixed entries to their fixed 0/1 values (**derived** from those two read
  facts). Only three of the four can be missing: float 15 = 1.0 is written under both arg3
  values (0x007656F1). The missing ones are floats 12-14 (new arg3 != 0) or floats 3, 7, 11
  (new arg3 == 0) (**derived** from C7). Whether they are really stale in the palette depends
  on C21 (the packers leave exactly those floats alone), which is pseudocode only: under C21 a
  1->0 change leaves floats 3, 7, 11 holding the old translation, so they were written, just
  not to 0; they are uninitialised only when the buffer was never packed. **unverified**
  (conditional on 0x00761AE0/0x00761B60, pseudocode only; their instructions would settle it).
  No caller is shown to change arg3 for one mode-4 record (0x00779710 passes 0, **unverified**,
  C22).

### The non-uniform-scale flag

- **C9** The flag byte `[ESP+0x18]` passed to `+0xFC` is **always 0 as a byte**, for
  real-valued scales and also for NaN; **the pushed dword is unspecified in its upper bytes**.
  The byte is set to 0 at 0x00765776. The only two writes of 1 (0x0076578A, 0x0076584E) need the
  tested scale to be `< 0.99` (fallthrough of B10/B15) and `> 1.01` (fallthrough of
  B11/B16) at the same time. NaN takes the JP at B10/B15 (C0 = C2 = 1 gives even parity).
  **derived** from read B10, B11, B15 and B16. pseudo.c shows the same conjunction
  (`local_38 < 0.99 && 1.01 < local_38`). This corrects knowledge/bone-palettes.md, which reads
  the slot as receiving a live non-uniform-scale flag, so OBVR should know. The upper three
  bytes of the pushed dword (0x00765976 reads the whole dword `[ESP+0x18]`, but only its low
  byte is written) are stale stack contents (**read**). What the callee does with them is
  **unverified**.
- **C10** The first test reads `V.scale` (`[ESP+0xC0]` = V+0x30 at 0x00765759), where
  `V = skinData.skinTransform ∘ inverse(rootNode.world)`. It does not read U or the record.
  The per-bone test reads `node.world.scale` (+0x94). **read** (offsets). The meaning of
  ∘ is **unverified** (C13).

### Transforms (order of composition)

- **C11** `T0 = 0x00718A80(this = [skin+0x10]+0x64, out = &T)`. In pseudocode, 0x00718A80
  inverts a 13-float transform (rotation through 0x00710400, scale 1/s, translation
  -(1/s)·R'·t). **read** (call shape, 0x00765703-0x0076570E); the inverse meaning is
  **unverified** (pseudocode only; the instructions of 0x00718A80 would settle it).
- **C12** `V = 0x0053D7A0(this = skinData+0x0C, out = W, rhs = &T0)`, copied to V (13 dwords,
  0x0076572D-0x00765739). `U = 0x0053D7A0(this = arg2, out = W, rhs = &V)`, copied to U
  (0x00765760-0x0076576F). **read**.
- **C13** 0x0053D7A0 is thiscall with two stack arguments (out, rhs) and cleans them itself:
  no `ADD ESP` follows any of its four call sites, and the stack offsets used afterwards
  match base. It returns a pointer that is copied from (0x0076572B, 0x00765757, 0x00765878).
  **read/derived**. In pseudocode it computes `out.s = this.s·rhs.s`,
  `out.R = this.R·rhs.R` (0x007100A0), and `out.t = this.s·(this.R·rhs.t) + this.t`. In
  other words `out = this ∘ rhs`, applying rhs first. **unverified** (pseudocode only; the
  instructions of 0x0053D7A0 would settle it).
- **C14** Per bone: `T = 0x0053D7A0(this = node[i]+0x64, out = &T, rhs = bind[i])`
  (0x00765810-0x00765820; out is T itself, and the return value is not used here). Then, only
  when arg5 == 0: `T = U ∘ T` (0x0076585D-0x0076587E). **read**.
- **C15** When arg5 != 0, U is not composed into the bones. Instead, U is packed once a build
  into `skin->skinToWorld` through `0x00761BE0(skinToWorld, &U.R, &U.t, U.s)`: cdecl,
  four arguments, `ADD ESP,0x10` (0x007657C1-0x007657DF). **read**. In pseudocode,
  0x00761BE0 writes a 4x4 with the rotation transposed and scaled and the translation in
  floats 12-14, without the global offset (**unverified**). Its fixed entries (3, 7, 11 = 0;
  15 = 1) match that layout (**derived**).

### Row layout (question 1)

- **C16** The palette element for bone i in any mode other than 4 is twelve floats at
  `palette + i*0x30`. Here T is the per-bone transform (floats T[0..8] the 3x3 rotation, T[9..11]
  the translation, T[12] the scale) and s = T[12] (`[ESP+0x58]`, 0x007658D5). **read**
  (0x007658D1-0x0076594B; EBX = palette+0x20+i*0x30, so `[EBX-0x20]` is float 0):

  | Palette float | Value | Store |
  |---|---|---|
  | 0 | T[0]·s | 0x007658DF `[EBX-0x20]` |
  | 1 | T[1]·s | 0x007658F9 `[EBX-0x1C]` |
  | 2 | T[2]·s | 0x00765914 `[EBX-0x18]` |
  | 3 | T[9] - [0x00B3F92C] | 0x00765931 `[EBX-0x14]` |
  | 4 | T[3]·s | 0x007658E8 `[EBX-0x10]` |
  | 5 | T[4]·s | 0x00765902 `[EBX-0x0C]` |
  | 6 | T[5]·s | 0x0076591D `[EBX-0x08]` |
  | 7 | T[10] - [0x00B3F930] | 0x0076593E `[EBX-0x04]` |
  | 8 | T[6]·s | 0x007658F1 `[EBX]` |
  | 9 | T[7]·s | 0x0076590B `[EBX+0x04]` |
  | 10 | T[8]·s | 0x00765924 `[EBX+0x08]` (`FMUL [ESP+0x48]` = T[8]) |
  | 11 | T[11] - [0x00B3F934] | 0x0076594B `[EBX+0x0C]` |

  The rotation is written as stored, row by row, with no transpose, and every rotation entry
  is multiplied by s. **The translation is not multiplied by s**. It is copied minus the global
  vector at 0x00B3F92C/30/34, which is 0.0 in the file image (data.json) and whose runtime
  writer and value are **unverified** (a write-xref scan of 0x00B3F92C-0x00B3F934 or a runtime
  read would settle it). s is the scale of the composed per-bone transform (per
  C13: node scale · bind scale, and · U.s when arg5 == 0). It is not "the skin's world scale"
  as the seed put it (**derived** from C13/C14, which rest on pseudocode).
- **C17** Floats 3, 7 and 11 are the translation, as the seed said. Taking T's rotation as
  row-major (`m[row][column]`, knowledge/corpse-becomes-zombie.md line 51), each palette row r
  is `(s·R[r][0], s·R[r][1], s·R[r][2], t[r] - origin[r])`, so the element is the
  3x4 matrix `[sR | t - origin]`. **derived**.

### Packed path (question 3)

- **C18** Only `mode == 4` selects the packed path (B18 compares with exactly 4). `mode == 3`
  goes down the 4x3 row path like any other value that is not 4. **read**.
- **C19** Forcing arg3 to 1 when mode == 3 (0x00765652) has no effect inside this function,
  because arg3 is read only on mode-4 paths (0x007656CC inside B5's mode-4 branch, and
  0x00765892 after B18). **derived** from read B2, B5 and B18. It is still a write into the
  caller's argument slot, which the caller cannot observe after `RET 0x14`.
- **C20** In mode 4, both packers get the same four cdecl arguments, pushed at
  0x0076589A-0x007658C6 and cleaned by `ADD ESP,0x10`: `(float* dest = palette + i*0x40,
  const float* R = &T[0], const float* t = &T[9], float s = T[12])`. arg3 != 0 calls
  0x00761B60 and arg3 == 0 calls 0x00761AE0. **read**. pseudo.c drops the fourth argument
  for 0x00761B60, but the instructions push it (0x0076589E-0x0076589F, shared by both
  branches). The instructions win.
- **C21** In pseudocode, 0x00761B60 writes the rotation as stored, scaled, into floats 0-2,
  4-6 and 8-10, and the translation minus the 0x00B3F92C vector into floats 3, 7 and 11: the
  same values as the 4x3 path, padded to 0x40. 0x00761AE0 writes the transposed rotation,
  scaled, and the translation minus the vector into floats 12-14. Each leaves exactly the four
  floats untouched that C7 initialised for its arg3. **unverified** (callee pseudocode only;
  the instructions of 0x00761AE0, 0x00761B60 and 0x00761BE0 would settle it); the match with C7
  is **derived**.

### Callers (pseudocode only)

- **C22** 0x00779710 calls `(skin, param_7, 0, 4, 0)`: mode 4, arg3 0 (0x00761AE0), arg5 0.
  0x007C9230 calls `(skin, param_7, 0, 3, 1)`: mode 3, rows, with the separate skin-to-world
  matrix. In 0x007FB6F0 Ghidra shows pushes of mode 3 and arg3 0, and arg5 is not recovered.
  Each call is guarded by `[ecx+0x34] == 0` in the caller. **unverified** (rea-all pseudocode,
  not instructions). The call-site instructions in 0x00779710, 0x007C9230 and 0x007FB6F0
  (their asm.s) would settle it.

### Cost shape

- **C23** Per bone, the builder makes one 0x0053D7A0 call when arg5 != 0, or two calls plus a
  13-dword copy when arg5 == 0. It also makes one x87 compare whose result can never change the
  flag (C9). Once per build it does one inverse, two composes, two 13-dword copies, and, when
  arg5 != 0, one 0x00761BE0. **derived** from the read loop body.

| Callee | Why | Mark |
|---|---|---|

| 0x00761AE0 / 0x00761B60 / 0x00761BE0 packers | tiny, pure, same signature; a rebuild of the builder needs them bit-exact | signature read, bodies unverified |
| 0x00718A80 transform inverse | once per build; pure | unverified |

## Open questions

1. What writes the global vector at 0x00B3F92C/30/34 at runtime? It is subtracted from every
   palette translation, so it may be a world-origin rebase. That matters to OBVR's bone rebase
   (`src/render/BoneRebase.h`).
2. What does the vtable slot `+0xFC` of the object at `this+0x8AC` do with a flag that is
   always 0 as a byte, with unspecified upper bytes (C9)? Does any other caller of that slot pass 1?
3. Is the value 0x00422DE0 returns on `[this+0x8B0]` a frame counter (knowledge/bone-palettes.md),
   another per-render counter, or an identity key such as a niNode pointer (OBVR
   GameAddresses.h:1463-1465)? Settled by the instructions of 0x00422DE0 and the type of
   `[this+0x8B0]`. If it is a counter: under a dual pass (two renders a frame), does it advance
   between the renders? That decides
   whether the palette is built once a frame or once a render (knowledge/bone-palettes.md,
   unverified section).
4. What is `skin+0x10` (the node whose world transform is inverted)? Is it the skin's root
   parent (as in Gamebryo's NiSkinInstance), and what is arg2? The signature `(skin, world,
   transpose, registersPerBone, worldSpaceBones)` and the mode-3-forces-transpose rule look
   like Gamebryo's `NiDX9Renderer::CalculateBoneMatrices`. I could not verify this. No
   Gamebryo source or symbol was consulted.
5. What are the 0x18 bytes after the 13 floats in each 0x4C bind-transform record (the seed's
   "bound")? This function does not read them.
6. 0x007FB6F0's fifth argument (arg5) needs its call-site instructions.

## Layout requests

Fields a shared header (`SkinInstanceRecord`, `SkinData`, `NiTransform13`) would need:

- `SkinInstanceRecord` (0x007655F0): +0x08 `SkinData* skinData`, +0x10 `Node* rootNode`,
  +0x14 `Node** boneNodes`, +0x18 `uint32 buildStamp`, +0x1C `uint32 paletteCapacity`,
  +0x20 `float* palette`, +0x24 `uint32 paletteMode`, +0x28 `float* skinToWorld` (16 floats).
- `SkinData` (0x007655F0): +0x0C `NiTransform13 skinTransform`, +0x40 `uint32 boneCount`,
  +0x44 `BoneBind* bones` (stride 0x4C, first 0x34 bytes an `NiTransform13`).
- `NiTransform13`: `float R[9]` (+0x00), `float t[3]` (+0x24), `float s` (+0x30), size 0x34.
- Node (NiAVObject): +0x64 `NiTransform13 world` (scale at +0x94).
- Renderer: +0x8AC object pointer (vtable slot +0xFC), +0x8B0 object pointer (`stampSource`;
  its +0x3C is returned by 0x00422DE0, meaning unverified).
- Globals: 0x00B3F92C float[3] `paletteOrigin`; 0x00A88D40 double 0.99; 0x00A88D38 float
  1.01.
