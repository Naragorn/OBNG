## Purpose

For one geometry `P` (arg1) and one ShadowSceneNode (arg2, or found from P's shader
property when arg2 is null), this function first detaches P from every light that
currently lights it (0x007C5750) and, when that reports true, walks the node's
light list (`[node+0xE8]`, the head of the list at node+0xE4) and, for every
entry with a non-null light, asks `light->IsInRange(P, sourceLight)` with a
temporary NiPointer copy of the light's source light; when the answer is true it
calls `light->AddGeometry(P)`. It returns AL = 1 after the walk (also when there is
no property, or the list is empty) and AL = 0 when the detach returned AL = 0.

**unverified** - The meaning of the callees this purpose and the proposed name rest
on (0x007C5750 "detach", 0x007D5790 "AddGeometry", 0x00707530 "GetProperty", the node
getter 0x007B4280) comes from knowledge/shadow-light-list-remove.md, not from this
export (no strings, no RTTI here). What the instructions carry is the call order: the
detach call, the walk of node+0xE8, the per-light test, the conditional call to
0x007D5790. Alternative readings (e.g. 0x007D5790 being a "mark visible" rather than a
list insert) are excluded only through that knowledge file; no contradicting evidence
was found. Settled by: the callee slices of 0x007D5790 and 0x007C5750 proposed below.

Subsystems touched, in order (read, from the call order in asm.s):

1. SEH frame install (FS:[0], cookie 0x00B30AAC XOR ESP) - 0x007C6100-0x007C611E.
2. Only when arg2 is null: property lookup `P->GetProperty(4)` (0x007C6132), the
   property's virtual slot +0x54 (0x007C6148), the node getter 0x007B4280 with the
   property's top nibble of +0x1C (0x007C615F).
3. The detach 0x007C5750 (0x007C6170) - the walk over the property's light list
   that calls `ShadowSceneLight::RemoveGeometry` 0x007D6940 per light (body not in
   this export; knowledge/shadow-light-list-remove.md).
4. Per node light: 0x00405AD0 (NiPointer copy, 0x007C61AB), the range test
   0x007D2EA0 (0x007C61C2), the NiPointer release (InterlockedDecrement 0x007C61DF,
   deleting destructor through vtable +0x00 at 0x007C61F5 when the count reached 0),
   and, when in range, 0x007D5790 (0x007C6202).
5. SEH frame removal (0x007C6179/0x007C620D) and return.

No clock is read or written, no timer or performance counter is called, and no
global is read besides the cookie 0x00B30AAC and FS:[0] (read: data.json lists the
three data references above and nothing else; no other absolute address appears
in asm.s).

## Calling convention and parameters

- **`__cdecl`**: both exits are a plain `RET` (0xC3 at 0x007C618C and 0x007C6220),
  so the caller removes the two stack arguments (read). This agrees with
  knowledge/shadow-light-list-remove.md ("corrected 2026-10-27 after a crash: ...
  a `ret 8` hook killed the load").
- ECX and EDX are not read before they are written: the first ECX access is the
  write at 0x007C612C or 0x007C6169, EDX is first written at 0x007C6143 or
  0x007C61A4 (read). There is no `this` register.
- Frame (ESP0 = ESP at entry, base = ESP after the eight pushes 0x007C6100-0x007C6119
  = ESP0-0x20): base+0x00 cookie XOR (ESP at 0x007C6117 = base+4), +0x04 EDI,
  +0x08 ESI, +0x0C EBP, +0x10 EBX, +0x14 previous FS:[0] (the registration record
  installed at 0x007C611A/0x007C611E), +0x18 handler 0x009CE678, +0x1C EH state
  (initial -1), +0x20 return address, **+0x24 arg1, +0x28 arg2** (read).
- **arg1 `P`** ([ESP+0x24], read at 0x007C612C, 0x007C6169, 0x007C61B3 with one push
  outstanding, 0x007C61FB): the geometry. It is `this` of `GetProperty(4)`, the stack
  argument of the detach, IsInRange's arg1 and AddGeometry's argument. This body never
  dereferences P (read). That P is an `NiTriBasedGeom` is derived in
  knowledge/shadow-light-list-remove.md (the light's +0xE4 list element type), not here.
- **arg2 `nodeOverride`** ([ESP+0x28], read at 0x007C6124 into EDI): the
  ShadowSceneNode whose light list is walked; null selects the fallback (B1). The
  slot is **reused as a local**: 0x007C61A4 passes `&arg2` to 0x00405AD0, which
  stores the NiPointer copy there; 0x007C61C9 reads it back for the release (read).
  Derived: after the first loop iteration the caller's arg2 slot holds a released
  pointer; the caller 0x007C7050 must not rely on the slot (cdecl lets the callee own
  it; whether 0x007C7050 re-pushes is unverified - its body is not in this export).
- Return: AL. `MOV AL,1` at 0x007C620B on the walk exit (B2, B5, normal end); on the
  early exit 0x007C618C AL is 0x007C5750's AL, which is 0 there (B4). The upper 24
  bits of EAX are not set by this function on either exit (read: MOV AL only, and
  0x007C5750's EAX passed through on the early exit).
- Registers: EBX, EBP, ESI, EDI saved and restored (PUSH 0x007C610E-0x007C6111,
  POP 0x007C6185-0x007C6188 and 0x007C6219-0x007C621C); ECX is the POP target of
  the cookie (0x007C6184, 0x007C6218), EDX clobbered (read).
- SEH: state at base+0x1C is set to 0 before IsInRange (0x007C61BA `MOV [ESP+0x24],0`
  with two pushes outstanding = base+0x1C) and back to -1 after (0x007C61CF) (read).
  Derived: an exception inside IsInRange unwinds the temporary NiPointer. The handler
  stub (data.json bytes at 0x009CE678, decoded with objdump) is `MOV EDX,[ESP+8];
  LEA EAX,[EDX-0x10]; MOV ECX,[EDX-0x14]; XOR ECX,EAX; CALL 0x009811E2; MOV EAX,
  0x00AF7610; JMP 0x00980EA4` - it re-checks the cookie slot (EDX = registration =
  base+0x14, so EDX-0x14 = base, EDX-0x10 = base+4) before handing a FuncInfo to the
  frame handler (read for the bytes; that 0x009811E2 is `__security_check_cookie`,
  0x00980EA4 `__CxxFrameHandler` and 0x00AF7610 a FuncInfo is **unverified**, shape
  only). The cookie is not checked on the normal exits (read: no call between the
  POPs). data.json reads 0xBB40E64E at 0x00B30AAC in the file image.

## Claims

C1. **read** - `__cdecl`, two stack arguments, plain `RET` on both exits
(0x007C618C, 0x007C6220); ECX/EDX are not inputs (first accesses are writes,
0x007C612C/0x007C6169, 0x007C6143/0x007C61A4).

C2. **read** - The node is arg2 when non-null (0x007C6124-0x007C612A). Otherwise it is
`0x007B4280((prop+0x1C) >> 28)` with `prop = P->GetProperty(4)` (ECX = P, push 4 at
0x007C612C-0x007C6132), taken only when `prop` is non-null and its vtable slot +0x54
returns a value other than -1 (0x007C6139-0x007C6167). The SUB/NEG/SBB/AND sequence
at 0x007C614A-0x007C6151 yields `prop` when the slot returned != -1 and 0 when it
returned -1 (derived from the instruction semantics: EAX+1 == 0 leaves CF clear after
NEG, SBB gives 0).

C3. **read** - When arg2 is null and `prop` is null, the function returns AL = 1 at
0x007C620B without calling 0x007C5750 or IsInRange (B2). Derived: the caller sees
"relit" for a geometry without a type-4 property.

C4. **read** - When arg2 is null and the slot +0x54 returns -1, EDI stays 0 and
0x007C5750 is called with ECX = 0 (0x007C616E). If it then returned AL != 0,
0x007C618D would read address 0xE8 (a null dereference). Whether 0x007C5750 returns
0 before reading `this` for such a property is **unverified** (its body is not in
this export; knowledge/shadow-light-list-remove.md says it gates on
`1 <= GetShaderType <= 10` first, which -1 fails, but does not say the gate precedes
the `this+0x11C` read). The same holds for a null result of 0x007B4280 (not checked,
B3').

C5. **read** - The detach `node->0x007C5750(P)` runs on every call that gets past B2,
before any list read, and its AL decides between return 0 (B4) and the walk
(0x007C6170-0x007C6177).

C6. **read** - The walk starts at `[node+0xE8]` and follows `item+0x00`; the next
pointer is loaded **before** any call for the current item (0x007C619F), and EDI is
overwritten by the source copy at 0x007C61D9, so the node is not re-read during the
walk. Derived: the walk visits the items as linked at the moment each `next` is read;
a callee that unlinked the next item would leave EBP dangling (no callee here is
known to touch the node's list: AddGeometry and the detach work on the light's +0xE4
list and the property's +0x70 list per knowledge/shadow-light-list-remove.md -
unverified for this export).

C7. **read** - Per item with non-null data: `src = *light->0x00405AD0(&arg2slot)`
(0x007C61A4-0x007C61B0), `BL = light->IsInRange(P, src)` (0x007C61B2-0x007C61C7),
release of the copy in the arg2 slot (0x007C61C9-0x007C61F5), then
`light->AddGeometry(P)` when BL != 0 (0x007C61F7-0x007C6202). The function ignores
AddGeometry's return value (read: EAX not read after 0x007C6202).

C8. **read** - This body never reads or writes the light's +0x1B0, +0x14C, +0xF4 or
any other light field: the light (ESI) only ever appears as `MOV ECX,ESI`
(0x007C61A9, 0x007C61B8, 0x007C6200). Derived: every light of the node's list with
non-null item data (B6, 0x007C61A2) is range-tested here, shadow-casting (+0xF4) or
not; the only filter is that non-null data and, inside IsInRange, the source light.

C9. **derived** (from C6, C7 and re/functions/0x007D2EA0.md C5/C6) - Within one call,
each IsInRange call goes to a different list item, so two calls inside one
invocation touch the same light's +0x1B0 only if the same light is linked twice in
the node's list (unverified; nothing here prevents or detects it). The mask question
is therefore **across** calls: light L's mask after geometry P1's test is the mask
L's test of the next geometry P2 starts from, unless something in between rewrites
it. Between those two tests the code that runs is (in this body) the rest of P1's
walk (other lights, the release, AddGeometry on L when in range), then 0x007C7050's
traversal, then 0x007C5750 for P2 (which calls 0x007D6940 RemoveGeometry on L when L
lit P2). None of them writes +0x1B0 in this body (C8).

C10. **derived** (from C9 and re/functions/0x007D2EA0.md C18) - The draw-setup run's
textual sweep found no direct `[reg+0x1B0]` writer in 0x007C0000-0x007E0000 besides
IsInRange (0x007D2F3E), the three restores in 0x007D59E0 and the constructor

unverified) is what the detach walks, not what this loop walks. What bounds N
(all ShadowSceneLights of the scene node; how many exist in the measured cell) is
**unverified**. The loop iterates every list item, including items with null data
(B6 skips only the copy, the test and the add, 0x007C61A2). Derived from C14 (the
line-76 window of OBNG.log, 2 793 260 calls in 10 seconds at 70 frames a second):
~3 990 IsInRange calls a frame from 0x007C61C7. That count is the non-null-data items
of calls whose detach returned true (the B2, B4 and B6 exits make no call), so it is a
**lower bound** on N x (geometries relit per frame), not equal to it.

C16. **derived** (from C9, C15) - Unit for a batched rebuild. The loop nesting is
geometry-outer (0x007C7050's traversal), light-inner (this function). An
IsInRange outcome depends on the light's mask, which (when the plane path runs here)
carries over from the previous geometry tested against that light; a per-light batch
over all geometries of the pass keeps, for each light, the same geometry order as
the original only if the batch preserves 0x007C7050's traversal order and nothing
else touches the mask in between (C10 open). The side effects are not order-free:
AddGeometry is an AddHead into the light's +0xE4 list and a sorted insert into the
property's +0x70 list (knowledge file), and each geometry's detach must precede its
own adds; an interchange would change list orders (sorted-insert ties, +0xE4 order),
which the remove walk's cost depends on. So the safe unit is "per geometry over its
node's lights" (this function as it is), and a per-light batch of the range test
alone is equal only under the conditions above (**unverified** in the game).

C17. **read** - pseudo.c disagrees with the instructions on every thiscall: it shows
`FUN_00707530(4)`, `FUN_007c5750(param_1)`, `FUN_00405ad0(&param_2)`,
`FUN_007d2ea0(param_1,*puVar6)` and `FUN_007d5790(param_1)` without the `this` that
asm.s loads into ECX (P at 0x007C612C, the node at 0x007C616E, the light at
0x007C61A9, 0x007C61B8, 0x007C6200). The instructions win. pseudo.c's
`puVar5[0x3a]` is `[node+0xE8]` (0x3A x 4) and agrees.

## Open questions

1. Is `+0x14C != 0` for any light in a node's +0xE4 list? (C12; cheapest: the probe at
   0x007C61C2 counting `[ESI+0x14C] != 0`.)
2. Who resets `+0x1B0` between geometries, if anyone? (C10; read 0x00717A40 and the
   function around 0x007D4D11 first, then 0x007EE720, 0x007EE330, 0x007ECEC0.) If no
   one does, a plane-path light tested here narrows its mask monotonically until a
   reset elsewhere - an engine defect a rebuild must reproduce bit for bit or fix
   knowingly.
3. Does 0x007C5750 read `this` before its shader-type gate (C4: the null-node path
   after B3 / a null 0x007B4280)?
4. How many lights does a ShadowSceneNode hold in the measured scene (N of C15), and
   how many geometries 0x007C7050 relights a frame? A counter on 0x007C6100's entry
   next to the existing 0x007C61C7 counter gives N on average.
5. Does 0x007C7050 reuse its pushed argument slots across calls (the arg2 slot is
   overwritten here)? Its call site is not in this export.
6. 0x009811E2 / 0x00980EA4 / 0x00AF7610 (the handler stub's targets): CRT names
   unverified; irrelevant to behaviour unless an exception is thrown.

Callees worth their own slice: **0x007D5790** AddGeometry (the in-range side effect,
the cursor scan, its callees 0x007EE330/0x007ECEC0 for the mask question),
**0x007C5750** the detach (the quadratic remove path, the null-`this` question), and
the plane builder candidate **0x00717A40** with its caller near 0x007D4D11 (who sets
+0x14C and the planes, and whether +0x1B0 is rewritten). 0x00405AD0 (NiPointer copy)
and 0x007B4280 (table lookup) are small; one read each suffices. The caller
0x007C7050 gives the traversal order the batched rebuild must keep.

## Layout requests

A shared header would need:

- `ShadowSceneNode`: `+0xE4 NiTPointerList<NiPointer<ShadowSceneLight>> lights` with
  `+0xE8 head` (static check `offsetof(lights) + 4 == 0xE8`); `+0x11C uint8_t index`
  (knowledge file; not accessed here).
- `NiTListItem<T>`: `+0x00 next`, `+0x04 prev` (knowledge file; not accessed here),
  `+0x08 data`.
- `BSShaderProperty` (type-4 property): vtable slot `+0x54 GetShaderType()` returning
  `int` (-1 = plain NiShadeProperty); `+0x1C uint32_t flags` with bits 28..31 the
  ShadowSceneNode index.
- `NiRefObject`: `+0x00 vtable` with slot 0 the deleting destructor taking `bool`,
  `+0x04 volatile LONG refCount`.
- `ShadowSceneLight`: `+0x100 NiPointer<NiLight> sourceLight` (what 0x00405AD0
  copies; knowledge file), plus the IsInRange fields of re/functions/0x007D2EA0.md
  (`+0x14C`, `+0x150 planes[6]`, `+0x1B0 activePlanes`).
- Free functions: `bool RelightGeometry(NiGeometry* P, ShadowSceneNode* nodeOverride)`
  `__cdecl`; `ShadowSceneNode* 0x007B4280(int index)` `__cdecl`.
