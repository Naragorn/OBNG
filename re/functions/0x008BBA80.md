# 0x008BBA80 - Havok base system init (proposal)

Slice: havok-thread-conditions. Map only, not rebuilt. Evidence: `re/export/havok-thread-conditions/0x008BBA80/`
(meta.json, asm.s, data.json, pseudo.c) and the caller's asm `re/export/havok-thread-conditions/0x0088B070/asm.s`.
Callee bodies were read only as pseudocode from `re/export/rea-all/functions/0x<address>.c`; those claims
carry the mark **Up**.

Marks: **R** read in the instructions (address given), **D** derived (from which R facts),
**U** unverified, **Up** unverified, seen in pseudocode only.

## Purpose

Once for calls that do not overlap (guarded by the byte 0x00BA8040 with unlocked accesses; see claim 1), installs Havok's memory system and its
process-wide service objects, and gives the *calling* thread its per-thread allocator:

1. Guard: when byte `[0x00BA8040] != 0`, returns 0 at once (R 0x008BBA80-0x008BBA88).
2. 0x008BA9C0: zeroes the calling thread's TLS block fields +0x1A0, +0x1AC, +0x1A4, +0x1A8 (Up). Per
   knowledge/actor-frame-map.md, +0x1A4/+0x1A8 hold the per-thread RDTSC profiler markers.
3. When arg1 (the memory object) is null: jumps to 0x008BBB7A, an `INT3` (R 0x008BBA97-0x008BBA99, 0x008BBB7A).
4. 0x008A70F0(arg1): installs arg1 as the process-global memory `[0x00BA7D98]`, adding a reference at
   arg1+0x0C and releasing the previous one through its vtable +0x34 (Up; the call and its cdecl cleanup are R 0x008BBA9F-0x008BBAA9).
5. Per-thread allocator for the calling thread: when arg2 is null, `FormHeap_Allocate(0x330)` and
   0x008A72A0 (thiscall, this = the new block, args (arg1, 0)) build one (R 0x008BBAAC-0x008BBACB);
   when the allocation returns null, null is used (R 0x008BBACD). The result (or arg2 when non-null,
   R 0x008BBAA5/0x008BBAAE) goes to 0x008A7260, which writes it into TLS +0x19C, adds a reference at
   +0x14 and releases the old one through vtable +0x08 (Up).
6. 0x008BA9C0 again: zeroes TLS +0x1A0..+0x1AC a second time (R call at 0x008BBAD5; effect Up).
7. Shared fallback allocator: a second `FormHeap_Allocate(0x330)` + 0x008A72A0(arg1, 0) is stored in
   `[0x00BA7D9C]`, or 0 when the allocation failed (R 0x008BBADA-0x008BBB00). knowledge/actor-frame-map.md
   records that Havok code uses `[0x00BA7D9C]` whenever TLS +0x19C is null.
8. An 8-byte object from `[0x00BA7D98]`->vtable+0x10 (args (8, 0x15)): +0x04 = 8 (word), +0x06 = 1
   (word), +0x00 = vtable 0x00A98240; handed to 0x00534070, which stores it in `[0x00BA7FB4]` and
   releases the previous one (R 0x008BBB06-0x008BBB28; 0x00534070's body Up).
9. A 0x28-byte object from the same allocator slot (args (0x28, 0x15)): +0x04 = 0x28 (word),
   constructed by 0x008BB560 (thiscall) with (arg3, arg4), and handed to 0x00534020, which stores it in
   `[0x00BA7FB0]` (R 0x008BBB2D-0x008BBB5C). 0x008BB560 writes vtable 0x00A982C0, +0x06 = 1, +0x20 = arg3,
   +0x24 = arg4 (Up). From the caller, arg3 = 0x00981FC6 and arg4 = 0 (R 0x0088B0E5-0x0088B0EE); that
   0x00981FC6 is a printf-like report function is the slice's "known" line, U here.
10. 0x008BB420: walks a singly linked list headed at 0x00BA8188, calls each entry's create function,
    stores non-null results through entry[2], and retries the ones that returned null until none is
    left or no progress (Up) - proposed: the singleton registry's initialisation.
11. `[0x00BA803C]`->vtable+0x08() (thiscall, no stack args; R 0x008BBB64-0x008BBB6C). What
    `[0x00BA803C]` is: U (not written by this function; presumably one of the singletons from step 10, U).
12. Sets byte `[0x00BA8040] = 1` (R 0x008BBB6F) and returns 0 (R 0x008BBB76).

Clock: the body has no RDTSC, no timer import and no reference to a time global (R, whole asm.s).
The only clock-adjacent effect is step 2/6, which zeroes the calling thread's TLS profiler fields
(Up via 0x008BA9C0; their meaning from knowledge/actor-frame-map.md).

## Calling convention and parameters

- `__cdecl`: four stack arguments, plain `RET` (R 0x008BBB79); the caller removes 0x10 bytes with
  `ADD ESP,0x10` (R 0x0088B0FC). No `this`: ECX is not read before it is overwritten (R).
- ESI is saved at 0x008BBA87 and restored at 0x008BBB78 (R); ESI holds arg1 from 0x008BBA93 on.
- Return value: EAX = 0 on both normal paths (R 0x008BBB76). The arg1 == 0 path ends in INT3 and has no return (R 0x008BBB7A).

Pseudocode disagreement (instructions win): pseudo.c declares only two parameters and passes
`unaff_ESI, unaff_retaddr` to 0x008BB560. The asm reads `[ESP+0x14]` and `[ESP+0x10]` at
0x008BBB3F/0x008BBB43 with only ESI on the stack, i.e. args 4 and 3, and pushes them for 0x008BB560
with ECX = the 0x28-byte object (R 0x008BBB47-0x008BBB51). pseudo.c also omits the `this` of
0x008A72A0 and 0x008BB560 and shows the INT3 path as a `swi(3)` call with a return.

## Claims

1. **R** The body runs at most once for calls made after a first call has completed: it tests byte 0x00BA8040 first (`MOV AL,[0x00BA8040]` at 0x008BBA80, `JNZ` at 0x008BBA88) and sets it to 1 last (`MOV byte ptr [0x00BA8040],0x1` at 0x008BBB6F). Both are plain, unlocked byte accesses with no interlocked instruction and the whole init between them, so two calls that overlap before 0x008BBB6F would both run the body (**D** from those two instructions). Today the only caller is 0x0088B070 (meta.json), which checks the same flag again at 0x0088B092 (`CMP byte ptr [0x00BA8040],0x0`, equally unlocked; R).
2. **D** (from 1) A second thread that calls 0x008BBA80 after a first call has completed gets nothing: no TLS +0x19C, no zeroing of its profiler fields. Its per-thread setup must be done by other code.
3. **R** The calling thread's thread memory is one of three values: arg2 when non-null (0x008BBAA5, `JNZ` 0x008BBAAE); otherwise the result of 0x008A72A0(arg1, 0) on a fresh `FormHeap_Allocate(0x330)` block (0x008BBAAC-0x008BBACB); or null (0x008BBACD) when that allocation fails. All three are passed to 0x008A7260 at 0x008BBAD0.
4. **Up** 0x008A7260 stores its argument in TLS block +0x19C (`FS:[0x2C][_tls_index] + 0x19C`), with reference counting at +0x14 and release via vtable +0x08.
5. **R** A second 0x330-byte object of the same kind is built and stored in the global 0x00BA7D9C (0x008BBAF5), so the process has one shared allocator next to the main thread's TLS one.
6. **D** (from 3, 5 and knowledge/actor-frame-map.md: Havok code falls back to `[0x00BA7D9C]` when TLS +0x19C is null) A thread whose TLS +0x19C is null shares the single object at 0x00BA7D9C, including its unlocked stack top at +0x20 (the knowledge file's R sites); so two such threads race on it.
7. **D with Up dependencies** (from 2-6 and 0x0088B070's asm) One sufficient recipe for a second thread, not the required one - for example, as this function does: (a) zero its TLS +0x1A0..+0x1AC with 0x008BA9C0 (needed only per 0x008BA9C0's pseudocode, Up); (b) build its own thread memory over the same memory object this function received as arg1 - with `FormHeap_Allocate(0x330)` + 0x008A72A0(arg1, 0), since this function constructs with arg1 held in ESI (R 0x008BBA93, `PUSH ESI` 0x008BBAC3, call 0x008BBAC6), not with `[0x00BA7D98]`; the two are equal only if 0x008A70F0 stores arg1 there (Up, pseudocode only) - and install it with 0x008A7260 into its TLS +0x19C; (c) give that object a stack area of the thread's own through its vtable slot 0. 0x0088B070 gives the main thread's object the static area at 0x00B47900, aligned up to 16, about 0x60000 bytes (R 0x0088B110-0x0088B155); a second thread must not reuse that area (D: it is one static buffer). The engine's own template is the Havok worker 0x008BADF0 (with 0x008BB000/0x008BB020; 0x0088B070.md C12, pseudocode only, Up): it builds the thread memory as a 0x330-byte stack local with 0x008A72A0(manager, 0x10), gives it a 2 000 000-byte area from the manager via 0x008A7220, and tears down with 0x008A7220(0,0), 0x008BB020 and 0x008A7200. Everything else (0x00BA7D98, 0x00BA7D9C, 0x00BA7FB0, 0x00BA7FB4, the singleton list, 0x00BA803C) is process-wide and must not be repeated. **U**: this list stays incomplete until two things are read: whether 0x008A83C0 (called by 0x0088B070 at 0x0088B157 right after the stack area is set, R for the call) does per-thread work, and whether a fresh thread's TLS +0x19C is zero (the PE TLS directory's template).
8. **U** Whether 0x008A72A0 / the 0x330 object is safe when several of them share the same parent memory `[0x00BA7D98]` (whether the parent's allocate is locked) is not established here.
9. **R** The body contains no clock read or write (no RDTSC, timer import or time global in asm.s).
10. **Up** The only clock-adjacent effect is zeroing TLS +0x1A4/+0x1A8 (profiler markers per knowledge/actor-frame-map.md) through 0x008BA9C0, twice (calls at 0x008BBA8E and 0x008BBAD5).
11. **R** The arg1 == 0 path ends in INT3 at 0x008BBB7A, and 0x008BA9C0 has run before that test (0x008BBA8E precedes 0x008BBA97).
12. **R** Results of the allocator slot +0x10 are not null-checked (0x008BBB15-0x008BBB22, 0x008BBB3C-0x008BBB4B).
13. **R** The caller passes (memory object, 0, 0x00981FC6, 0) (0x0088B0E5-0x0088B0EE) and releases one reference at memory+0x0C right after the call (0x0088B0FF), which balances the reference 0x008A70F0 adds (Up for the add).

## Open questions

- What `[0x00BA803C]` is and what its vtable +0x08 does (the last step before the flag). Find its writer (likely in the singleton list walked by 0x008BB420, U).
- The entries of the list at 0x00BA8188: which singletons, and whether any of them is per-thread.
- Whether 0x00981FC6 really is a printf-style report function and what the 0x28-byte object at 0x00BA7FB0 does with it.
- 0x008A72A0 sets its +0x30 from `arg2 & -(parent->vtable+0x20() != 0)` (Up): the meaning of that flag and of the size-class table it builds (17 entries x2, buckets up to 0x2000).
- Whether 0x008A72A0's 0x330-byte object takes a reference on its parent (arg1).
- The TLS template: is TLS +0x19C zero for a fresh thread (the EXE's static TLS directory), so that a new thread lands on the 0x00BA7D9C fallback by default? Read the PE TLS directory.
- Why 0x008BA9C0 runs twice (0x008BBA8E and 0x008BBAD5).
- What vtable slot +0x10 of the memory object (class with vtable 0x00A95C70) is; the second argument 0x15 (proposed: a memory class / bucket id, U).

- `HavokThreadMemory` (0x330 bytes, vtable 0x00A975C8): +0x10 parent memory, +0x14 refcount, +0x20 stack top (from knowledge/actor-frame-map.md), +0x30 flag; vtable +0x00 set stack area, +0x08 release.
